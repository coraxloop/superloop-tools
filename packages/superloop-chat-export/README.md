# `superloop-chat-export` · `guide:chatexport:superloop-chat-export`

`superloop-chat-export` reads a loop's session transcripts as one record tree and renders its conversations as HTML pages. A transcript file is a view of a conversation, not a list of it: the harness rewrites whole stretches of a session when it resumes and copies a session's opening into the next session it starts, so one record appears in several places. A record is identified by its `uuid`, its first copy is the node with its parent and content, and its `parentUuid` places it in the tree.

It builds the tree, plans every page, renders the pages that changed through templates compiled into the binary, and prints one report line per loop.

## Usage · `sec:chatexport:usage`

The workspace build deploys the binary as `~/.local/bin/superloop-chat-export`. `superloop-chat-export --all` renders every registered loop and `superloop-chat-export --loop NAME` one of them, with the flags described under the command line. The output directory holds the loops index and one folder per loop:

```text
~/chats/
  index.html                 the loops index
  chat-export.css            the stylesheet the loops index shares with the pages
  chat-export-root.json      the root's manifest: the two files above with their digests
  LOOP/
    p0001.html ...           the first conversation's pages, oldest first
    c2/p0001.html ...        a later conversation's pages, beside its own pages.html
    branches/*.html          the pages of a branch file
    agents/*.html            the pages of each subagent thread
    index.html               the loop's index of conversations, pages and branches
    pages.html               the first conversation's page list
    latest.html              a forward to the newest page
    chat-export.css          the stylesheet
    chat-export.js           the script
    chat-export-manifest.json  what the pages were rendered from, and each file above with its digest
```

Each run prints one line per loop and a closing `loops=N wall_ms=N` line. The loop's line gives the counts of its first pass and its tree, then `pages_rendered` for the pages sent to the templates, `files_written`, `files_unchanged`, `files_removed` and `files_foreign` for the files of the loop's folder, and `wall_ms`; every field is described under the report. A second run over unchanged transcripts renders no page and writes no file, so its line reports `pages_rendered=0 files_written=0` with every file unchanged; a transcript that grew renders each page whose content changed, its last page and the pages after it among them, and a new program, template set or block limit renders every page. The program changes only files it made, which it knows by the digest its manifest recorded: any other file in a loop's folder is left where it is, counted as foreign, the first five of them named on the error stream with how many more there are, and one standing where the run writes a file of its own refuses that loop, which the run reports and skips before ending with status 1. A folder rendered by a version whose manifest is of another schema owns nothing, so its owner clears it once before the first run of this version.

## Command line · `sec:chatexport:command-line`

```text
superloop-chat-export (--all | --loop NAME ...) [--registry DIR] [--projects DIR] [--chats DIR] [--max-block-bytes N]
superloop-chat-export --version
```

A sole `--version` emits one JSON version record on standard error, leaves standard output empty and exits zero, or one if emission fails.

`--loop` repeats and `--all` takes every registered loop; one of them is required and they exclude each other. The registry directory (default `~/.local/share/superloop-tools/loops.d`) holds one `*.env` file per loop naming `LOOP_NAME` and `LOOP_CWD`. A loop's sessions live in the projects directory (default `~/.claude/projects`) under its working directory with every character other than an ASCII letter or digit replaced by `-`. The pages are written under the output directory `--chats` (default `~/chats`), one directory per loop, and `--max-block-bytes` (default 16384, at least 64) is the most bytes of one text a page shows; a smaller value is a usage error, since below 64 bytes a cut text no longer keeps its opening words, and a time or a record id would be cut.

A loop's name becomes a folder and a link, so it is a segment of one grammar, the one every name the program derives from a transcript's file name follows as well: one to 64 bytes of ASCII letters, digits, `-`, `_` and `.`, opening with a letter or a digit. Such a segment holds no separator, no parent component, no scheme, no query and no fragment, and every byte of it is unreserved in a URL. Every registered name is checked, selected or not: a name outside the grammar is named on the error stream, left out of the run and of the loops index, and the run ends with status 1.

A hidden `--dump-plan FILE` writes the plan of the selected loops as JSON lines, one page per line with the id of every record the page shows and its parent's id, an agent page's records linked within its thread, so the plan can be checked outside the program. The dump is created through its folder's descriptor: the folder is opened once, it and every folder above it, reached from that descriptor, are compared with the projects and the output directory by device and inode, a folder that is or lies under either is refused, and the file is created exclusively, without following a link, in the folder so checked.

An unknown loop name, a missing or conflicting selection, and an unset `HOME` without the directory flags are usage errors with status 2. An unreadable registry, projects directory or transcript file, an output directory that cannot be written or is a symbolic link, or a refused plan dump, ends the run with status 1.

## First pass · `sec:chatexport:first-pass`

The first pass reads every line of a loop's session files once and keeps only its head: the record id and the ids that link it (its parent, a boundary's logical parent and preserved tail, and the record written just before a boundary), its kind, its timestamp, its API message, the calls it makes and the calls its results answer, a boundary's compaction trigger and token counts, and the byte span of its line, so a page later re-reads exactly the records it renders. The projects folder is the operator's and is resolved as the system resolves it; below it, the loop's project folder, each session folder and its `subagents` folder, and every transcript and meta file are opened relative to their folder's descriptor without following a link, and a file is read only when the opened descriptor is a regular file. In the project folder, a regular file named `*.jsonl` is a session file and a folder of any name, one named `*.jsonl` among them, is a session folder whose `subagents` folder is read; a link of any name is left unread, since it could stand for either, and so is a pipe or other special entry named `*.jsonl`; any other entry is not a transcript and is passed over without a count. In a session folder only the `subagents` name is read, and one that is a link or not a folder is left unread. In a `subagents` folder, a regular file named `*.jsonl` is a subagent file and any other entry named `*.jsonl`, a folder among them, is left unread; other names there are passed over, the meta files being read with their transcripts. Every entry left unread for its kind is counted as `skipped`; a meta file that is a link or anything but a regular file is counted as `meta_skipped` instead, and a project folder that is a link or not a folder is named and reported as having no projects directory. The first pass takes the SHA-256 digest of each record's line as it reads it. A page reads its records through the same descriptors, checks by device and inode that each file is the one the first pass read and no shorter, and checks each record's bytes against the digest the first pass took of them, so what is rendered is what was planned. A file replaced or a record changed between the two passes ends the run with status 1 only when the run reads it again, for a page it renders or for the first prompts of the loop's index; a change to a record the run does not read again is not seen by this run, and reaches the next one through its first pass and its page keys. A line is held only up to 64 MiB; a longer one is read through without being kept and counted as `oversized`, in a session file or a subagent file alike. A session file is `STEM.jsonl` and a subagent file `agent-ID.jsonl`, each STEM and ID a segment of the name grammar; a regular `*.jsonl` file whose name is not of that form is left unread and counted as `ignored`, while a file not named `*.jsonl` is not a transcript and is passed over without a count. Of the subagent files that give one id, the first in path order is the thread and every other is left unread and counted as `ignored`, so no two threads derive one page name. Every file and entry left unread is counted, and the error stream names the first five of each kind for each loop: those left unread for their names, those whose agent id an earlier file gives, with the file rendered in its place, and those left unread for their kind. At most 16 files are scanned at once, fewer on a machine with fewer processors, and merged in load order: by first timestamp, the file with more distinct records first among equal timestamps (an original before its prefix copies), then by name. The first copy of each id in that order is the node; later copies are dropped and counted.

A record's kind is what placing and paging it needs. The owner's typed prompt and a queued command of human origin open a turn, and a slash command is the owner's within its turn; a message from another session is a peer message; meta text, text from a non-human origin and the harness's own forms are notes; tool calls, tool results, thinking, responses, compaction boundaries and summaries, system notes and attachments keep their own kinds, and a record type this version does not know loads as other.

A user record's text is the harness's by the name of the tag it opens with, never by its shape, so an owner's message that opens with a tag of any other name stays the owner's. The slash-command form opens with `command-name`, `command-message` or `command-args`; the harness's own forms are `local-command-stdout`, `local-command-stderr`, `local-command-caveat`, `bash-stdout`, `bash-stderr`, `system-reminder` and `task-notification`.

A line that is not a JSON object with well-typed known fields, or whose record ids are not canonical UUID text, is counted as malformed and skipped. Unknown fields are skipped unread, and unknown record, block and attachment kinds load as such.

## Tree · `sec:chatexport:tree`

A node's parent is the record its `parentUuid` names. A compaction boundary has none, so it takes its logical parent, else the tail of the segment its compaction preserved, else the record written just before it in its file. A `parentUuid` naming a record no file holds starts a conversation of its own. Nodes are ordered by the stable topological order: among the nodes whose parent is placed, the one written first comes next, so a record written before its parent is held back until the parent is placed and nothing else moves.

The connected components are the loop's conversations, in order of their first timestamp. A session file is a view of its conversation: the spine is the chain of files that leads to the conversation's latest record, each file reached through the node its own records first attach to; a file with records of its own off that chain is a branch, forking at that node; a file with no record of its own is a copy. The spine files' records form the conversation's main sequence and each branch file's records a sequence of their own.

The main sequence is cut at each compaction boundary into segments, in write order, each keeping its compaction's trigger and token counts. A turn is an owner message and everything written until the next one, and a segment's records before its first owner message form a turn without one. A turn's items are the owner's message (typed, queued or a slash command), responses grouped by API message with the thinking that precedes them, tool runs, compactions with their summary, peer messages, and notes. A tool run holds the calls of one API message as a group, with the result blocks that answer them and the harness traffic written between them. A record may make several calls and a record may hold several result blocks, and each call and each block is paired on its own. Every tool-use block is a call, known by its place, its record and its index among the record's tool-use blocks; its id is a property it may have, and a block that carries none is a call all the same. A result block answers a call carrying the id it names and no other: of the calls carrying that id, the nearest earlier one in the order the loop's records were read that no block answers yet, and a call whose id another call also carries says on its page that its call id is not unique. A block that names no call answers the one call of the record it names as its source, only when that record makes exactly one call, counting every tool-use block with an id or without, and no block answers it yet. Only a tool result record answers a call, and a block whose call the transcript does not determine is shown in its place as the result of a call the transcript does not identify; a block naming an id whose calls are all answered is shown as the result of the nearest earlier of them. A result block written after its call's turn closed, as one written after a queued message can be, is shown in the turn it was written in and still answers its call: which block answers which call is found over the whole loop, or the whole agent thread, so a call stays unanswered only when no result block of the transcript answers it.

A subagent's transcript and meta file are read with the sessions. The meta file names the call that spawned the agent: a call on a session's line or a call in another agent's thread. It is reached like its transcript, without following a link, and read only when it is a regular file of at most 1 MiB; one that is not, that is larger, that cannot be read or that does not parse is skipped and counted as `meta_skipped`, and its thread stands unattached. A thread's records are linked by the same rules as a session's, put once in their stable topological order and cut into turns, and stay on disk until a page needs them.

## Page plan · `sec:chatexport:page-plan`

The plan lists every page a loop has. A conversation's main pages follow its segments: within a segment a page takes records until they reach the page budget of 2 MiB of source and closes where the next turn opens, so a turn stays whole while it fits; a page never takes a record that would carry it past the page limit of 4 MiB, twice the budget, so a turn larger than that is cut there, at a record boundary, into consecutive pages, and a single record larger than the limit stands on a page of its own, its texts cut to the block limit with the bytes omitted stated, as every text is. A page therefore holds at most 4 MiB of source records, or one record, which the line limit holds to 64 MiB. Whether a page closes rests only on the records before it and the next one, so appending records only extends the last page or adds pages after it. The first conversation's pages are `p0001.html` onward at the loop's output root and a later conversation's are under `c2/`, `c3/` and on. A branch file has pages of its own, `branches/STEM-01.html` onward, and a subagent thread its own, `agents/ID-01.html` onward, each packed by the same rule; a thread without records keeps one empty page, so the call that spawned it has a page to link to. A numbered name puts its number of two or more digits after the last `-`, so two distinct stems or ids never derive one name, and before it writes anything a run checks that no two entries of its plan derive the same path, refusing to render the loop when two do. Each page records its span, the positions of its records in its sequence, its turns, its size, and the SHA-256 digest of its path and of each record's id, file, byte span and the SHA-256 digest of its bytes, so a record whose bytes change, whatever their length, gives its page another plan digest unless SHA-256 collides, and the page reads the changed bytes when it is built. The plan digest names what a page is built from and is written to the plan dump; it does not decide whether the page is written, which is its key's, below.

## Pages · `sec:chatexport:pages`

A page shows every one of its records once, in plan order, each with its anchor `r-` and the record's id: the owner's messages (typed, queued with a marker that it was sent while the agent worked, and slash commands shown as the command with its arguments), responses with their thinking, tool runs with each call's input and the result that answers it, compaction dividers with their summary, messages from other sessions, and notes. A tool run keeps its entries in plan order: the calls of one message form a group at the first call, a result joins its call when its own parent is already shown, and otherwise it is shown at its own place with a link to its call, on the page that holds the call, so no record comes before its parent. A page shows only its own records: a turn it cuts opens with a link to the page the turn began on and closes with a link to the page it goes on to, the owner's message stays on the first of its pages, and the record anchors, the prompt list, the calls that spawned a subagent and the records where a branch forks each link to the page that holds the record. The rendering of one page reads back and holds only its own records, and visits only their places: each turn keeps an index of every record's place in its items, in order of position, built once with the tree, and a page takes from it the places of its own records, so a page cut from a long turn or a long tool run does work in proportion to its own records, however long the rest. Nonstructural displayed text is cut in Rust to `--max-block-bytes` with the number of bytes it omitted. A page's records are read back one at a time as a stream from their byte spans, and nonstructural string values are cut to the block limit as they are decoded, their full lengths kept for the omitted count, while a member name and the value of a `type` or `subtype` member, which name and tell apart the content the view looks up, are cut only past 256 bytes or the block limit if that is larger, so the block limit cuts what is displayed and never what finds it; a name repeated within one object keeps its first member, and the others are read through without being kept. A record a page holds therefore keeps nonstructural string values within the block limit and member names and `type` or `subtype` values within the greater of that limit and 256 bytes, and beside those texts only its structure, its numbers, members and items, at a fixed cost for each value of its line, which the line limit holds to 64 MiB; while it decodes a string or a name the decoder holds that one text whole, at most the line. At most 8 pages are rendered at once. A response's text and a compaction summary are Markdown and are rendered by the program's own writer; every other text, the owner's messages among them, is shown as text with its line breaks kept, never interpreted as markup.

Every call and every result block is shown exactly once, each with an anchor of its own made from its place: `call-RECORD-N` for the call at index N, counted from zero, among its record's tool-use blocks, with its own input, and `result-RECORD-N` for the block at index N among its record's result blocks. Anchors carry the transcript's record UUID after canonical parsing and printing, plus block indices for calls and results; they carry no raw call id or other free-form transcript text. An element's `id` is its anchor as it is, escaped for the attribute, and a link's fragment is the anchor percent-encoded, which the script decodes before it looks the element up, so a link finds its element whatever bytes an anchor holds. A call shows its result block beneath it when the block's record is on the page, the block is not shown yet and the record's parent is already shown; otherwise the call says where its result is, in one of three ways: "Its result is shown further down this page" (or "further up") with a link to the block, "Its result is shown on page N" (or "on part N" in a branch or a thread) with a link to the block on that page, and "No result was recorded" only when no result block of the transcript answers the call. A result block shown apart from its call is headed "Result of" a link to the call, by the call's tool name on the same page and as "the call on page N" on another, or "Result of a call the transcript does not identify" when the transcript determines none. A call that spawned a subagent links to the thread's first page and each of the thread's pages links back to the call, on the page that holds it; a record where a branch file forks links to the branch's page and the branch's page links back to it. Every page links to its previous and next page in its conversation, branch or thread, to the loop's index, to the loops index and to `latest.html`, which forwards to the newest page; the conversation's page list opens in a disclosure from a list file the page frames, so a page does not change when pages are added after it. The loop's index lists each conversation's pages newest first with their span, compaction, prompt count and the first line of their first prompt, and its branches; it counts the loop's subagent threads and lists, with a link to its first page, each thread no page's call links to, because its spawning call is on no page or it names none, so every thread is reached from the index or from its call. Each loop directory carries one stylesheet and one script shared by its pages; the script controls reading mode, opens the disclosures around a linked record, and marks and centres a main page's row inside its shared page-list frame. Without it the page remains readable and its page number stays visible beside the list. No page loads anything from outside the output directory.

The loops index at the root of the output directory lists every registered loop that has pages, from each loop's manifest, and links a copy of the pages' stylesheet written beside it, so it reads like the loops' pages in either colour scheme. Each link it prints is built from a checked loop name. The root keeps a small manifest of its own, `chat-export-root.json`, recording those two files with their digests under the same ownership rule as a loop's folder: each is written where nothing stands or where the program owns the file, and any other file under its name is left in place and reported, with the run ending with status 1.

A main page's heading, its title and its row in the page lists lead with the span of time it covers, the conversation and page number following, because the dates are what a reader navigates by. A record's time shows its date and time of day in UTC to the second, with the transcript's full instant in the `datetime` attribute of its `time` element; every displayed clock ends in `UTC`. An invalid source value is labelled `unparsed timestamp: TEXT` and has no `datetime` attribute.

## Markdown · `sec:chatexport:markdown`

The agent writes its responses and its compaction summaries in Markdown, so those two texts are rendered: pulldown-cmark parses them with tables and strikethrough, and a writer in the `markdown` module turns the parser's events into HTML over an allowlist of paragraphs, headings, lists, block quotes, rules, emphasis, strong, strikethrough, inline code, code blocks and tables. A heading moves two levels down, so a response's first level sits below the page's own heading; a table scrolls sideways inside its record. Every text the writer prints goes through one escape function, the one the template environment's escaping matches; raw HTML, as a block or inline, is written as escaped text; a link keeps its target only for an `http` or `https` address or a fragment of the page, and any other target is written as its text; an image is written as a link to its address, or as its description, never as an image element, so a page still loads nothing from outside the output directory. A text is cut to the block limit before it is parsed, so a code fence the cut leaves open closes at the block's end, and a response's summary line is the plain text of its first block, without the Markdown marks.

## Reading aids · `sec:chatexport:reading-aids`

A page folds the tool traffic and keeps what the owner wrote in view. A tool run, with its groups, notes and results shown apart, is one disclosure, closed by default, whose summary line counts its calls, names its tools in order of first use (six, then how many more), counts its errors and the agent threads it spawned when there are any, and gives the span of time it covers; a stretch of notes with no call folds the same way under its count, its labels in order of first use (six, then how many more, with attachments of several kinds counted under one word) and its span. A note's label says what it is: the harness form its text opens with, the origin that sent it, a message the harness wrote, a tool result shown apart from its call, or a system note or attachment by its kind; the output of a slash command is a note labelled as such, folded after the command. Inside an open run every exchange shows its input and its result, which the block limit already bounds. A response is a disclosure, open by default, whose summary is the first line of its first text, cut in Rust to 120 characters, so a closed response still says what it answered; its thinking is a closed disclosure with its size. An owner message is never inside a disclosure.

When a page has owner messages, an open disclosure under the header lists them with their time and first line, each a link to its anchor, and counts them in its summary. A reader can close it. A page without prompts has no prompt disclosure. The list is part of the page, so the page key covers it.

**Requirement (Navigation opens ready to use)** · `req:chatexport:lists-open`

The header and footer page lists are open when a page opens and can be closed. A prompt list is open and closable when the page has prompts; a page without prompts has no prompt list.

**Requirement (The page list shows the current main page)** · `req:chatexport:current-page-row`

The page-list frame loads the shared `pages.html` without a fragment. On a main page its `name` is `page-N`, where `N` is the ordinal page number from the plan and never transcript text. The list marks a row only when it is framed, its own `window.name` has that positive-decimal form, and the row exists. Where the browser exposes `frameElement`, the script also requires the frame to be in the generated `nav.pager > details.pages` position, to load `pages.html`, and to have that same `name` attribute. Where origin rules hide the element, it uses the same numeric name without that extra check, so opening an export as local files still marks and centres the row. The mark has a background, outline, bold text, a visible "Current page" label and `aria-current="page"`; centring uses only the frame's visible part and clamps naturally at the first and last rows. A branch page has no main-page row, so it supplies no page number.

|Viewing context|What the reader sees|
|---------------|--------------------|
|Generated page and list served and framed together|The frame element is checked where accessible; its matching row is marked and centred.|
|Shared list opened directly, even in a tab retaining `page-N`|No row is marked or centred because the list is the top document.|
|Generated page and list opened as files from disk|The list is framed and its generated name selects the matching row; inaccessible frame-element evidence does not suppress the mark or centring. A list opened directly from disk follows the direct case.|

Without frame-element access, a page other than a generated page could frame the shared list under a `page-N` name and cause a wrong row to be marked. This is acceptable for this reading aid: the mark decides nothing and reveals nothing, and the list's content and links are identical whoever frames it. Both paths use only the same `window.name` to choose the row, so they cannot disagree about which row is current.

**Requirement (Opening preserves the reader's position)** · `req:chatexport:opening-keeps-place`

Opening a page does not move the reader from its top or from a linked prompt. The generated frame address has no fragment, so loading or lazily loading it makes no native fragment navigation. The frame has a fixed height before its content loads, and the script changes only that frame document's scrolling element on entry, after checking that it is framed and has a numeric page name; it never scrolls the embedding document for page-list navigation and does not react to later reader scrolling. This relies on the frame's `name` being exposed inside it as `window.name` and on changing the frame's own scrolling element being confined to that frame; it does not require same-origin access to the embedding page or rely on a browser confining framed fragment navigation. Without a browser, local-file origin handling, viewport movement during lazy loading and Back navigation, centring, and assistive announcement remain unmeasured.

**Requirement (One list document serves a conversation)** · `req:chatexport:one-list-per-conversation`

Each conversation has one shared `pages.html`, reused by the header and footer frames of every main page. The embedding page says "Current page N" next to each list and in its frame title even with scripts off; the shared list then has no row marker or centring, while both available lists remain open. A page without prompts has only the page-list disclosure.

The header and footer navigation carry one button, present in the page and hidden until the script reveals it, that switches to reading prompts only: every response and every run is closed, so the page reads as the owner's messages with one line per answer, and leaving the mode opens the responses again. The mode is kept in `localStorage` under the key `chat-export.mode`, with the values `all` and `prompts`, read inside a `try` so that a browser refusing storage shows the default mode. The script loads synchronously in the page head, so it knows the stored mode before the body is parsed: in the prompts mode it marks the root element, the stylesheet hides every response's body under that mark, and once the document is parsed the script closes the disclosures and removes the mark, so a page never shows its responses open before closing them. A link to a record opens the disclosures around it in either mode. The script reads `location.hash` for record links, `window.name` for the page-list row, and its fixed storage key; it sets disclosure and button attributes, a row class and ARIA attribute, and only the frame's own scroll position, and makes no request.

The stylesheet follows the reader's colour scheme: a `prefers-color-scheme: dark` block recolours the same classes and keeps the owner's, the responses', peer and summary records apart at a glance.

## Templates · `sec:chatexport:templates`

Pages render through minijinja templates compiled into the binary: `base.html` for the page layout, `macros.html` for the navigation and one turn's items, `turns.html` for a page's turns, `page.html`, `branch.html` and `agent.html` for the three kinds of page, `prompts.html` for a page's list of prompts, `index.html` and `rows.html` for a loop's index, `pages.html` for a conversation's page list, `loops.html` for the loops index and `latest.html`. The template environment escapes every value for HTML whatever the template's name and removes the `safe` filter, which minijinja keeps in its core, so transcript text cannot be marked as already escaped and a template that tries fails to render. The one value the templates print as it is, rendered Markdown, is made in one place: the `Serialize` implementation of `Markup` in the `markdown` module is the program's only call of minijinja's `Value::from_safe_string`. `Markup` has a private field and only that module's `render` makes one, from the writer's output, so no other module can hand the templates unescaped text; a test reads the crate's sources and fails if any other file makes a pre-escaped value. minijinja is built without its builtin filters because the templates receive values the program has already counted, cut and summarised.

## Manifest · `sec:chatexport:manifest`

Each loop's output directory holds `chat-export-manifest.json`, written after the pages. It records the schema, the program and version, the SHA-256 digest of the templates and assets, the block limit, the loop's title and counts for the loops index, each source file's path, size and modification time, and each page's path, kind, conversation, record range and key: the SHA-256 digest of the whole value its template renders, the views of its records included, and every page and asset the run produced in the folder with the SHA-256 digest of the bytes written. A run reads it first: when the program, the templates or the block limit changed, or there is no manifest, every page renders; otherwise a page renders when its key changed or its file is not an owned file. To know a page's key the run builds the page's value, reading its records and making their views, on every run; only the template's rendering and the write are saved for a page whose key is unchanged. A changed record therefore renders again each page whose value it changes: its own page when the change is in what that page shows, and a page that links to it when a link's words or target change; a change to bytes no page shows, such as a field no view reads, changes the page's plan digest and renders nothing. A file is written only when its bytes change, so an unchanged run writes nothing.

A manifest cannot prove who wrote it, so it never authorises by itself. A file is the program's only when its path is of the grammar the program generates (the fixed files, `pNNNN.html`, the page lists, `cN/` pages, `branches/STEM-NN.html` and `agents/ID-NN.html`), the manifest or the journal records it, and its bytes on disk still have the recorded digest; the program removes or replaces a file only then. Every other file, a link or a file edited after the run among them, is foreign: left in place and counted, the first five by path named on the error stream with the count of the rest, and one standing where the run writes, or at a folder a written path lies in, refuses the loop before anything is written. The most a forged manifest can do is let the program remove or replace a file that has a generated name and exactly the bytes the forger recorded. A manifest of another schema, as versions before this one wrote, owns nothing, which refuses the loop where a generated name is taken.

Every key that decides whether something on disk may be kept is a SHA-256 digest stored whole, as 64 hex digits, over a stated sequence of fields, each written after its length, each list after its count and each link that may be absent after a mark of whether it is there, and led by a field naming what it keys: a page's plan digest covers its path and, for each record in order, its id, file, byte span and the digest of its bytes; a page's key covers the whole value its template renders, written as JSON: the header (the template, the loop's name, the heading, the span, the path to the assets, the navigation, the back link, and an agent's type and task), the prompt list, and the views of its records with every text, time, anchor, summary and link they print, among them the subagents its calls spawned, the branches that fork at them, where each call's result lies and each result's call, and the pages a turn it cuts began on and goes on to; the template renders that same value, made once, so whatever a page shows is covered by its key by construction, a field a view gains among them; the templates' digest covers every template's name and source, the stylesheet and the script; and a file is owned by the SHA-256 digest of its bytes. Two pages that show different things under one key are therefore a SHA-256 collision. The loop's index, its page lists, its latest page, the loops index, the stylesheet and the script carry no key: they are rendered on every run and written only when their bytes differ. No shorter hash is stored or decides what is kept: the only ones left are the hash tables of a single run, which find records and links in memory and are rebuilt on every run.

The output root and the loop's folder are opened as directories that are not symbolic links, and every path below them is reached component by component from those directories with no-follow, so a link placed below the output root, before or during a run, redirects no write; the path above the output root is resolved as the system resolves it. Each file is written to a temporary file in the folder's staging folder, `.chat-export-PID-N`, which the run makes at its first write, exclusively under a name no entry holds and with owner-only mode, pins without following a link, gives owner-only mode again through that descriptor when the process's umask took any of it away, opens from the pinned descriptor and checks to be the user's own directory of that mode, removing it again when any of that fails; the temporary file is created exclusively there and renamed from the staging folder's descriptor over its destination, a failed write removes it, and the run removes the staging folder once it is done with the folder. No other user can place or replace an entry in the staging folder, so nothing can take a temporary file's place between its creation and its rename. Before writing a file the run records its path and the digest of its new bytes in the folder's journal, `chat-export-journal.txt`, and it removes the journal once its manifest is written, so every completed page and asset of a stopped run is claimed by the journal and owned by the next run, while what it left in its staging folder stays foreign and out of the way. A reader of the journal keeps every complete line and drops only an unfinished last one, which a run stopped while recording, before it wrote the file the line names; the next run cuts that line away before it appends its own. Whatever a killed process leaves in a staging folder is foreign, never in the way.

Four control files stand outside the digests. A loop's `chat-export-manifest.json` cannot record its own digest and its `chat-export-journal.txt` lives only while a run writes, and the same holds for the root's `chat-export-root.json` and `chat-export-root-journal.txt`: the program takes each as its own when it is a regular file reached without a link that parses as its form, and a file under one of those names that does not is foreign and refuses its loop, or at the root the root's files. Of the four only a loop's manifest is counted, in `files_written` or `files_unchanged`; the journals, the root's manifest and the staging folders are named in no manifest and counted nowhere.

## Trust · `sec:chatexport:trust`

The program treats as data a stranger may have written the transcripts and the folder entries that lead to them below the projects folder, the registry, and whatever stands in the output folder when a run begins. It trusts the path the operator names for the output and that path's ancestors, and the projects folder the operator names and that folder's ancestors, since the operator chose them, and resolves them as the system does; the path of a plan dump is the operator's in the same way. It assumes no other writer changes the output folder while a run is in progress, since a writer who can do that can replace any page after the run as well, and no care during the run would protect the reader from it.

Inside those assumptions the program still guards the reader. A name it takes from the registry or from a transcript file's name becomes a folder, a file or a link only as a segment of the name grammar, and a registered working directory becomes a project folder of letters, digits and `-` alone. Below the projects folder, the program reaches the loop's project folder and every folder and file in it by descriptor without following a link, reads a transcript or a meta file only as a regular file, leaves every link, pipe and other entry unread, and renders a page only from the records its first pass read, each file checked by device and inode and each record by the digest of its bytes. A transcript line is held only to the line limit, a page holds at most the page limit of records or one record, a record read back keeps nonstructural string values within the block limit and member names and `type` or `subtype` values within the greater of that limit and 256 bytes, and a meta file is read only within its limit. Below the output root it opens, the program reaches every directory by descriptor with no-follow, owns a file only by the digest its records hold for it, and writes through temporary files created exclusively in a staging folder only the user can enter and renamed from that folder's descriptor, so a link or a file placed in the output folder before the run, or by another user during it, redirects no write and takes no temporary file's place.

## Report · `sec:chatexport:report`

```text
loop=NAME files=N records=N copies_dropped=N malformed=N oversized=N ignored=N skipped=N meta_skipped=N conversations=N segments=N turns=N prompts=N pages=N branches=N agents=N agents_nested=N agents_unattached=N held_back=N missing_logical_parents=N links=parent:N,logical:N,tail:N,previous:N,root:N,dangling:N exchanges=N groups=N unanswered=N pages_rendered=N files_written=N files_unchanged=N files_removed=N files_foreign=N wall_ms=N
loop=NAME files=0 status=no-projects-directory wall_ms=N
loop=NAME status=refused wall_ms=N
loops=N wall_ms=N
```

One line per selected loop, then one for the run. `records` counts distinct records and `copies_dropped` the record lines beyond each id's first copy; `malformed` and `oversized` count the lines of every transcript file, session and subagent alike, that do not parse and those over the line limit, `ignored` the transcript files left unread for their names, a repeated subagent id among them, `skipped` the entries of the project folder and its `subagents` folders left unread for their kind, and `meta_skipped` the subagent meta files skipped; `files` and `records` count the session files and their records; `turns` counts every turn and `prompts` those that open with an owner message; `links` counts the nodes each link rule placed; `agents_nested` counts threads spawned by another thread; `unanswered` counts the calls of the loop's conversations that no result block of the loop answers, each of which its page tells that no result was recorded; `pages_rendered` counts the pages the manifest sent to the templates. The file counts cover the loop's folder: `files_written` and `files_unchanged` every file the run produced, its manifest among them, `files_removed` the owned files this run did not produce, and `files_foreign` the files the program does not own, the first five of which the error stream names; the journal and the staging folder are in none of them. A refused loop's line says so and writes nothing; its message names the entry in the way. Every line carries its wall time in milliseconds (`[ORCHESTRATION-req:environment:wall-time-reported]`).
