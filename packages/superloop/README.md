# Loop entry · `guide:superloop:loop-entry`

`superloop` owns the public loop entry and session commands. The home and session libraries remain internal tier 1 dependencies. Private account and worker operations retain their executable boundaries.

## Entry commands · `sec:superloop:entry-commands`

`enter NAME -- COMMAND…` enters the selected loop, `provision NAME` creates its declared roots, `verify NAME` inspects roots without repairing them, and `show NAME` reads the registry row. `run-bridge gpg|ssh NAME -- ARG…` executes the selected bridge. Per-loop bridge copies dispatch by their installed filename before version handling.

The private `driver-launch`, `bind-custody` and `ensure-roots` forms preserve exact arguments and child status. They are called by declared tools rather than entered by a person.

## Session decisions · `sec:superloop:session-decisions`

`heartbeat on|off|status` and `orchestrator on|off|status [--global]` use the neutral session core. Status does not create absent state. `decide FILE` reads a schema-1 JSON observation record and applies the decision's bookkeeping to the named session as the adapter does: a heartbeat decision writes that session's guard count, warning, prompt marker and internal log under `~/.local/state/superloop-tools/hook`, and an orchestrator decision writes its rulebook snapshot and session state under `ORCHESTRATOR_STATE_DIR`, which defaults to the same directory. Neither command takes a harness event or harness transcript.

A heartbeat decision names `cwd`, `session`, `observations`, `retry` and `letters`. The observations file is JSON Lines of neutral facts: `sidechain`, optional `timestamp`, `role` (`user`, `assistant`, `other`), `real_user`, `feedback`, `results` (identifier/success pairs), and `timers` (identifier/stop/optional-delay triples). `letters.kind` is `empty`, `unread`, `history` or `failed`; the last three carry `text`. The reply names the terminal, reached path, retry count and feedback.

An orchestrator decision names `kind` (`start` or `prompt`), `class` (`fresh`, `resumed`, `tracked`), `session`, `cwd`, `source`, optional `prompt`, and optional `witnessed_digests`. The last names a JSON array of rulebook digests already observed in the session. The core compares the current rulebook digest against those observations and replies with its injection or null. Unknown fields and schemas refuse before state access.

## Command requests · `sec:superloop:command-requests`

`superloop command {judge|answer|claim|complete|status} LOOP` reads one schema-one JSON envelope from stdin and writes one verdict envelope to stdout. It composes (`[EXECUTECOMMAND-rule:executecommand:persistence]`) with effective-UID authentication and request-core custody. The entered loop reads its owner-published, loop-group-readable policy snapshot from the registered `policy/snapshot.json`; request mode, floor and rubric strings remain evidence. The separate loop-owned `direct/` tier holds `command-requests.jsonl`, an atomically replaced schema-one snapshot line containing verdicts, review, intent, claims and outcomes, with the judging snapshot digest in every row. Neither tier is the entered home, and the entry neither creates the tiers nor opens owner-private state. Missing policy names `superloop-lane requests publish-snapshot LOOP`; unsafe custody and a different loop UID refuse independently. A changed policy snapshot requires a fresh judgement before a claim, while completion of an already claimed effect retains its original policy evidence.

`status` takes exactly `{"schema":1,"binding":null,"resolve":null}` to discover the authenticated principal, registration digest and cwd without creating a journal. A request uses the exact schema in (`[EXECUTECOMMAND-rule:executecommand:strict-vocabulary]`); its context names that principal and registration. Its `context_digest` is SHA-256 of compact, recursively key-sorted JSON for the full context, and its `request_id` is the same digest of the full request with the binding field omitted. Command bytes and argv remain distinct. `judge` takes exactly `{"schema":1,"request":REQUEST}`. It applies shared hygiene, learned exact matches and effective door modes from the authenticated snapshot; a miss uses the shared bounded door-agent profile under the loop's own sign-in. Caller policy strings cannot select the floor, mode, rubric or model. Missing operations or owner routes retain a provisioning remedy and grant no effect.

The entered home locates the standard loop root but grants no authority. The reader holds the `.var` class root, refuses its own UID as the owner anchor, and walks `loops/LOOP/policy` without symlinks, requiring the observed owner and no group or other write bits at each component. The policy group must equal the reader's effective GID, and the snapshot must be a regular mode-0640 file with that owner and group. The journal tier must instead belong to the reader at mode 0700. No host UID offset is inferred. The bounded agent receives the digest-verified rubric from this snapshot through its private input and uses the loop's own sign-in.

`answer` takes exactly `{"schema":1,"answer":ANSWER}`, where the shared answer contains binding, current review, approve, deny or abandon decision, adjudicator and reason. The authenticated loop UID may answer a loop-scoped referral and claim its approved requests; this entry does not infer a session role from caller text. `claim` takes exactly `{"schema":1,"binding":BINDING}`. It revalidates registration, principal and deadline, persists intent, and returns `fresh_claim:true` once. The caller executes only after that fresh claim; this command never runs the requested effect. A missing acknowledgement is not permission to execute: `status` with the binding reads the durable claim and unknown outcome with `fresh_claim:false`, and another claim refuses. `complete` takes exactly `{"schema":1,"binding":BINDING,"outcome":OUTCOME}`; the outcome is the shared typed outcome record. An identical completion changes no bytes, and a conflicting completion refuses. Refusals before effect record that outcome explicitly; a claim retains an unknown outcome until completion supplies evidence.

`status` with a binding and `resolve:null` returns the retained verdict, revision, review, claim and outcome. After a publication uncertainty, set `resolve` to the operation identity named by the refusal and read custody before retrying; a resolved claim never grants another effect. Invalid input and custody return a named JSON refusal on stderr with status 2; unknown request versions name `execute-command-request-shape`, and unknown stored versions name `execute-command-record-shape`. Existing door, hook and gateway envelopes retain their own strict readers.

Activate this entry only after its authority, context and no-replay fixtures pass. Ensure both registered tiers, publish the first snapshot under owner custody for every loop, replace each door service and lane command under its stop letter, install the public entry atomically, and regenerate per-loop bridge copies through Meson's `loop_registry`. The new journal needs no conversion. The external operations and owner routes remain deferred.

The built-binary acceptance uses `tests/command_door.py` for the public door exercise and `tests/command_gateway.py` for the gateway with a local fixture transport, then `tests/command_custody.py` under two independently provisioned owner and loop accounts. Supply the measured reports with `--door-report` and `--gateway-report`, and the built hook with `--hook`, to compare all four callers per shared rule. The fixture records source binary digests, shared hygiene and remedy decisions, learned matches and modes, authenticated review answers, and one retained outcome per caller-controlled effect; a hook outcome remains unknown until its harness observes execution. These tests provision no accounts and do not replace the deploy host's live door-service acceptance.

## Private dispatch and installation · `sec:superloop:private-dispatch-and-installation`

`account` executes the absolute `SUPERLOOP_ACCOUNT_BIN` with the remaining arguments and preserves streams and status. Meson binds it to the private `account` output; an explicit runtime setting can select another absolute installation. `run-bridge gh -- ARG…` requires `CLAUDE_TOOLBOX` and `GH_CONFIG_DIR`, and forwards arguments through the host portal and that toolbox.

Set Meson's `loop_registry` option to the trusted registry at install. Its install script generates `LOOP-gpg` and `LOOP-ssh` in `libexec/superloop`, copies the root's bytes exactly, and reports unchanged copies on a second invocation. `DESTDIR` contains every generated destination. Bridge argv0 dispatch precedes `--version` and ordinary argument parsing.

The live switch belongs to the orchestrator: move entry callers to `superloop enter`, registry readers to `superloop show`, signing and SSH settings to the generated private bridges, account callers to `superloop account`, and session toggles to the public root. Read back hook registrations and drain old sessions before retiring the old entry, bridges and hook paths. The version is one advance for the entire unreleased lane, not another advance at import.
