# `lane-lifecycle` · `guide:lanelifecycle:lane-lifecycle`

`lane-lifecycle` provides the backend-independent durable process lifecycle shared by the Codex and Claude lane drivers.

This is an internal library, not a separately installed public tool. Until the dependency ledger exists, this README is the declaration authority for the shared driver-directory and report data edges; the integration runbook beside `driver-launch` declares the owner-maintained `workers.toml` root setting and the trusted entry transport.

The two drivers, through lifecycle, write a durable directory beneath the configured runs root. The directory survives the disposable worker home. Its `.step-name`, `.event-start`, `.started-at`, backend lock, `events.jsonl`, `last-message.txt`, `run-report.txt` and `steps/NAME/` history form one lifecycle protocol. The lock's first line is the driver PID and its optional second line is the child PID. `superloop-lane driver status` and `superloop-lane driver follow` read the report and event/step evidence. These are shared-file dependencies, not executable calls. The entry and lane launcher select and check the directory; lifecycle owns allocation, locking, resume and publication semantics.

Lifecycle owns the `RUN-REPORT` grammar, emitted on stdout and atomically published as `run-report.txt`: `lane`, `exit`, `wall`, `budget`, `verdict` and the directory field retain their existing order and meanings, with existing optional evidence fields preserved. A refusal before allocation emits its diagnostic on stderr and a fallback report with `dir=unknown`; it does not invent a durable directory. A published report settles the current step; resume archives that step before preparing another. Report readers remain compatible across the root-setting change. `superloop-lane driver follow` owns the shared `.feed-offset` capture cursor, which lifecycle archives at resume. No new report version or ledger validation is claimed by this declaration.

Lifecycle diagnostics are constructed with the backend binary name so shared failures point at the driver that emitted them.

The configured backend vector is transported by the entry or host runner in `LANE_BACKEND_ARGV`, alongside `LANE_DRIVER_ARGV` and `LANE_SETTINGS_EVIDENCE`. Each production driver validates these values before allocating a directory; the library does not import the entry's registry implementation or reopen its owner-only settings. An executed step saves `backend-settings.json` with its absolute backend program, settings source and exact selector values. The report appends `backend_program`, `settings` and `settings_sha256`, percent-encoding report words and hashing the selected settings evidence. Resume archives the previous evidence beside its report before publishing the next step's values.

Every fresh launch requires an absolute `LANE_RUNS_ROOT`, transported from the trusted workers setting; an unset, empty, relative or dotted value is refused by name before any run directory is allocated or written, including when `-d DIR` names the exact fresh directory. The entry also supplies `LANE_RUN_DIR`, its selected durable run container directly beneath that root. Boxed driver steps live beneath that selected directory; a standalone launch allocates directly beneath the root. An explicit fresh `-d` must be a direct child of the selected directory, or of the root when no selection was supplied. A standalone resume retains its supplied directory; an entry-launched resume must remain a direct child of `LANE_RUN_DIR`. Neither value comes from the executable's location, and the driver does not reopen owner-only settings after the identity transition.

The shared fresh allocator exclusively creates `{UTC-stamp}-{name}` when free, then tries `{UTC-stamp}-{name}-2` through `-32` in order when names are occupied; it never adopts an existing directory, and another create error or exhaustion is a runtime failure. A directory the caller names is created exclusively under exactly that name and never suffixed, because a caller that recorded the name before the driver started must find the step there: when anything already holds the name the dispatch is refused with status 2 before anything is written, with the refusal on standard error, and a missing parent is a runtime failure.

## Resume boundary · `sec:lanelifecycle:resume-boundary`

A resume requires the prior step's `run-report.txt`, a step name no earlier step used, and an event stream whose first thread identity matches the requested session. A lock file whose holder is still live is a running step and refuses the resume. A lock file whose holder is dead is recovered before those checks, because the step behind it can no longer publish anything itself.

Dead-holder recovery reads the run directory before it writes, and what it finds there decides which of three things happened. A `run-report.txt` beside the dead lock is proof the step published before its driver died: that report and its `last-message.txt` are kept untouched, only the stale lock is cleared, and no recovery ever manufactures a record over a settled one.

Without a report, the step never published, and recovery reads the transcript. A driver killed after its child's terminal result event but before its own report leaves a step that finished in fact and not on disk: the lock and `.step-name` stand, `run-report.txt` and `last-message.txt` are missing, and the step's own events end in a complete top-level result event. That step is reconstructed instead of re-run at the cost of the whole step, because the transcript already carries the result the re-run would buy. The result event supplies the exit and the verdict, the same region supplies `last-message.txt`, the lock clears, and the `RUN-REPORT` line keeps its published shape so every reader of it keeps working.

A step's own events are the region of `events.jsonl` at or after the offset `.event-start` records; everything before it belongs to earlier steps of the same run. Both the result and the message are read from that region alone, so a driver killed before its child wrote a single line cannot inherit the previous step's finish or the previous step's answer. A missing, unreadable, or out-of-range `.event-start` bounds nothing, and an unbounded transcript is never reconstructed.

The active `.started-at` records the driver's UTC wall second after its input is durable and becomes `steps/NAME/started-at.txt` at resume when present; a reader uses it with the settled report's wall and timed server, ssh, and git calls to divide the step's wall.

The wall figure comes from the result event's `duration_ms`; a transcript that measures nothing reconstructs at `wall=0s`. A derived wall is not a measured one, so a `.reconstructed` record beside the report names the derivation, the finish, the dead holder, and the time, and the next resume archives it as `steps/NAME/reconstructed.txt` with the rest of that step's evidence. The run directory records no budget for a finished step, so a reconstruction never judges over budget and reports `budget=0s`.

A transcript whose last complete line is not a terminal result event belongs to a step that never finished, and a backend whose event shape carried no such event would have nothing to read for any step. Both keep the CRASHED report, which also clears any `.reconstructed` record an earlier step left, so no sidecar ever describes a report it does not belong to. Both shipped shapes do carry the evidence: a finished Claude turn ends on its `result` line and a finished Codex turn on `turn.completed`, or on `turn.failed` for a turn the provider ended, so an interrupted step of either driver is reconstructed from the finish it reached rather than paid for twice. A running step keeps one sidecar of its own: every monitor poll writes `.monitor-PID-SEQUENCE` beside the lock as the single line `quiet=<s>s wall=<s>s event_size=<n> boot=<s>s awake=<s>s` with optional trailing `awaiting=<lane>:<seq>` when a gateway run is credited. It also carries the mandatory budget, current last-growth offset and growth state; after expiry, an immutable tuple records the first over-budget wall, event size, last-growth offset, quiet interval and state while later polls update the current state. Distinct monitors cannot overwrite each other's capture, and a failed advisory write leaves the step running. The `--gateway-lane <lane>` option names this step's registered gateway lane; when its registration names the step's workdir, either an approved run inside its proposal timeout or an audited roster request inside its command's registered wall budget credits progress under the stall window until a result for its sequence reaches the audit; for a roster request, an audited refusal of its sequence ends the credit too.

The lock names the driver on its first line and, from the moment the child exists, that child on its second. A driver found dead whose child is still alive is a live lock and refuses the resume naming that child, because the step is still running: its transcript is still growing, and a CRASHED report written over it would settle a step that has not ended. A one-line lock is a driver that died before its child existed and is read exactly as it always was. The second line is written best-effort, for the same reason the monitor sidecar is: the child already exists when it is written, and a lock rewrite is never worth killing running work over.

## Stopping a live step · `sec:lanelifecycle:stopping-a-live-step`

Silence is what the monitor measures, not what the end of a step means. The mandatory budget is a reporting threshold: the first over-budget poll latches the expiry in the sidecar and the worker continues. The 120-second no-growth window yields `stalled`; more than four budgets yields `runaway`; after expiry, all other polls are `growing`. Before expiry the sidecar carries budget and last-growth fields without a growth state. These are observations for the loop, not signals. The `superloop-lane driver follow` capture tool publishes the expiry and subsequent state changes, and the loop chooses to wait, write to the worker, or stop it explicitly. A naturally completed step keeps its result: success past budget is `OVER-BUDGET`, and a failed result is `FAILED`. Here the monitor is the driver program; the lane's Sonnet watcher consumes the capture, owns the wait and deadline, and relays the evidence for the session's decision.

A request to stop the driver stops the step. The driver blocks `SIGTERM` and `SIGINT` and records their arrival, then stops and reaps the child at its next poll. If the last complete line of the child's own region is its terminal result, the driver classifies by that result and settles its last message; success past budget is `OVER-BUDGET` at status 0. An unfinished child is `FAILED` at status 1. The watch is advisory — a host that refuses it leaves the default disposition every earlier driver had — and it never reaches the child, which `std::process::Command` starts with an empty mask.

New steps do not write `kill-evidence.txt`; a historical one left by an earlier driver moves into the prior step's history at the next resume boundary, and no other reader remains. Historical `STALLED-KILLED` and `RUNAWAY-KILLED` reports remain accepted by report and watcher readers.

## Refused dispatches · `sec:lanelifecycle:refused-dispatches`

A provider that refuses a dispatch ends the child in seconds with a nonzero status, which is exactly what a step that ran and failed looks like. When the backend finds a refusal in the step's own event region, that nonzero natural exit publishes `RATE-LIMITED` instead of `FAILED`, keeps status 1 and the report line's published field order, states the window and its reset on standard error, and leaves a `rate-limit.txt` sidecar beside the report. Reconstruction and explicit signal disposition retain their own verdicts. A failed step whose box helper stopped its attempt at the attempt wall is neither rate-limited nor retried for capacity: the helper client leaves the `.attempt-end` record at the path the driver exports as `LANE_ATTEMPT_END`, and the report keeps `FAILED` with `cause=attempt-wall`, the elapsed and the bound seconds after `dir`.

A Codex result saying that its selected model is at capacity resumes the same thread with the saved step message after delays of 60, 120 and 240 seconds, for at most four attempts. A wait starts only when the step's remaining awake budget exceeds that delay; termination or budget exhaustion prevents another attempt, and retries retain the original budget origin. Missing thread identity prevents a fresh-thread retry. Every attempt and planned and measured wait is recorded in `capacity-attempts.txt` outside the worker home, and the run report adds `capacity_attempts=N` and `capacity_waits=SECONDSs` beside any `suspend_resumes` field. A later success settles the step once; exhausted attempts keep the capacity refusal and fail. Recognition reads complete lines in the last 1 MiB of the current attempt, so large transcripts retain terminal capacity evidence without adopting a previous attempt's refusal. Claude has no measured capacity event fixture and does not classify capacity refusals.

Every step records the last pool state its own region carries as `lane-pool.json` in the lane home it dispatched from, and every dispatch reads that record first. A record observed before its own window reset, whose window has still not reset, and whose status is a refusal or whose utilization has reached the configured threshold, refuses the next dispatch with usage status 2 before any run directory exists — no allocation and nothing to clean up, and because a refusal is still a terminal path of an agent-text command it publishes the fallback `FAILED` report naming the unknown directory, with the classed reason on standard error. The read is advisory by construction: it is one step old, several lane homes can share one window, and a missing or already-reset record simply dispatches. The verdict is the guarantee; the read only avoids paying for a dispatch that the last observation says will be refused.
