# Heartbeat decisions · `guide:heartbeatguard:heartbeat-guard`

The adapter and public session command use the same neutral heartbeat graph. It keeps its turn counters and warning markers in the one store shape stated below, and preserves the deployed flag name when the working directory is already the project root. The orchestrator wakeup's policy purpose is only to check each live lane's Sonnet watcher for liveness, deadline and complete duty coverage; it is not a session-side lane, gate or inbox poll. The machine behavior below is unchanged by that ownership rule.

## Commands · `sec:heartbeatguard:commands`

```text
superloop-claude-hook stop|pre-tool-use|session-start|user-prompt-submit
superloop heartbeat on|off|status
superloop hook|on|off|status
```

`superloop` is the same guard under the tool's name, sharing the state directory and every message, deployed beside `heartbeat` until the Stop-hook settings name it.

With no arguments the binary preserves the shell toggle's default `status` operation. Toggle state is keyed by the project root resolved from `PWD` or the hook payload's working directory. For an absolute working directory, `HOME` bounds the walk whenever it is a lexical prefix of that directory, including when the two are equal; candidates are the working directory itself and its ancestors strictly below that exclusive boundary, or the same unbounded walk through the filesystem root when `HOME` is not a prefix. The first existing `.git` entry ends the walk: a directory containing a `HEAD` file or a file beginning with `gitdir:` selects its directory, while an implausible entry or no entry leaves the supplied working directory as the key. A relative or empty working directory is returned unchanged without a filesystem probe. A nested repository or worktree therefore deliberately selects itself, matching Git's nearest-root behavior, and toggle output makes that selection visible. The resolved path is folded from slashes to hyphens and written as `heartbeat{folded-project}` below the state root. Calls made at or below the same plausible marker with no nearer `.git` entry make the toggle and hooks agree on one key; a working directory with no such marker keys on itself, as before. This replaces the failure where a subdirectory toggle and root hook used two sibling files and looked like the guard had flipped mid-flight. Its output bytes otherwise retain the shell command's `ON`, `OFF`, and blocked-on-user wording. There is no global heartbeat toggle.

When pausing a session, run the toggle from the session's launch directory, never inside a command that has changed into a scratchpad or clone: `off` removes the flag keyed by the project root resolved from its `PWD`, while the hooks read the flag keyed by the project root resolved from the payload's working directory. Run `off` first and then end an armed timer with `ScheduleWakeup` and `stop: true`: a wakeup already armed outlives `off`, and the `PreToolUse` gate does not read `stop`, so while the toggle is ON it refuses that call unless the session holds a fresh prompt marker, whereas after `off` it allows the call with a non-blocking warning. In a measured pause, `off` run from a scratchpad printed the scratchpad's key and left the hooks' flag in place, while a wakeup armed before the pause fired seven seconds after the next compaction resume.

Only an explicit `on` creates the project flag and only an explicit `off` removes it; no hook event writes it. `SessionStart` and `UserPromptSubmit` list letters without evaluating the heartbeat machine or touching its flag, counter, warning or guard-prompt marker. Other events except Stop and `PreToolUse` pass silently without state access. Because the toggle keys on its `PWD` and the hooks key on the payload's working directory, a stored OFF still reads OFF after a compaction only while that directory resolves to the project root the `off` reported.

`hook` dispatches on the input object's hook event name. Stop events retain the graph-driven behavior: silent allows write nothing and exit zero, lapse allows write one compact hook response object to standard output and exit zero, and intentional prompt and correction blocks write the agent-directed reason to standard error and exit two. A prompt that asks for `ScheduleWakeup` writes `guard-prompt-{session}` in the state root with an ISO-8601 UTC timestamp, named from the payload's usable session identity, and writes no marker when the payload carries none.

At each Stop, the letters callback matches the heartbeat cwd project key against registry launch project keys and runs `superloop enter LOOP -- letters list` from the hook working directory. It reads the current five-field metadata shape, including the quoted subject, and renders a stateless newest-first tail over `new/` and `cur/`. Each displayed row contains the letter name, sender, posting instant and `unread=true` or `unread=false`; the heading carries the full unread count. Feedback contains at most eight entries and 4096 UTF-8 bytes including heading and omission text, within the composed twenty-line ceiling. Subjects and bodies are not copied into hook feedback. The session compares names with those it knows. The inbox watcher hand-back is the primary notification; this prompt-and-stop tail is the second route, and the inbox directory is the record. Only `letters read` takes a letter. No match is silent; ambiguity and entry failures are named. The deployed entry precedes PATH and its five-second deadline kills its process group before the hook timeout. Unread letters retain the existing first-stop block, continuation notification and shared three-block counter behavior; read history alone only notifies. Heartbeat lapse and failure behavior remain unchanged.

A `PreToolUse` event for `ScheduleWakeup` with a usable session identity first resolves the payload-selected project's toggle. When it is OFF, the timer is allowed with a non-blocking warning on standard error and exit one, without reading or consuming any marker. When it is ON, the only marker consulted is `guard-prompt-{session}` named from that call's own payload, so sessions sharing a machine cannot consume each other's prompt. A fresh marker is consumed and allowed silently; a missing or more-than-fifteen-minute-old marker is a healthy policy refusal on standard error with exit two, and a stale marker is removed. Only the file actually consulted is removed. Other tools pass through without state access. A payload with no usable session identity fails open at zero, output-free, recording the case in the internal log, with no marker access. Malformed payloads, unreadable toggle or marker state, and garbled marker timestamps fail open at zero. `superloop heartbeat off` clears only the project flag.

Letters are inspected on `SessionStart`, `UserPromptSubmit` and Stop through the same registry lookup and entry callback. The two context events return exit zero with `hookSpecificOutput.hookEventName` and `additionalContext`, never a block decision. Empty listings, unmatched projects and all failures are silent on these events; Stop retains its named failure notifications. The owner registers both context events beside Stop with an eight-second harness timeout. The callback retains its five-second deadline, leaving three seconds for hook overhead, process-group cleanup and rendering; this is headroom rather than a scheduling guarantee under arbitrary load. No registration is performed by the binary.

Letters context has no delivery receipts or turn-local seen set. Repeated `SessionStart`, `UserPromptSubmit` and `Stop` events re-read the same inbox history, even while heartbeat is off. Old `guard-letters-HEX_SESSION.json` files are ignored and no replacement receipt is written. The independent heartbeat counter, warning and prompt marker retain their existing meanings.

Every `SessionStart` source, including startup, resume and compaction, supplies the current tail. Empty listings add nothing. Context-event listing failures log `LettersListingFailed` and fail open silently; a later event retries without receipt state. The orchestrator hook's separate rulebook-injection deduplication is unchanged.

## Paths and controlled time · `sec:heartbeatguard:paths-and-controlled-time`

The deployed path override is `HOME`: the guard resolves its `~/.local/state/superloop-tools/hook` state directory from it. The callback's transcript remains the payload-selected path, and its project flag is keyed by the resolver rule above. Tests replace `HOME` or pass an isolated state root directly and never access the operator's state.

After upgrading, any flag previously keyed to a subdirectory is no longer read. Its absence at the resolved project-root key selects `FlagAbsent` and fails open, so `heartbeat on` must be run again at the project root.

Production execution samples UTC from the system clock and performs the specified one-second reload only after an initially unarmed active-stop evaluation. Integration fixtures call the same graph adapter with two fixed UTC samples and no real sleep, so expiry and retry assertions have no wall-clock dependence.

## Direct state graph · `sec:heartbeatguard:direct-state-graph`

The heartbeat machine is a `petgraph::graph::DiGraph` with thirty-nine node weights. The letters inspection states precede the heartbeat decision states; six composition decisions then lead to sixteen explicit terminal verdicts, covering the six heartbeat-only results, four first-stop letters blocks and six notification combinations. Guards and ordered effects are graph edges, including the shared counter write on each letters-block edge. Evaluation advances through `NodeIndex`, and process status and output fields are rendered from the reached terminal; no post-graph adapter overrides the verdict. Lapse composition has no letters-block edge.

The graph preserves all four exception states and makes fresh-warning versus already-warned phases explicit edges. Counter or warning persistence failure returns through the semantic state's `InternalError` edge to `FAIL_OPEN`; it cannot publish an unrecorded repeatable block. Graph tests prove unique inventory, reachability, terminal totality, resolution coverage, warning-edge visibility and bounded composition; controlled fixtures reach every composed terminal.

The manifest uses inherited `petgraph`, `serde_json`, `nix` (deadline process-group and pipe handling) and `loop-home` (the registry reader). It deliberately does not use `superloop-cli-common`: the harness owns hook streams and statuses, so the shared machine-JSON and agent-text adapters do not apply.

The guard store has one current shape: `guard-count-{session}` contains the latest real-user marker and block count, `guard-warn-{session}` contains the marker, and the project flag keeps its deployed name. Letters delivery receipt files are retired and have no reader or writer. A missing, malformed, negative or mismatched-marker count reads as zero; I/O-unreadable count or warning state fails open.

## Specification-over-Python divergences · `sec:heartbeatguard:specification-over-python-divergences`

The ratified hook and output specifications govern these six reference differences:

- (`[TOOLS-spec:output:hook-json-streams]`): Python prints a block decision object to stdout and exits zero. The harness contract requires the agent reason on stderr with exit two. Fixture: `spec-block-stderr.json`.
- (`[ORCHESTRATION-scenario:hooks:heartbeat-fail-open]`): truthy nonstring payload fields, structurally invalid transcript fields, and undecodable transcript bytes can escape Python as exceptions. Rust returns output-free fail-open with no traceback. Fixture: `spec-invalid-field-fail-open.json`.
- (`[ORCHESTRATION-inv:hooks:fail-open-safety]`): Python treats an I/O-unreadable counter or warning as absent and may fabricate a prompt or correction. Rust distinguishes malformed readable bytes, which recover as specified, from unreadable state, which fails open. Fixture: `spec-unreadable-state-fail-open.json`.
- (`[ORCHESTRATION-rule:hooks:turn-local-block-cap]`): Python ignores counter and warning write failures and can repeat a block without a persisted bound. Rust takes the explicit anti-wedge fail-open edge before publication. Fixture: `spec-state-write-fail-open.json`.
- (`[ORCHESTRATION-def:hooks:pending-wakeup]`): Python's `float` conversion accepts a numeric JSON string as a delay. The specification requires a numeric delay, so Rust skips string-valued delay evidence. Fixture: `spec-nonnumeric-delay.json`.
- (`[ORCHESTRATION-sig:hooks:stop-input]`): Python excludes string-form guard feedback from real user turns but treats list-form feedback as a new turn. The specification excludes guard feedback in either carrier, so Rust preserves the marker across both forms. Fixture: `spec-list-feedback-turn-marker.json`.

The deployed Python audit itself has a separate stale expectation, not a source-level machine divergence: P4, P8, P13, P21, P23, and P24 still look for the retired user-directed warning. Current Python source and the specification instead use a once-per-turn agent-directed correction block. `python-reference-suite.stdout` captures all 26 scenarios and those six expected audit failures with only elapsed times normalized; the Rust port retains each scenario with the governed expectation.

## Test boundaries · `sec:heartbeatguard:test-boundaries`

The integration suite carries all 26 deployed scenarios, the complete scheduler structural matrix, fixed-clock clamp/slack/horizon boundaries, every counter and warning phase, all six terminal paths, counter and warning persistence read-back, toggle parity, per-session prompt-marker isolation and refusal of an unkeyed marker, and ADR-001 subprocess streams and statuses. Fault fixtures cover malformed input, missing and undecodable transcripts, invalid field types, unreadable state, failed count and warning writes, and a forced panic with redacted logging. No assertion derives a scheduler verdict from result prose.
