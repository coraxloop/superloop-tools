# Permission triage core · `guide:permissiontriage:permission-triage-core`

`permission-triage` implements protected rubric loading, the nested model runner, the `PreToolUse` adapter, the private verdict journal, and the loop-scoped request helper of the permission gate described by (`[ORCHESTRATION-proposal:permissiontriage:rubric-driven-model-gate]`). The shared execute-command crate owns hygiene, rubric framing and digests, classification validation, verdict selection and command answer bindings; request-core owns the common request transitions. The hook requires an explicit audit or enforce mode, decodes one request, resolves its caller, records every verdict, and crosses a distinct response boundary that is silent in audit and serializes the exact harness response in enforce.

The shared judgement preserves the six-class model profile and caller journal shape. Invalid output and scope below the observed floor are referrals in memory and denies at the harness boundary. An estate referral retains the unprovisioned operations route as verdict evidence until authenticated operations and owner routes are configured; hook responses retain their existing review and infrastructure reasons, granting no authority or effect. Loop answers remain bound to the stored request and rubric digests, current review and authenticated caller. Replacing these binaries requires draining synchronous classifier calls and a hook session boundary; no existing journal converts.

Explicit audit/enforce mode, complete audit silence, audit/bypass topology evidence, semantic scope, and registry-selected loop/estate journals are implemented. Owner-run audit installation and enforce-readiness validation now render a reviewable audit instance and evidence record; the later owner flip and reverse-safe rollback are documented behavior. Estate approval marks remain blocked by the existing journal authority boundary; the owner must supply an estate adjudication route without assuming that loop marks grant estate authority. The existing journal reader has no timestamp parser to share, so evidence validates the writer's canonical UTC format independently; that scoped deviation is recorded in the proposal. Fake-harness tests and the disposable procedure rehearsal do not replace the real authenticated host rehearsal or authorize live deployment. The revised acceptance contract and implementation bites are in `docs/proposals/permission-triage.md`.

## Request decoding · `sec:permissiontriage:request-decoding`

The private `requests-helper` binary implements `status`, `list`, `triage`, `review` and `adjudicate`. Its registered permission collection forms are `COMMAND --loop NAME`, with `--pending` on status and list, and an ID after `review --loop NAME`. Triage reads the schema-one `items` document, and adjudicate reads the schema-one `id`, `review_id`, `decision` document. Changing forms also require `PERMISSION_TRIAGE_REQUEST_CONTEXT`, an absolute path to the caller's Claude request payload; the existing registry, uid, session, checkout and subagent checks resolve that context. A review identifier supplies no authority.

Permission records retain the complete validated escalation as their body. Their common ID is the SHA-256 of the original event ID's bytes; the original caller role and event ID supply the worker and run identifiers where the old journal has no finer identity. Answers name one of the existing disposition outcomes: `adjudicated-rejected`, `adjudicated-rule-added` with `rule`, or `corrected-and-rerun` and `adjudicated-approved` with `request_digest`. The decision reason is mandatory. Approval retains the identical-request and orchestrator-only checks, and estate adjudication remains refused.

The journal's existing lock serializes old and new writers. A common transition and its legacy disposition rows publish by one atomic replacement of the private journal, followed by directory sync. One schema `superloop-requests-v1` row retains the common collection, complete review history and revision; publication replaces earlier collection snapshots while retaining all legacy event rows. The journal renderer ignores validated collection rows and continues reading disposition rows. Request collection reads reconcile existing dispositions against the same source and refuse a disagreement, duplicate, malformed row or torn tail. Status and list create neither files nor locks. Invalid batches leave journal bytes unchanged. A post-rename sync failure reports `requests-commit-uncertain`; the caller must read the durable record before retrying.

The custody owner uses `--owner-read --loop NAME` to read the common collection, and `--owner-preview COMMAND --loop NAME` followed by `--owner-commit COMMAND --loop NAME` to serialize a batch containing permission, door and gateway kinds through that one journal. It holds the door store lock throughout. The exact input envelope has `schema: 1`, validated `records`, nullable `document` and `id`, `pending`, `now_ns` (integer nanoseconds since `1970-01-01T00:00:00Z`), nullable `expected` and nullable `publication`. Preview returns `schema: 1`, `before`, candidate `collection` and `result`, and creates no file or lock. The owner validates door projections and mode corrections, then sends `before` as `expected`; a concurrent permission change refuses the entire commit. Optional `publication` may change only door source bodies, preserving their source IDs and every evaluated common field; this lets the custody owner publish its validated labels in the same atomic transaction. Permission records independently retain their caller and scope checks in both phases. The same private protocol admits door-before-effect and gateway `claim`, `complete` and `withdraw` service documents, with exact fields `schema`, `id`, plus `claim` for claim/complete and `result` for complete. A repeated identical claim admits no new execution. This release does not run a service effect in the helper.

`requests-helper --registry-validate parse|deployment` validates a descriptor-pinned registry snapshot supplied on stdin as a map of entry names to byte arrays. It opens no paths and changes no state. Both modes require a complete parse; deployment also applies the helper's deployment structure rules at its effective uid. The schema-one reply contains entry names, state roots and homes. `superloop-lane requests provision-registry` retains the directory pins and lock, checks existing state roots, validates the candidate through this exact private command and only then writes its entries and report. This keeps registry policy with the helper without a public-lane dependency on its package.

`requests-helper --snapshot COMMAND` is a private pure protocol for the door's custody owner. Its exact envelope contains `schema: 1`, `collection`, nullable `document` and `id`, `pending`, and `now_ns` (integer nanoseconds since `1970-01-01T00:00:00Z`); success returns `schema: 1`, the candidate `collection` and command `result`. The owner validates source records, holds its lock, validates the returned candidate and publishes it before any effect. This form opens no files and grants no permission. Door bodies bind `source_id` to `record.id`; answers contain only `outcome: allow|refuse`. Before-effect door judgements remain service-pending until their custody owner records the claimed execution or refusal; after-effect labels need no service. Gateway bodies and answers use the neutral request-core schema. Owner `file` admits only undecided gateway rows, compares immutable bodies on retry and refuses another loop. Gateway marks, reviews and decisions require the registered loop orchestrator; the gateway service alone executes approved argv. Each collection command is tested through the built helper, including atomic batch refusal and stale reviews.

The decoder requires string values for `session_id`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`, and `tool_use_id`, plus an object for `tool_input`. The event name must be `PreToolUse`. Optional `transcript_path` and `agent_id` values are retained only for role resolution; their absence or wrong type does not make the request unclassifiable. A Bash input additionally requires a string `command`; its optional `description` is a string, `timeout` is a nonnegative integer number no greater than 600000 milliseconds, and `run_in_background` is a boolean. Unknown fields are ignored. Missing required fields, malformed JSON, and wrong types for required or Bash-specific fields produce an unclassifiable value carrying a stable reason.

## Deterministic classification · `sec:permissiontriage:deterministic-classification`

The fast lane delegates its ordered hygiene predicates and read-only table to execute-command through a pure adapter over the decoded request and computed scope floor. It can name a harness-owned read-only allow, return one mechanical agent error with its smallest correction, or defer to the future model adapter. All read-only table entries are disabled until the acceptance matrix confirms their exact grammar, so matching one currently defers to the model.

The conservative shell tokenizer accounts for quoting, escapes, command substitutions, pipelines, conjunctions, separators, redirects, heredoc shape, and subshell balance. Unsupported but potentially valid shell remains model-routed. Plainly malformed syntax is an agent error.

The deterministic hygiene table implements general-rubric rules 1 through 8. Rule 9, claimed-read side effects, and rule 10, field type and range validity, have no fast-lane counterpart; the classifier model judges both from the complete rubric and reduced request.

Gate help follows the same subcommand-query rule across package managers: `npm run --help` is informational and defers to the model without a timing correction, while `npm run SCRIPT` remains an execution gate that requires timing at its execution boundary.

The background-observation check deliberately follows the embedded general rubric's stricter contract in place of the proposal's earlier alternative: a detached request must carry both a completion marker and a supervised status path, together with declared background execution, a finite startup timeout, stable job identity, and a real append-only log. Supplying only the marker or only the status path remains an `agent-error`; the two observers are complementary rather than interchangeable.

## Process boundary · `sec:permissiontriage:process-boundary`

The request decoder and deterministic fast lane remain process-free. Rubric filesystem access and the nested classifier process are isolated in their own modules. The binary owns environment inspection, process launch, input/output, and wall measurements; the hook adapter remains a pure mapping over supplied values.

## Rubric loader · `sec:permissiontriage:rubric-loader`

The reviewed bytes in `rubrics/general.md` and their SHA-256 digest are embedded at compile time. `PERMISSION_TRIAGE_OWNER_RUBRIC` optionally names an absolute private owner-rubric path; an unset or empty variable, or a missing file, selects no owner rubric. A resolved main session or in-session subagent selects its loop's registered `LOOP_ORCHESTRATOR_RUBRIC`, which deployment validation requires to lie inside the directory holding the configured owner rubric, or by convention `LOOP_CWD/local/permissions/domain.md` when none is registered; a worker resolved by its uid block selects `LOOP_HOME/shared/permissions/domain.md`; an unknown role selects no domain path and performs no domain-rubric read. Owner and domain bytes pass through the identical Linux-only loader: it opens a regular file read-only without following a symbolic link in the final component, rejects every other read error, invalid UTF-8, and content beyond 64 KiB, and returns the SHA-256 digest of the exact bytes read. It never writes a rubric or exposes either configured path to the model.

The prompt contains the replacement system instruction followed by complete general rubric, complete optional owner rubric, caller role, complete optional domain rubric, tool name, working directory, and canonical command or reduced action string in explicit length-delimited untrusted-data sections. `CALLER ROLE` and `DOMAIN RUBRIC` appear in that fixed order immediately after `OWNER RUBRIC`. Every prompt derives one nonce from the process identity, a monotonic clock reading, a sequence number, and the exact prompt fields; every real begin and end marker carries that nonce, and the declared byte count covers the exact unsynthesized value bytes between them. Marker-like input carrying another nonce remains data. The prompt adds no session identifier, tool-use identifier, arbitrary tool input, prior output, transcript path, agent identifier, registry path, file body, or environment value; only the Agent and Task reducers' caller-authored description enters through their canonical action.

## Role resolution · `sec:permissiontriage:role-resolution`

`PERMISSION_TRIAGE_LOOP_REGISTRY` optionally names the estate's absolute loop-registry directory. An unset or empty value resolves every request as `unknown` without a filesystem read. A configured registry is accepted in one of two shapes — private, a mode-0700 directory of mode-0600 entries owned by the reading process's effective uid; or estate, a mode-0755 directory of mode-0644 entries owned by the uid the instance declares, with no component of the path carrying group or other write permission and no component owned by a third principal, the deployment uid beneath whose home the tree sits not being one, and the declared uid cross-checked against the estate entry's `LOOP_UID` — and an absent or invalid configured registry resolves as `unknown`, while repeated directory, entry, or incomplete-row read failures, including an unannotated worker block or duplicate `LOOP_UID`, refuse as `loop registry generation changed`. The bounded parser accepts one `LOOP_NAME`, one `LOOP_SID`, one absolute dot-component-free `LOOP_CWD`, one `LOOP_UID`, one absolute dot-component-free `LOOP_HOME`, one `LOOP_WORKER_UIDS` block within 1000 through 65535 with a positive count and both a canonical `LOOP_ALLOCATIONS_SHA256` digest and `LOOP_ALLOCATIONS_COPIED_AT` time, and one `LOOP_STATE_ROOT`; a request whose effective uid lies in a registered block resolves to that loop as `orchestrator-subagent` without consulting its working directory, and every other request resolves from the working directory and session identifier as before. The `LOOP_NAME` must itself be one path-safe component, because a deployment derives per-loop paths from the registered name and a name of `.` or `..` would traverse out of the tree that names it; the supplied-byte parser ignores an invalid entry as a whole and sorts valid entries, while the filesystem loader retries an incomplete listed row and refuses after three attempts. Deployment validation requires the state-root assignment for every registered entry, requires worker blocks to be pairwise disjoint and disjoint from every registered `LOOP_UID` and from the deployment uid, and, when any block is declared, requires every block and every registered `LOOP_UID` to lie within the deployment account's subordinate uid and gid counts read from `/etc/subuid` and `/etc/subgid`.

`LOOP_WORKER_UIDS` in this deployed text registry is a readable snapshot of the tools-owned allocation ledger's block for the same loop. Redeploy the hook binary before running the revised `permission-triage-assemble`, because the old hook rejects its digest and copy-time keys. The session owner runs `superloop-lane prepare LOOP` to reserve the block, then runs the assembler under its exclusive nonblocking registry-parent lock, followed by the configuration-root lock shared when distinct and the ledger lock shared when present from the final digest check through output publication; when both directories are one inode, the existing exclusive guard covers the configuration root; `prepare` takes the configuration-root lock exclusive, then the ledger lock exclusive. Assembly reads the private ledger, refreshes a block when that ledger is newer than the row's copy time, refuses a disagreeing row when the ledger did not change, stages the complete registry and dedicated review output generations, rechecks the ledger digest, exchanges the live registry when a ledger exists, and publishes the output directory with an `assembly-marker.json` binding the ledger digest, copy time, and registry inventory digest. Only after the assembly command exits zero, compare the output marker's ledger digest and copy time with every deployed row's `LOOP_ALLOCATIONS_SHA256` and `LOOP_ALLOCATIONS_COPIED_AT`, and its inventory digest with the deployment record; then read back both owner and worker routing before any worker uses the result. A failed output publication can leave the exchanged registry with the previous review directory; a matching marker never overrides the failed exit status, and its files must not be installed. A row without snapshot fields grants no worker; after `prepare` adds a ledger block for that loop, the owner hook refuses the unannotated row as stale until assembly. The hook running as the session owner compares the deployed digest and block with the ledger and refuses a stale snapshot by name. The hook running as a worker cannot read the owner's private ledger and uses the annotated deployed row, so a changed allocation reaches workers when the registry exchange occurs; the owner checks the marker and routing before using the new output generation. The person-written `registry.toml` contains no worker block.

The assembler takes the registry-parent lock, then the configuration-root lock shared when distinct, then the ledger lock shared when present; when the first two name one inode, the exclusive registry-parent guard covers both.

`prepare` takes the configuration-root lock exclusive, then the ledger lock exclusive.

All these lock acquisitions are nonblocking: a contender is refused rather than waiting, including when the registry parent is the configuration root, so no wait cycle can form.

The three roles are `orchestrator`, `orchestrator-subagent`, and `unknown`. Role resolution applies these rules:

1. A relative request `cwd`, a `cwd` containing parent traversal, or a `cwd` beneath no registered launch directory resolves as `unknown`.
2. The candidate loop is the registry entry whose `LOOP_CWD` launch directory is equal to or an ancestor of the normalized request `cwd`; deployment validation refuses equal or nested launch directories, so a deployable registry has at most one matching entry.
3. If the request `session_id` matches a different entry's `LOOP_SID` than the checkout-selected candidate, the role resolves as `unknown`.
4. If the candidate's `LOOP_SID` matches the request `session_id`, the role resolves; if the candidate has no `LOOP_SID`, the role resolves by checkout alone; if the candidate has a different `LOOP_SID`, the role resolves as `unknown`, and `stale_session` is recorded as `false` on every resolved role because no resolved role carries an unmatched identifier.
5. After the candidate passes those checks, a truthy `agent_id` or a `transcript_path` containing `/subagents/` selects `orchestrator-subagent`, and otherwise the candidate selects `orchestrator`.

An in-session subagent presents its main session's `session_id` and transcript path with a non-null `agent_id` (measured 2026-09-23), so the identifier requirement narrows the launch-directory grant without regressing subagents, and on that harness only the `agent_id` signal of rule 5 fires.

No environment value participates as evidence in a permission decision; role evidence comes from hook input, parsed registry bytes, and the reading process's own effective uid, which the hook reads from the owner of `/proc/self` and which no request can assert. The registry directory is an authorization source rather than domain state: it decides which role a request resolves to, so a deployment keeps it outside every loop's domain exactly as it keeps the rubrics outside, and a request that writes a registry entry stays `suspicious`.

The registry has a required deployment field `LOOP_STATE_ROOT`, an absolute dot-component-free path. It changes journal/state routing, not the five implemented identity rules above: `LOOP_SID` is required by deployment validation and, when registered, must match for a launch-directory role to resolve; equal or nested launch directories fail deployment validation, another entry's SID rejects it, and a rotated unmatched SID resolves `unknown`. Deployment structure validation requires `LOOP_SID` on every entry, because an entry without one resolves by checkout alone — where `LOOP_CWD` is a launch directory rather than a loop's material, any owner-uid session started there then takes that loop's orchestrator role, and `stale_session` reads `false` precisely because no registered session can contradict it — while routing keeps the identifier optional, so an entry without an identifier still resolves by checkout while a rotated identifier resolves `unknown`. Every live loop must have a valid registration, distinct safe state root, and domain rubric before audit installation or an enforce-readiness check can pass. Identity and domain selection, peer boundaries, caller root, and estate routing use one registry snapshot. A missing or invalid selected root is an infrastructure failure, never permission to select another loop's sink.

## Nested model runner · `sec:permissiontriage:nested-model-runner`

The default settings argument vector is `--print --setting-sources "" --settings '{"disableAllHooks":true}' --strict-mcp-config --disable-slash-commands --model MODEL --output-format json --json-schema SCHEMA --tools "" --system-prompt SYSTEM --no-session-persistence`, while `PERMISSION_TRIAGE_ISOLATION=bare` emits the unchanged `--print --bare --model MODEL --output-format json --json-schema SCHEMA --tools "" --system-prompt SYSTEM --no-session-persistence`. `MODEL` defaults to `claude-opus-5`, `SCHEMA` is the embedded `schema/classification.json`, and `SYSTEM` is the replacement classifier instruction. Which model is the routine default is a measurement rather than a repository fact, so the default stays `claude-opus-5` until the acceptance matrix and corpus rerun measure a faster candidate that moves no row toward `allow`; the instance file selects a different model in the meantime. `PERMISSION_TRIAGE_CLI` selects the executable and defaults to `claude`. The prompt and rubrics travel only over standard input; the inherited environment is passed unchanged except that the runner reads field 22 from `/proc/self/stat` and adds `PERMISSION_TRIAGE_NESTED=PID:STARTTIME` only to the classifier child.

`PERMISSION_TRIAGE_MODEL_DEADLINE_MS` defaults to 55000 and is capped at 55000. The clock starts before spawn, standard input and output run on joined helper threads, and the child enters its own process group. A deadline or cap violation signals that group, escalates to a hard group kill after a bounded grace period, reaps the direct child, and joins both helpers. Standard output is retained only through 64 KiB, standard error is discarded, and launch, input, wait, kill, reap, capture, nonzero-exit, timeout, cap, envelope, and schema failures remain distinguishable. Harness 2.1.258 was measured returning both a `result` string and a `structured_output` object; `result` was byte-identical to the compact JSON serialization of `structured_output`, while `num_turns: 2` and `stop_reason: "tool_use"` were recorded alongside it. The parser accepts either field alone or both when their JSON values agree, rejects trailing data, and revalidates exactly three fields (`classification`, `reason`, `scope`), the fixed classification enum, a 1-to-1,000-byte reason, and required `scope=loop|estate`. Missing, null, unknown, or wrongly cased scope and additional fields fail closed; both envelope payloads must agree on scope as well as classification and reason.

The nesting value is proof rather than a presence flag. A hook parses exactly one decimal `u32` PID and one decimal `u64` start time separated by a colon, requires field 22 of `/proc/PID/stat` to match that start time, walks field 4 from `/proc/self/stat` through the parent chain to prove that PID is an ancestor, and requires `/proc/PID/exe` to resolve to the same path as `current_exe`. Only a proof passing all four checks receives the fixed nested allow without another model call; that verdict is journaled and is silent in audit. An empty, malformed, forged, stale, non-ancestor, different-executable, or unreadable proof receives the fixed nesting-guard infrastructure denial, is journaled when the sink is available, and never reaches the model.

## Isolation and authentication · `sec:permissiontriage:isolation-and-authentication`

`PERMISSION_TRIAGE_ISOLATION=settings|bare` selects isolation and defaults to `settings`. A stored login is the common installation, and harness 2.1.258 documents that bare isolation reads authentication only from `ANTHROPIC_API_KEY` or an `apiKeyHelper` supplied through `--settings`, never from OAuth or the keychain. Settings isolation therefore permits the stored OAuth login while suppressing configuration sources and hooks; bare remains available for installations that authenticate with an API key. The runner neither copies authentication values into the prompt nor logs them, and rejected or missing authentication surfaces as a nonzero model failure for the adapter to deny as an infrastructure failure. Before installation, acceptance runs one authenticated classification through the deployed hook against the real classifier with the exact production argument vector, and one classification with authentication deliberately unavailable that must produce the structured infrastructure-failure denial; both are recorded with their walls.

Measurements on harness 2.1.258 establish that an empty `--setting-sources` value is accepted, empty sources alone suppress project hooks, `disableAllHooks` suppresses hooks that a positive control makes fire, stored OAuth remains available without bare isolation, and `--strict-mcp-config` plus `--disable-slash-commands` are accepted alongside those settings. Without bare isolation, auto-memory keys on the child working directory and otherwise feeds the current project's memory index—agent-written text—into the classifier; the runner therefore creates and uses the empty private `STATE_ROOT/classifier-cwd` directory in both isolation modes. CLAUDE.md files were not observed in classifier context under either mode. Bare additionally skips auto-memory by documented design and remains selectable for API-key installations.

## Hook adapter · `sec:permissiontriage:hook-adapter`

The pure adapter maps a decoded request, its optional fast-lane verdict, resolved caller role, and optional rubric or model outcome to a `HookResponse` and a schema-2 verdict. The four runnable classes have a would-be `allow`; an `agent-error` and `suspicious` have a would-be `deny`; and decoder, reduction, rubric, journal-approval, and model failures fail closed as infrastructure would-be denials. The binary applies the pipeline in this order: decode, one registry snapshot and role/root selection, nesting guard, fast lane, safe action reduction, rubric load in general-owner-domain order, model call, scope validation, eligible approval lookup or enforce consumption, response mapping, wall capture, journal publication, and the mode-specific response boundary.

For Bash and a command-form `Monitor`, the model action is the exact command; both traverse the same shell hygiene and canonical-command path, so a Monitor command inherits Bash timing, timeout, background, pipeline, destructive-operand, privilege, and syntax corrections. `Monitor` spells its deadline `timeout_ms`, bounded at 3600000 milliseconds, and its long-running declaration `persistent`, so those two fields carry the shape the Bash `timeout` and `run_in_background` fields carry and a persistent monitor is held to the background observation contract. Every reviewed reducer below names the fields of that tool's published input schema and treats each field as required or optional exactly as the schema does, because a reducer demanding a field the schema calls optional would deny real traffic as an infrastructure failure; a tool whose schema cannot be read has no reviewed reduction at all. Reviewed metadata reducers carry only the following fields:

|`NotebookEdit`|`notebook_path`, optional `cell_id`|Cell source and every other input field.|

|`ListAgents`, `ExitPlanMode`|Bare operation name|Every input field.|

An MCP tool name is split at its last `__` so the server segment is anchored to the whole prefix, and a server segment that still contains `__` is rejected rather than split again; without that anchor a tool name such as `mcp__filesystem__x__tool` would read as server `filesystem` and borrow that server's reviewed allowlist.

An unknown tool, including an MCP server with no allowlist, becomes `TOOLNAME fields=["SORTED","KEYS"]`: it contains field names but no values and reaches the model as an ambiguous capability. A missing or wrongly typed field needed by a reviewed reduction still denies as an infrastructure failure because a safe action cannot be formed. Unknown request fields on reviewed reducers are accepted without effect or echo. Write and message bodies, fetched and artifact page content, prompts, environment values, session data, transcripts, and prior output never enter the canonical action; the `Agent` and `Task` caller-authored description is the one exception, because it names the objective being delegated and is the safety-relevant fact those requests would otherwise reduce away. A tool whose input schema this package cannot read keeps no reducer, so it takes the unknown-tool path: an invented reducer that denies real traffic as an infrastructure failure misreports a working gate, while the unknown-tool path escalates honestly and names the tool in the journal.

`PERMISSION_TRIAGE_NESTED` is inspected only at the binary boundary after request decoding and caller-role collection and before policy evaluation. An absent value follows the normal pipeline, a verified value produces the fixed nested allow, and any supplied value that fails proof produces the fixed infrastructure denial; neither terminal guard result invokes the fast lane, rubric loader, or model runner, and both proceed through verdict publication and the mode-specific response boundary.

## Hook binary contract · `sec:permissiontriage:hook-binary-contract`

The instance requires exactly one `PERMISSION_TRIAGE_MODE=audit|enforce`; the adapter clears an inherited value before reading the instance, and the binary validates the selected value independently. In valid audit mode the whole applicable pipeline runs and journals every verdict, including deterministic results and infrastructure would-be denials, then writes zero stdout bytes and exits zero so the active harness gate decides. It emits neither a permission decision nor `additionalContext` and never consumes an approval. A failed audit sink yields only the bounded stderr diagnostic `permission-triage: lost audit event: journal publication failed` and exits zero with empty stdout, invalidating the audit window. Missing or malformed mode, an invalid instance, or an unavailable hook executable fails closed rather than defaulting to audit. In enforce, the structured allow/deny response remains, publication failure becomes a denial, and no infrastructure failure becomes an allow.

Audit silence applies only to a valid installation; a missing, replaced, or non-ELF hook binary fails closed in both modes before the instance mode is parsed.

`permission-triage hook` reads at most 1 MiB plus one overflow-detection byte from standard input. In enforce it writes exactly one compact JSON object to standard output: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow|deny","permissionDecisionReason":"…","additionalContext":"…"}}`; in valid audit it writes zero stdout bytes. Input of exactly 1 MiB is accepted by the bounded reader and passed to decoding; only the first byte beyond that boundary produces the over-cap infrastructure would-be denial, without buffering the remainder. Every serialized enforce response and every completed audit response exits zero. If an enforce response cannot be serialized or published, the binary writes a fixed last-resort infrastructure-failure deny to standard error and exits two. The hook never intentionally exits one. `permission-triage version` prints the crate version and embedded general-rubric SHA-256 digest without reading standard input. A sole `--version` on any of the four binaries emits one JSON version record on standard error with empty standard output and exits zero, or one if the record cannot be written. Any other `permission-triage` invocation prints `usage: permission-triage hook|version` to standard error without reading standard input and exits two.

The binary measures elapsed time from the start of hook input handling through response construction and separately around the model call. `additionalContext` repeats the concise result and appends `wall_ms=N model_wall_ms=N`; paths that do not invoke the model report zero model milliseconds. `PERMISSION_TRIAGE_HOOK_CEILING_MS` supplies the design ceiling used to budget journal locking: it defaults to and is capped at 60000 milliseconds, while a larger, nonnumeric, empty, or non-Unicode value falls back to that maximum. The harness remains responsible for terminating the complete hook invocation at its registered ceiling.

## Reason grammar · `sec:permissiontriage:reason-grammar`

Allow reasons begin with the selected class, including `safe` for a harness-owned read-only fast-lane decision; a consumed one-shot approval begins `adjudicated:` and names its journal mark. Deterministic and model `agent-error` denials begin `correction:` and describe the smallest repair. Suspicious denials begin `escalation:` and name scope, resolved role, caller loop, the exact journal event ID, and the responsible loop or estate adjudicator without echoing the action. An estate event requires separate estate authorization; a loop mark cannot authorize it. Decoder, input, action-reduction, rubric, adjudication-journal, and model failures begin `infrastructure-failure:`, name the failed component, and state that no policy judgment was made. Reasons are capped at 1,000 valid UTF-8 bytes. The no-echo guarantee is exact-substring removal, not a semantic redaction: when a reason contains a complete Bash command or reduced non-Bash action of at least four bytes, or any quoted non-Bash target value of at least four bytes, the adapter substitutes a fixed explanation under the original class or denial prefix. Values shorter than four bytes, including commands such as `w` and `ls`, do not trigger removal. Neither the response reason nor `additionalContext` echoes a removed value. The decision vocabulary contains only `allow` and `deny`.

Model output is exactly `{classification, reason, scope}`, with the existing six classes and precedence, capped reason, and required `scope=loop|estate`. Scope describes effects independently of class: a bounded estate read can still allow as `advanced-read-only`. The hook computes scope for deterministic results and diagnostics; unknown identity and unresolved effects are estate-scoped. Known protected targets impose an estate floor. A model loop verdict contradicting that floor becomes an infrastructure denial with null classification and estate scope, rather than a silently rerouted allow. Prompt instructions explain scope while the existing reviewed rubrics remain unchanged data.

Scope validation reuses the pure shell tokenizer, including bounded inspection of quoted shell bodies. The hook checks paths, existing symlink ancestors, configured authorization sources, peer checkouts, protected instruction/configuration names, and estate administration commands. Credential trees beneath a home's `.config` (the loop custody roots, the owner's `GnuPG` and Codex homes, the per-loop keyring and forge directories, and an entered home's custody bind target) are protected as adjacent path components, so `loops` or `codex` directories elsewhere are not protected by name. Native file reducers use their target fields; body text is not a target. Model judgments may also use absolute directory roots quoted in the reviewed domain rubric, including its single-component wildcard roots; those candidate roots never suppress protected targets or grant an allow by themselves. Host configuration and system installation roots impose an unconditional estate floor on both the lexical target and its resolved symlink destination; quoting `/etc/` cannot make `/etc/hosts` loop-scoped, and `/` is not a domain candidate. Deterministic paths without loaded domain facts conservatively use the registered checkout. Provisioned-account domain work differs from account or shared-service configuration. Unresolved expansions, unsupported scope shapes, and unknown capabilities cannot obtain loop authority. Peer boundaries come from the same registry snapshot that resolved the caller and cover each peer's checkout, state root, and home, so a caller at the deployment uid reading a peer's world-readable run directory is estate-scoped; under the deployed tier layout a worker's uid additionally cannot open a peer loop's home, private tree, worker trees, or run directories at all, so for a worker the rubric boundary is the second refusal rather than the only one. A caller's own registered `LOOP_HOME/runs/` is loop-scoped beside its checkout; nothing else under its home is.

## Escalation journal · `sec:permissiontriage:escalation-journal`

A deployment-uid caller selects its registered `LOOP_STATE_ROOT`, while a worker uid selects `LOOP_HOME/runs/<uid>` from the same validated registry snapshot. Registered loop and estate roots use mode 0700 and mode-0600 journals; worker run roots may be world-readable and carry mode-0644 journals, and every root still passes ownership and no-follow checks. A worker resolved by its uid block journals in its own run directory `LOOP_HOME/runs/<uid>`, owned by that uid with no group or other write bit and a mode-0644 journal. A worker's estate-scoped verdict is written as one mode-0644 file named by its event identifier into its loop's outbox, the mode-1775 directory `outboxes/NAME` beside the registry, at the worker's own uid; the outbox's shape and owner are verified on every write, a collision or an unwritable outbox is an infrastructure failure, and the record carries `loop-outbox` as its destination in place of a journal line. `PERMISSION_TRIAGE_STATE_ROOT` selects the explicit estate root, matching the registered estate entry, rather than the journal for every loop. Loop-scoped events go only to the caller root's `escalations.jsonl`; a deployment-uid caller's estate-scoped events go only to the estate root's distinct `estate-escalations.jsonl` and retain caller loop/role. The estate orchestrator's own loop-scoped work therefore stays out of its estate stream; each stream has its own lock. Unknown identity records an estate diagnostic in audit and denies for infrastructure failure in enforce. A failed known-loop sink never copies a loop-scoped record to estate. The classifier creates a private empty `classifier-cwd` beneath the selected root; loop-scoped verdicts append to that root's journal, and the estate root also holds its distinct estate journal.

The journal writer publishes every verdict as schema 2 with `schema`, `event`, `event_id`, `recorded_at`, `tool_use_id`, `request_digest`, `tool`, `cwd`, `command`, `classification`, `reason`, `scope`, `mode`, `would_be_decision`, `emitted_decision`, `role`, `loop_name`, `stale_session`, `general_rubric_digest`, `owner_rubric_digest`, `domain_rubric_digest`, `model_status`, `wall_ms`, and `model_wall_ms`. `mode` is `audit|enforce`, and would-be decision is `allow|deny`; emitted decision is null in audit and the intended serialized decision in enforce, never proof of execution. Infrastructure and nested diagnostics have null classification instead of a fabricated policy class; unavailable fields are null and unresolved role is `unknown`. Nonnegative monotonic `wall_ms` ends immediately before append, and `model_wall_ms` is null without a model call. Every new verdict records its computed or validated scope. Scope selects exactly one registered destination, with no duplicate record in the caller stream for an estate event. Deployment validation rejects a missing, overlapping, or unsafe registered state root before verdict publication. Schema 2 dispositions and approval consumption retain their source scope and adjudicator identity. Schema 1 history stays readable with an explicit legacy/unscoped label but cannot supply a new disposition or approval consumption.

`PERMISSION_TRIAGE_STATE_ROOT` is required and selects only the estate root, which must match exactly one registered entry. Every loop root must exist at its registered absolute path and every worker root beneath its loop's registered home at the caller's own uid; each must be owned by the effective uid, carry no group or other write permission, contain no registered authorization source, and remain disjoint from every other root. Root opening rejects dot components and symlinks in every path component. The hook pins opened root directory descriptors for journal accesses, so a later registry replacement cannot mix an earlier role with a new destination. The classifier creates only its empty private `classifier-cwd` beneath the selected caller root; an unknown caller uses the private estate diagnostic root. When the registry is absent or unavailable, that explicit private estate root can retain an unknown audit diagnostic, but enforcement refuses identity and no known-loop failure uses this exception. Registered review uses the same strict root validation. A broken audit sink emits a bounded lost-event diagnostic with zero decision bytes; enforce denies. Rust's standard advisory `File::lock` API postdates this crate's Rust 1.88 compatibility contract, so the std-only fallback acquires `escalations.lock` for loop scope or `estate-escalations.lock` for estate scope with atomic exclusive creation, writes the holder PID, and verifies that any contended lock is a regular mode-0600 file without following a final symbolic link. Stale recovery is attempted on the first contention poll and every later poll throughout the bounded wait. Only a lock whose PID is no longer live and whose mtime is at least 60 seconds old is eligible; it is claimed by renaming it to a process-unique `escalations.lock.steal.*` path and re-reading its device, inode, contents, and mtime. A matching claim is removed, while a mismatched claim is restored only when the canonical path appears absent and acquisition always retries. Before acquisition, orphaned steal claims and `.permission-triage-owner-probe.*` files receive the same dead-pid and 60-second-mtime conjunction, process-unique rename, identity recheck, and conditional removal or restoration, using the PID encoded in each orphan name. PID liveness is a std-only read of `/proc/PID/stat`: a missing entry or `Z` state is dead, while malformed or otherwise unreadable state is conservatively live. That observation is meaningful only within the caller's PID namespace; a state root shared across namespaces therefore relies on the mtime bound as well as the conjunction, so a live-looking foreign PID is never stolen before the bound. A guard removes the canonical lock on release only when its open handle and the current path still have the same device and inode; if a steal claim temporarily displaced that path, the guard rechecks for one quarter of the lock-acquisition budget that remained when it acquired the lock. After creating either `escalations.lock` or `escalations.jsonl`, the process opens the state-root directory and calls `sync_data` so the new dirent survives a crash. The writer opens the journal append-only without following a final symbolic link, requires it to be a regular file at mode 0600 on every open, performs one append, calls `sync_data`, and releases the lock. A missing, relative, unsafe, unusable, unlocked, or unsynchronized journal makes enforce publish an infrastructure denial and makes audit emit only the bounded lost-event diagnostic; journal failure never allows in enforce. Because the standard library has no inode-conditional rename or unlink, residual path-lock races never lose or truncate evidence, but a duplicate disposition halts journal reconstruction with `DuplicateDisposition` until the duplicate line is removed by hand from `escalations.jsonl`; the other bounded outcome is a spurious empty journal line.

If a lock failure names `STATE_ROOT/escalations.lock`, first inspect its recorded PID; if an ownership failure names `STATE_ROOT/.permission-triage-owner-probe.*`, inspect the PID encoded in that probe name. Confirm that the named process is not live. A lock or probe is reclaimed automatically only when that PID is dead and the file is older than 60 seconds; if automatic recovery repeatedly fails, the owner may remove that exact path only after confirming it has not changed and its PID remains dead, then retry the denied request.

Each JSON Lines record is at most 8 KiB including its newline. Before an append, the locked writer checks the existing tail; when a nonempty journal does not end in a newline, it appends one newline separator before the next record and never shortens the file. The separated fragment is a malformed complete line, which review reports and skips and disposition lookup ignores. An oversized record shortens `command` and `reason` only at valid UTF-8 boundaries and adds `"truncated":true`; if the fixed fields alone cannot fit, journaling fails closed. A schema-2 suspicious result uses `event=escalated`, every other classification or diagnostic uses `event=verdict`, and `event_id` is a per-process monotonic-sequence-derived SHA-256 identifier. A disposition repeats the source correlation fields, uses `event=disposition`, adds `outcome`, `adjudicator_role`, `adjudicator_loop_name`, and `source_scope`, records the owner action in `reason`, and uses `model_status=owner-mark`. The observable outcome vocabulary is `escalated` for an unadjudicated classification and `adjudicated-rule-added`, `adjudicated-rejected`, `corrected-and-rerun`, or `adjudicated-approved` for a correlated disposition. Consuming an enforce approval appends its schema-2 `approval-consumed` event and the resulting allow verdict together under the same lookup lock, with one append and synchronization. Consumption retains the prior event ID, current tool-use identifier, approved request digest, caller role and loop, scope, and all three rubric digests. Audit performs a read-only eligible lookup and never consumes. The model must complete successfully and pass scope validation before any approval is considered; estate results, corrections, and infrastructure failures cannot be replaced by a loop approval. Complete schema-1 escalation, disposition, and consumption records remain readable for historical review and are labeled legacy/unscoped, but source selection skips them for new dispositions and approvals. Session identifiers, transcript paths, agent identifiers, registry paths, descriptions, arbitrary tool input, tool output, model standard error, rubric contents, and environment values are never retained. The cross-process uniqueness assumption for `event_id` is that PID reuse will not coincide with the same nanosecond timestamp, per-process counter value, and request digest.

## Owner workflow · `sec:permissiontriage:owner-workflow`

The superloop's orchestrator agent reviews its own private journal and adjudicates each escalation; no person participates in per-request adjudication. When a stable legitimate request shape needs reusable authority, the owner first writes and reviews the narrow owner-rubric rule by hand, including its exact alias, account, command grammar, path, operand, deadline, timing, and forbidden-expansion constraints, and only then records `adjudicated-rule-added` with that already-written rule identifier. A rejected request is marked `adjudicated-rejected` with the reason. After an issuing worker repairs and reruns a malformed request and reports that success, the owner may mark the original event `corrected-and-rerun` with the corrected request digest. Neither review nor any mark form edits a rubric.

Suspicious loop-scoped work from a worker, including a Codex lane or in-session subagent, is reviewed by its loop's main session. The main session must re-issue approved work as its own request; the worker cannot consume an approval. Marks are bound to that prior request's original caller identity. Separate registry-selected loop journals and the estate stream provide the corresponding destinations. Only estate-scoped escalations reach the estate orchestrator: harness settings/hooks, instruction and authorization sources including rubrics and registry, host/network configuration, shared infrastructure such as hub services, server-account configuration, toolchains and gateway, and another loop's state. Routine use of a loop's provisioned hub/account differs from modifying that shared service or account. Scope-bound review rejects cross-loop marks and worker self-approval; loop approvals cannot authorize estate changes. Rubric updates require estate review even when their files are loop-local. Estate-adjudicator provisioning remains unspecified and unavailable in this bite: every estate mark is refused, even from the owner of the explicit sink. Bite 5 must provision explicit estate adjudicator identity and a trusted invocation route before estate marks can be enabled; root ownership or a loop approval cannot supply that authority.

## Deployment · `sec:permissiontriage:deployment`

The closed instance grammar requires `PERMISSION_TRIAGE_MODE`, accepts only `audit` or `enforce` with no default, and rejects duplicates, empty or wrongly cased values, and inherited-only values. That state root is ignored by Git and must remain ignored so private verdict evidence cannot be staged.

Assembly runs as `permission-triage-assemble --verdict FILE --repo DIR --instance FILE --out DIR [--audit-evidence FILE] [--check]`. It requires an eligible schema-2 full-roster bypass verdict with every audit, bypass, settings-deny, infrastructure, table-confirmation and friction row, including the correlated repetitions and captures. Schema 1 and historical manual/AUTO success do not qualify. Fake provenance is rejected with exit 3 and `harness: fake`, including retained fake-name/byte/digest flags in a verdict claiming real. The instance's owner rubric and repository domain rubric remain beneath `REPO/local/`, while the instance's estate state root, like every registered loop root, is an absolute dot-component-free path provisioned at its registered location and may lie outside the checkout; worker run roots derive from registered homes and may be world-readable, and every registered rubric must be present. The estate checkout/root must match its registry entry. The configured private hook supplies version/general-rubric identity; the configured executable classifier is recorded by path and digest. `loopRegistry.sha256` binds compact JSON serialization of the sorted `(name, optional identifier, checkout, state root)` tuples, and `domainRubricDigests` binds each rubric's exact bytes. The deployment record stores each published worker verdict under `workerRubricVerdicts` with `loop`, `orchestratorRubricDigest`, `workerRubricDigest`, and `checkedAt` keys. `bypassEvidenceDigest` binds compact sorted-key JSON serialization of the verdict's bypass rows; `verdictDigest` binds the exact verdict bytes. Optional readiness evidence has the strict schema documented in `deploy/assemble.md`, with no defaults or unknown object fields. Journal and evidence readers require calendar-valid UTC `YYYY-MM-DDTHH:MM:SS.nnnnnnnnnZ` timestamps, matching the journal writer's nine-fractional-digit UTC format. A successful `--check` validates the prospective registry in a disposable scratch directory, constructs the complete prospective output, prints nothing, leaves published files unchanged, and exits zero; an interrupted check can leave a hidden staged directory for a later successful publishing assembly to retire, if cleanup succeeds. Without `--check`, assembly exchanges the live registry when a ledger exists before publishing one review directory containing `settings-fragment.json`, an audit `permission-triage.env`, `deployment-record.json`, and `assembly-marker.json`. `auditEvidence` and `auditEvidenceDigest` are null for initial audit assembly; with validated evidence they retain the full observations/limits and exact evidence-file digest. The record always has `hookMode=audit`, `sourceHookMode` records the input mode, `instanceDigest` binds the rendered instance, and `sourceInstanceDigest` binds the input bytes. Output paths overlapping the ledger or its directory, registry or its parent, repository, registered checkouts, roots, rubrics, homes, worker verdicts, the configured private hook binary, system mapping files, or another protected input are refused; an existing output directory is empty or contains exactly the four previous review files. Usage exits 2; other infrastructure failures exit 1.

The `deploy/assemble.md` runbook is the owner installation procedure. The assembler stages registry rows and review files under the exclusive nonblocking lock on the registry parent, takes the configuration-root lock shared when distinct or reuses its exclusive guard when both names select one inode, then takes the ledger lock shared when present and rechecks it, exchanges the live registry when a ledger exists, atomically publishes the review directory, then retires older hidden generations. After a zero exit, the owner checks the marker against the deployed rows and record before installing the review files with the published commands and performing the real authenticated host rehearsal. Assembly changes live registration at the exchange when a ledger exists; it does not change the installed instance mode or harness settings. An interruption can leave a hidden staged directory or a retained registry generation, while an output publication failure can leave the new live registry beside an older review directory whose marker cannot authorize installation after a failure exit.

No deterministic fast-lane row or deployment topology is enabled by this bite. The historical `manual` and `auto` probe results remain characterization only and cannot satisfy the revised assembler. Authenticated acceptance and deployment require the owner-run rehearsal on a real harness and the owner's explicit flip decision.

## Test strategy · `sec:permissiontriage:test-strategy`

Unit tests use table-driven positive and negative twins for every read-only claim and every hygiene rule. Pure adapter tests cover verdict mapping, the silent/serialized response boundary, read-only-table revalidation, non-Bash reduction, reason caps, and the echo threshold. Integration tests spawn Cargo's built `permission-triage-hook` binary and cover both modes over all six classes, deterministic correction, model timeout and bad output, malformed requests, valid and forged nesting, journal failure, exact audit silence, schema-2 fields, enforce publication denial, audit approval non-consumption, legacy read-only review, mode grammar at adapter/binary/assembler boundaries, audit-only installation and reinstall rendering, binary exit statuses, argument handling, unknown fields, stdin-read gating, and version output.

The private `permission-triage-hook` executable owns the bounded input and permission authority implementation. Meson installs it in `libexec/superloop/hooks`; installing it does not register it. The assembler invokes the absolute `PERMISSION_TRIAGE_HOOK_BIN` configured at build time, with an explicit environment override for a separately staged release. A missing or relative path refuses; sibling names and PATH lookup are not used. The previous release stays in place until registration and session drain permit retirement; no old entry point or wrapper is built by the successor.
