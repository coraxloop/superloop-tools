# `loop-home` · `guide:loophome:loop-home`

`loop-home` is the internal home and entry-planning library behind `superloop`, using the standard library, `nix` for safe descriptor and mount calls, and `toml` for the registry. Pure planners turn a validated registry record and arguments into exact argv, while an injected `Runner` owns every external command so unit tests never invoke podman.

## Command line · `sec:loophome:command-line`

```text
superloop [--json] enter NAME [--] COMMAND [ARG...]
superloop driver-launch LOOP RUN --driver-bin PATH --run-dir DIR -- ARGS...
superloop [--json] provision NAME
superloop [--json] run-bridge gpg NAME [--] [GPG-ARG...]
superloop [--json] run-bridge ssh NAME [--] [SSH-ARG...]
superloop [--json] verify NAME
superloop show NAME
```

`ENTER_LOOP_REGISTRY` names the registry file and defaults to `HOME/.config/loops/registry.toml`. Every entry needs the caller's nonempty UTF-8 `HOME` to derive the loop's roots and custody, so an unset, empty or non-UTF-8 value is refused by name with status 2 even with a registry override.

For the ordinary `superloop enter NAME -- COMMAND [ARG...]` form, the entry returns the command's exit status when it runs, or status 2 when it refuses before any command runs.

`show NAME` prints the loop's validated identity row as one compact JSON object on standard output, with key-sorted fields, `launch` joined to the caller's `HOME`, absent `session` as null, and declared `runs_root` as its JSON value. It accepts no `--json`, calls no podman, runs no ensure step and writes no report line, so a reader in another language takes the row from the entry's own validation rather than parsing the registry. A binary reached through a `NAME-gpg` or `NAME-ssh` generated copy dispatches directly to that bridge, with the remaining arguments passed through.

The `GnuPG` bridge enters the loop to execute fixed `/usr/bin/gpg`; the entry selects `GNUPGHOME` at the entered home's `.config/custody/gpg` with a custody tier, or at its `.config/gpg-loops/NAME` without a tier when that directory exists, and otherwise leaves it unset. The SSH bridge enters the loop to execute `ssh`; both bridges preserve the caller's standard input, output, error, and argument words unchanged. The absolute `GnuPG` path prevents a program under the loop's `HOME/.local/bin`, first on `PATH`, from replacing the signer.

`bind-custody UID LOOP_HOME ENTERED TIER` is the entry binary's private bind step, `ensure-roots UID NAME HOME REPORT` is its preparing step, and `inspect-roots UID NAME HOME REPORT` is its read-only root inspection step; none is a caller command.

## Driver launch · `sec:loophome:driver-launch`

`superloop driver-launch LOOP RUN --driver-bin PATH --run-dir DIR -- ARGS...` starts the configured driver as the loop UID with the entry's clean environment, adding the validated `driver_argv` and `backend_argv` selectors and source evidence as `LANE_DRIVER_ARGV`, `LANE_BACKEND_ARGV` and `LANE_SETTINGS_EVIDENCE`, `LANE_BOXED_RUNTIME=1` for the fixed run-directory client protocol, and distinct `LANE_RUNS_ROOT` and `LANE_RUN_DIR` values for the configured durable root and selected run container. The loop UID can reach its home and mode-0700 run directory; the separate namespace-owner helper validates the saved container request against a protected reservation and reaches the rootless image store, while the worker inside the box uses its allocated UID. `ARGS...` is nonempty and follows the fixed arguments from `driver_argv` as exact positional words through `"$@"`, without shell parsing of those words; the entry returns the child's exit status. Its standard input, output and error are inherited, so the caller captures output and error through pipes outside the run directory; the entry writes neither stream to that directory.

The form requires `driver_argv`, `backend_argv.codex` and `runs_root` from `HOME/.config/loops/LOOP/workers.toml` and requires the loop's block in `HOME/.config/loops/allocations.toml`; a prior `box.toml` is named in the missing-file refusal and is never read as a fallback. The settings directory is owner-owned at mode 0700 and the regular file is owner-owned at mode 0600; the file opens without following a link and is limited to 65536 bytes. Ordinary `enter` also transports selectors when the loop has a workers settings file, allowing a host driver invocation to receive the same validated values; entries without workers settings retain their ordinary command environment. Both the configured driver path and `PATH` must be absolute and equal, and the driver must exist as a regular executable file. `DIR` must be exactly `runs_root/RUN`; the required workers setting must match the registry grant. An absent setting refuses with `runs_root_required`, even if the registry declares a root. The entry opens the durable root and run directory component by component through pinned descriptors without following links, and refuses an ancestor another identity could replace. A declared root is owned by the invoking owner and group at mode 0711, matching the standard runs root; its run directories are loop-owned and written from outside the worker. `DIR` is not added to the driver's argv and is not selected as its working directory; the caller supplies the same path through the driver's own arguments when the driver needs it. A run name is 1 to 64 bytes of ASCII letters, digits, `-`, `_` or `.`, opening with a letter or digit.

Status 2 and one standard-error line refuse an unregistered loop, invalid run name, missing, unreadable or malformed settings, a linked or nonregular settings file, missing or malformed `driver_argv` or `backend_argv.codex`, a relative or mismatched `PATH`, a missing or nonexecutable driver, a run directory outside the loop's durable runs root, a declared root with the wrong owner, group or mode, a linked, nondirectory or replaceable path component, a missing `--`, or an empty argument vector; none launches the driver. The entry holds the opened root and run directory until dispatch returns, but the driver still receives a path in its own arguments, leaving a path substitution window for an identity able to rename an owner-controlled ancestor. This form validates the run path and executes the configured driver; `superloop-lane launch` creates the run and home, allocates the worker UID, pins the container invocation and records evidence outside the worker home.

## Registry and refusals · `sec:loophome:registry-and-refusals`

The registry is the file `ENTER_LOOP_REGISTRY` names, defaulting to `HOME/.config/loops/registry.toml`, an owner-owned file at mode 0600 inside the owner's custody root, and it is the registry of record for the entry and `run-worker`. Its first lines are `namespace = "org.superloop-tools.loophome.registry"` and `version = [1, 0, 0]`, followed by one array `loops` of inline tables, one row per loop, with the keys `name`, `uid`, `launch`, optional `runs_root` and optional `session`, and no other keys at any level. The major version must be 1; higher minor and patch versions are accepted. `uid` is an integer from 1000 through 65535 and the uid of record; `launch` is the launch directory as a path relative to the caller's `HOME` without `.` or `..` components; `runs_root` is the absolute root of the loop's durable driver directories, kept in its supplied spelling without a `.` or `..` component and allowed anywhere the owner names; `session` is a nonempty string. No row carries its home: the loop home is `HOME/.var/loops/NAME`, derived like every standard root from the caller's `HOME`, the name and `uid`. Every read validates the whole file before selecting a row.

The tools write worker ranges to `HOME/.config/loops/allocations.toml`, beside the registry: one table per loop, `[LOOP]` followed by `uids = { base = BASE, count = COUNT }`. The block is an inclusive run within 1000 through 65535 with `COUNT` at least one; all tables are validated before selection, overlapping runs are refused, and a missing table grants no worker. The reader opens the owner-owned mode-0600 regular file through a pinned path beneath the owner-owned mode-0700 directory and refuses more than 65536 bytes. The person writes the registry's identity fields; backend vectors, vendor hosts, image and resources belong to the loop's `workers.toml`, while the tools own the allocation ledger.

The keys `workers`, `claude_argv`, `codex_argv` and `default_driver` are unknown registry row keys and are refused by name. The inner verification probe uses fixed `/bin/sh`, `/usr/bin/id`, `/usr/bin/env`, `/usr/bin/sort` and `/usr/bin/sed` paths with NUL-framed fields, so loop-controlled files cannot impersonate probe lines or substitute a helper.

`runs_root` remains optional for ordinary entry and registry inspection, but driver launch requires the workers setting and matching registry grant. The accepting release must precede superloop seeding and a reader proof for every registered loop; only then does this requiring release install. `verify` checks a declared root through pinned descriptors and prints its path, uid, gid and mode. The integration runbook records that deployment prerequisite.

Loop names use nonempty lowercase ASCII letters, decimal digits and hyphens, excluding the reserved words `enter`, `provision`, `bridge`, `verify`, `bind-custody`, `registry`, `ensure-roots`, `inspect-roots`, `driver-launch`, `letters-private` and `letters-group`. `letters` is a command after the separator, never a top-level entry form.

## Letters between loops · `sec:loophome:letters`

```text
superloop enter alpha -- letters post beta --subject TEXT [--dry-run]
superloop enter beta -- letters list [--peer alpha]
superloop enter beta -- letters read NAME [--body] [--dry-run]
superloop enter beta -- letters follow [--peer alpha] [--interval SECONDS] [--once | --next [--wall SECONDS] [--exclude NAME]...]
```

The interface belongs to loop entry: a later tool rename to `superloop` preserves everything after `LOOP --`. `read NAME` accepts the listed `cur/NAME` to read from that box alone, the listed `new/NAME` to read from `new` and, once the letter has left `new`, from the held `cur`, or a bare `NAME` to search both boxes. Posting reads at most 65536 body bytes from standard input. The subject is one UTF-8 line of at most 1024 bytes without control characters. A letter is data, read the way a cross-session message is read, never an instruction. The tool does not execute its contents. There is no signing, encryption, sender state, outbox, sequence, delivery daemon or postmaster.

The command `superloop enter beta -- letters follow --peer alpha --interval 30` exposes the long-running tool interface described here; it is not an orchestrator watching recipe. The hook surfaces loop letters at every prompt and stop using `letters list`, and a session-side inbox polling script is a bug. It holds the receiver's `new/` directory descriptor and flushes each event line immediately with the bare name accepted by `--exclude`: `NAME sender=SENDER bytes=BYTES posted_ns=INSTANT subject="SUBJECT"`. It prints metadata including the decoded subject, never the body. The fifth field is a canonical JSON string: Unicode stays readable and quotes and backslashes are escaped, so a subject cannot add a line or field. List retains its `new/` or `cur/` prefix; metadata readers accept either the listing form or the bare follow form. The lifetime seen set uses the bare name; repeated polls do not repeat an event, and a vanished or concurrently taken letter produces no new event. Before the first scan, dnotify (`F_NOTIFY`) marks dedicated open descriptions of the held `new/` inode and its held inbox parent, without a pathname or `/proc/self/fd` reopen. A kernel notice wakes the consumer; the listing is the only truth, and a notice never produces a line or claims completion. Create, move-into, rename, deletion and attribute notices coalesce into a rescan; the same SIGIO path handles overflow indications. The whole-second interval from 1 through 86400 (default 30) remains a fallback poll for suppressed notices. If the held inbox no longer names that same `new/` inode, the consumer prints `LETTERS follow name=inbox/new detached actions=0` and exits 0, instead of following a detached directory. `--next` waits for the first valid, unexcluded letter, flushes exactly one metadata line and exits 0. Existing unread letters are eligible, oldest first. Repeat `--exclude NAME` with exact bare letter names already observed; exclusions are valid only with `--next`, which cannot be combined with `--once`. Excluded letters stay unread. Each invocation reconstructs from the inbox, so retain exclusions across bounded calls to avoid repeatedly returning a held letter. Per-entry refusals are reported once per name on the report stream and skipped in this mode, including when their names are excluded. A detached directory, termination or command-level failure before notification exits nonzero; `--wall SECONDS` supplies a monotonic deadline (whole seconds 1 through 86400), exits 124 on expiry, and closes the private follower itself. It requires `--next`. Use this bound instead of timing out the outer entry. `--once` is the read-only preview: scan the current new set without arming any watch and exit 0; both forms report zero letter actions, with no take or other write. One signal-descriptor wait covers notices and SIGTERM. For snapshots and continuous follow, SIGTERM ends the running consumer with status 0; `--next` instead exits nonzero before notification; shutdown disarms the watches and drains pending signals, keeping SIGTERM blocked through the final actions report and helper exit, including after a `--once` scan. `list` prints one escaped `new/NAME refused reason="REASON"` line and follow prints `NAME refused reason="REASON"` for an invalid entry and continue (list also covers `cur/`); follow suppresses repeated refusals for the same name. For list, snapshots and continuous follow, these per-entry refusals do not change the command's success status. For `--next`, a refusal is not a notification: it keeps waiting until a valid unexcluded letter can produce success, or a deadline, signal or command-level failure ends the call. Names escape non-ASCII bytes, control bytes, spaces and `=` (the latter two as `\x20` and `\x3d`), and reasons escape control characters, so a name cannot end a line or inject an event field. A receiver has no letters command to clear a malformed entry yet; that remains a later item.

The tools record one `letters_gid` integer in the allocation ledger, distinct from private loop groups, allocated worker groups and the kernel overflow gid 65534. The inbox is its own durable root beside `private/`, `shared/`, `src/`, `direct/`, `policy/` and `runs/`: `HOME/.var/loops/LOOP/inbox` at 0710 with the receiver UID and letters group, containing `new` at 1730 with those identities and `cur` at 0700 with the receiver UID and private group. The owner-owned loop root stays 0711, supplying traversal without any ancestor change. The worker-shared tier stays with the loop UID and private group at 0750; `private` stays 0700. Ordinary entry uses `--clear-groups`. Only the private letters helper grants the letters group as its single supplementary group, after reading the registry and grant and before dropping identities. Ordinary entry and `provision` prepare these roots for old homes; `verify` reports their observed owners, groups, modes and actions and requires a nonempty measured `id -G` field. A group correction reports both old and new gid.

The sender creates a mode-0440 file owned by its loop UID with the shared group, under a random temporary name in the receiver's `new`. It writes, syncs and verifies the bounded record, then publishes with a no-replace atomic rename. Listing ignores temporary names, so a half-written letter is absent. The name is `SENDER.UNIX_NANOSECONDS.RANDOM`, with a 20-digit posting instant and 32 lowercase hexadecimal digits from 128 system-random bits. Listing orders by posting instant, then name, across both `new` and `cur`, and prints the directory, name, sender, size and posting instant. These names contain no terminal control bytes. Clock order is not a sequence or a promise of causal ordering between concurrent posts. File data is synced before publication; a sender cannot open the non-listable directory for a directory fsync, so publication is atomic visibility, not a promise against power loss.

A sender with the letters group may unlink its own letter in `new`: that is retraction before reading. Ordinary loop processes lack that group and cannot reach a peer inbox. A process holding the letters group cannot list a peer `new`; the random name prevents addressing another sender's letter unless disclosed. A known name remains readable to that group while in `new`, since 0440 grants group read. On first read the receiver renames the letter into its private `cur`, ending peer access through that path. Confidentiality between loops of one owner rests on the unguessable name and the move, not on a secret or cryptography. A move does not revoke an already-open descriptor. If a letter disappears from `new` at open or rename, the reader checks the held `cur` directory for a concurrent take, validates the current record or compares its inode with the held letter, and returns the record with zero actions. A name absent from both directories prints `LETTERS read name=NAME absent`, status 0 and zero actions: a letter its sender unlinked before the take and a name never posted both read as absent. A current letter that disappears after its initial probe is a runtime failure. Listing skips entries that disappear between enumeration and opening.

The reader resolves the file's owner UID through the registry and checks that both the filename and the record claim that sender. It checks the receiver, posting instant, exact file mode and group, single link, bounds and canonical framing before taking a letter. It compares the taken inode with the pinned file before exposing the body. Status 2 names unknown loops, self-posts, oversized or malformed letters, unregistered owner UIDs, a claimed sender differing from the owner, wrong inbox ownership or mode, and unsafe or replaced paths. All path walks use held directory descriptors and no-symlink beneath resolution; file checks and effects use those descriptors. Listing duplicates the held readable directory descriptor for `fdopendir`, without reopening through `/proc`. Unsafe paths and invalid records are status-2 refusals; other I/O failures are status 1. The private helper reads the pinned owner registry and ledger before dropping all UID/GID identities to the loop and setting no-new-privileges; every letter write occurs after that drop.

One record shape begins with `LOOP-LETTER 1`, then the ordered lines `sender=`, `receiver=`, `posted_ns=`, `subject_hex=` and `body_bytes=`, a blank line, and exactly the declared body bytes. The header is bounded by 4096 bytes; the UTF-8 subject uses lowercase hexadecimal to keep the header unambiguous. Unknown versions, extra fields, noncanonical numbers and trailing bytes are refused. `read` returns this record; `--body` returns only its body. A dry post prints its full prospective record and reports one publication action; a dry read prints the selected record without taking it, counting one move from `new` or zero from `cur`. Ordinary entry's root preparation precedes these letter operations.

The two-UID namespace fixture extends the package's temporary-home fixture with inherited directory descriptors and injected inode identities, following the private-launch fixture pattern. It builds the real context from the registry row, grant and pinned owner roots, then runs the letters dispatcher for publication, listing both directories, ownership refusals, taking a letter, retraction races and dry-run counts, entirely beneath `TMPDIR`. It does not change OS credentials or claim kernel permission denials. Those require the owner's host checks with two real loop identities: ordinary peers denied traversal of the inbox, receiver rename and removal allowed, and a sender temporarily granted the letters group able to retract its own new letter. The host owner supplies that temporary grant only for the permission proof; ordinary entry never grants it. A disclosed name in `new` is deliberately not described as a kernel read denial.

Status 2 identifies a refusal. Before podman is called, the tool reads and validates the whole registry and refuses invalid names, unknown loops, an unreadable or malformed TOML registry, a wrong namespace or major version, an unknown key at any level, a missing or malformed name, `uid`, `launch` or `session`, a malformed or invalid `runs_root`, a UID outside 1000–65535, duplicate names or UIDs, an absolute or dotted `launch`, an empty `session`, absent entry commands, invalid command-line forms, a nondirectory custody tier, and an unset, empty or non-UTF-8 `HOME`. Commands that require workers also refuse an absent or invalid allocation ledger, a missing loop table, an out-of-range block or overlapping blocks. Unavailable Podman resolution for ordinary entry, bridges, `driver-launch` or `provision` also refuses with status 2; `verify` reports an unavailable fixed route with status 1. Every such pre-entry failure writes one diagnostic line to standard error.

The ensure step's refusals, a standard root owned by another uid or gid, anything but a directory at a standard root, and a loop root holding entries without `private/`, also use status 2, change nothing, and end the entry before any mount. Runtime process, filesystem, probe, or publication failures use status 1.

Until the last reader moves to the registry, the env files `HOME/.local/share/superloop-tools/loops.d/NAME.env` stay for the readers not yet moved; the entry reads none of them, and `verify` compares its loop's file with the row.

Ordinary entry and `provision` resolve Podman through nonempty `ENTER_LOOP_PODMAN`, then `podman` on `PATH`, then `flatpak-spawn --host podman`; `verify` searches `/usr/bin`, `/bin` and `/usr/local/bin` for an executable Podman, then for an executable `flatpak-spawn` with `--host /usr/bin/podman`, and reports status 1 before root inspection with the searched routes named when neither is usable. It accepts a linked system program when every checked link and every holding directory and the final executable report uid 0 in the verifier's user namespace, the directories and final executable have no group or other write bit, and the final file has an execute bit; it then executes the original fixed candidate path. These checks do not establish ownership outside that user namespace or pin the chain against changes by its uid 0. An inspection failure and its reason follow the no-route message, even when an ancestor prevents determining whether the candidate itself exists.

Each `verify` child starts with a cleared environment containing only fixed system `PATH`, the validated caller `HOME` for rootless Podman, the selected `ENTER_LOOP_REGISTRY` when present, and the effective account's `/run/user/UID` as `XDG_RUNTIME_DIR` and the session-bus address for the host route; caller loader, shell-startup and tool override variables are not forwarded.

The grant reader takes no lock when `letters_gid` is present. Only the absent-grant writer takes the existing configuration-root exclusive lock and the current ledger-file exclusive lock, re-reads and verifies the named inode under those locks, and publishes the updated ledger while preserving worker blocks.

A ledger and home written before this commit gain `letters_gid` and the inbox root at the next ordinary entry or `provision`, after which every ledger reader built before this commit refuses the ledger by the name `letters_gid` and every assembled worker row's ledger digest is stale until assembly runs again. Rebuild and deploy the entry, `superloop-lane`, the permission-triage hook and assembler, and `run-worker` together before any new entry runs; announce that transition, provision each home, then assemble the worker rows again. There is one ledger shape, with no alternate representation for older readers. `ENTER_LOOP_REGISTRY` is forwarded into the preparing and verification namespace so those helpers use the selected registry.

## Entry composition · `sec:loophome:entry-composition`

Ordinary entry and `driver-launch` use one `podman unshare sh -c OUTER-SCRIPT`. At composition as the owner, the entry derives the loop home and custody tier from the selected registry row and caller's `HOME`; a nondirectory custody tier refuses with status 2 before podman. After `set -e` and the `h` assignment, the outer script calls the resolved entry executable as `ensure-roots UID NAME HOME REPORT`, then selects `private/` when present, creates temporary passwd, group and empty SSH configuration files outside the home, enters a nested mount namespace, binds those files, drops to the loop uid, and runs the command. `provision` runs only the ensure step. `verify` uses the same entry composition only after read-only inspection proves the home needs no preparation, and its outer script omits `ensure-roots`.

The inner script reads `t=$1` and `h=$2`. With custody, its next line runs the entry's resolved executable as `bind-custody UID LOOP_HOME "$h" TIER` before the three `/etc` binds; without custody that line is absent. The step opens the registry home and tier by path, opens `private` when entered, `.config/custody`, `.ssh` and the tier's `ssh` beneath descriptors with `openat2`, `RESOLVE_NO_SYMLINKS` and `RESOLVE_BENEATH`, opens every descriptor before checking any, checks each with `fstat` for a directory owned by the loop UID, then binds both sources and targets through `/proc/self/fd/N`. A failed open, check or mount writes one path and reason and returns status 1 before the `/etc` binds. The script then binds the temporary passwd, group and empty SSH configuration directory over `/etc/passwd`, `/etc/group` and `/etc/ssh/ssh_config.d`. Without custody, it tests the entered home's `.config/gpg-loops/NAME` as a directory, adds `GNUPGHOME` to the clean environment only when present, and performs no privileged action on that path. Ordinary entry executes `setpriv --reuid=UID --regid=UID --clear-groups env -i`; `driver-launch` also selects the loop UID; the separate helper retains rootless image-store authority. Both use the clean variables below before the caller's command. With custody, the command they execute runs through a fixed `/bin/sh -c` forge check under the loop UID, which exits 1 naming `forge-config-inaccessible`, `forge-config-absent` or `forge-config-not-directory` and `superloop provision LOOP` instead of executing it unless the bound `.config/custody` is searchable and `GH_CONFIG_DIR` is a directory the loop UID can read, write and search.

|Variable|Value|
|--------|-----|
|`HOME`|`CALLER/.var/loops/NAME/private`, `CALLER` being the caller's `HOME`, a directory the ensure step keeps present.|
|`USER`, `LOGNAME`|The loop name.|
|`SHELL`|`/bin/bash`.|
|`PATH`|`HOME/.local/bin:/usr/local/bin:/usr/bin:/bin:ENTRY_BIN_DIR`, where `ENTRY_BIN_DIR` is the deployed entry executable’s directory.|
|`TERM`|The caller's value, or `xterm` when absent.|
|`LANG`|The caller's value, or `C.UTF-8` when absent.|
|`TMPDIR`|`CALLER/.cache/loops/NAME/tmp`, the one row the ensure step creates inside the loop's transient partition.|
|`XDG_RUNTIME_DIR`|`HOME/.run`.|
|`XDG_CONFIG_HOME`|`HOME/.config`.|
|`XDG_CACHE_HOME`|`CALLER/.cache/loops/NAME`, the loop's transient partition.|
|`XDG_DATA_HOME`|`HOME/.local/share`.|
|`XDG_STATE_HOME`|`HOME/.local/state`.|
|`GNUPGHOME`|`HOME/.config/custody/gpg` with a custody tier; otherwise `HOME/.config/gpg-loops/NAME` when that directory exists; unset otherwise.|
|`GH_CONFIG_DIR`|`HOME/.config/custody/gh`, present only with a custody tier.|

A tiered loop home holds its clone, memory and keys under `private/`, so ordinary entry resolves its `HOME` there; the ensure step keeps that tier present. `verify` uses the same resolution only for a complete home, and skips entry when the ensure step would create, correct or refuse a row.

Every substituted value and command word is shell-quoted across both layers.

Command words are forwarded byte for byte: words with unsafe bytes use single-quoted literals because backslash-newline is a line continuation in `sh`.

## Provisioning · `sec:loophome:provisioning`

`provision NAME` runs the ensure step alone: one `podman unshare sh -c` whose script runs `ensure-roots UID NAME HOME REPORT` and nothing else, with no entry and no command run as the loop. It creates every missing standard root, corrects every differing mode, succeeds on a complete home with zero rows created, and refuses any home row the ensure rules reject. It is the form a registration or an owner-run chain uses to prepare a loop's roots before anything runs as the loop.

## Standard roots and the ensure step · `sec:loophome:standard-roots-and-ensure-step`

The standard roots are the rows of the estate layout's loop roots table, ``tab:estatelayout:loop-roots``, carried here by citation: the durable root `HOME/.var/loops/NAME` with `private/`, `shared/`, `src/`, `direct/`, `policy/` and `runs/`; beneath `private/`, the entry's XDG directories `.run`, `.config`, `.local`, `.local/bin`, `.local/share` and `.local/state` and the two custody bind targets `.config/custody` and `.ssh`; the custody root `HOME/.config/loops/NAME` with `lanes/` and `lanes/keys/`; and the cache partition `HOME/.cache/loops/NAME`, the entry's `XDG_CACHE_HOME`, with its `tmp/`, the entry's `TMPDIR`; each beneath the owner-owned partitions `HOME/.var/loops`, `HOME/.config/loops` and `HOME/.cache/loops`, `HOME` being the caller's. Every row derives from the caller's `HOME`, the name and the row's `uid`, and the table's owner, mode and ensure columns are the specification the step's tests pin row for row. The private-home `.config/custody` is only a bind target; provisioning creates the loop-owned mode-0700 `gh` child of an existing custody tier, preserves its contents, and never creates an absent tier.

`ensure-roots UID NAME HOME REPORT` accepts a decimal UID in 1000 through 65535, a valid loop name and absolute UTF-8 home and report paths; malformed arguments refuse with status 2. Preparation and verification walk the table separately and use one pure decision for each observed row's kind, uid, gid and mode. Before making any change, ensure refuses a wrong owner or group, a nondirectory or link, a checked class root without search permission for others, or a populated loop root without `private/`; it then creates missing required rows and corrects differing modes, while the optional custody tier is only checked when present. `verify` inspects without an action phase and writes no file in the named loop home.

Each row actually created or corrected by ordinary entry or `provision` appends `created PATH MODE` or `corrected PATH OLD NEW`, followed on success by `wall MICROS`, to a temporary report outside the loop home. `verify` puts its small temporary inspection report under fixed `/tmp` regardless of the caller's `TMPDIR`, removes it before returning, and writes no report or lock in the named home; its `roots` array contains the table rows plus the caller's `.config` class root, and its `would_create` and `would_correct` counts describe per-row actions after any refusals are resolved, since ensure stops at its first refusal.

## Verification and reports · `sec:loophome:verification-and-reports`

`verify NAME` accepts any registered loop name and leaves entry content, names, kinds, modes, owners, groups, modification times and change times unchanged, including on failure. It prints compact JSON with `roots` entries carrying `path`, `kind`, observed `uid`, `gid`, `mode`, `action`, `atime_may_have_changed` and a refusal or unseen reason when applicable, plus `would_create` and `would_correct`. If the home is as ensured, `probe.made` is true and the report also has entered `user`, `uid`, `home`, sorted `env`, `mounts_left` and `tmp_left`, owner-read `account_uid` and `registry_drift`, optional declared `runs_root`. If entry would require preparation or refuse, `probe.made` is false with a reason; entered fields are null, while the inspected roots and owner-read fields remain visible. The probe uses fixed system programs and NUL-framed fields and does not inspect the checkout with Git, so checkout configuration cannot launch a program or supply a warning. When `O_NOATIME` is refused, `verify` opens the readable loop root normally and marks that row `atime_may_have_changed`; its access time may also move on a filesystem that ignores `O_NOATIME`. A present account UID differing from the registry still ends with status 1 and a named diagnostic; drift alone does not change status.

After a complete home's inner probe returns, a fixed-path cleanup probe counts remaining binds at the passwd, group, SSH configuration and custody targets and temporary entry directories. The report distinguishes unavailable inner fields from zero counts when entry was skipped.

Ordinary entry, bridges, `driver-launch` and `provision` retain their byte-for-byte standard-error line `ENTER-REPORT loop=NAME uid=UID exit=STATUS wall=S.Ss created=N corrected=M`, or the existing `--json` equivalent with `created` and `corrected`. When the entry forwards a terminating signal, or its child ends by one, the line appends `signal=NAME` and `--json` adds `signal`, with `exit` at 128 plus the signal number. After `verify` creates its temporary report, it uses `ENTER-REPORT loop=NAME uid=UID exit=STATUS wall=S.Ss would_create=N would_correct=M`, or `--json` fields `would_create` and `would_correct`; counts are `null` if root inspection fails before observing them. A missing container route returns its diagnostic before report creation and therefore has no `ENTER-REPORT` line. `registry` writes no report line.

|Status|`verify` meaning|
|------|--------|
|0|Home is as ensured; the inner probe ran.|
|1|An existing runtime, filesystem, probe or publication failure; no complete report can be trusted.|
|2|An existing command-line, registry or pre-entry grammar refusal.|
|3|At least one row would be created or corrected; the inner probe was skipped.|
|4|At least one home row would be refused; this outranks status 3, and both kinds of decision remain in the report.|

Statuses 1 and 2 retain their existing failure meanings and preempt a home-state result; among observed home decisions the severity order is 4, then 3, then 0.

## Measured boundary reasons and canaries · `sec:loophome:boundary-reasons-and-canaries`

The clean environment exists because caller XDG paths leaked into the first real entry and made Git warn on every command. The temporary passwd entry exists because an unmapped subordinate UID had no passwd name and SSH exited immediately. The empty bind-mounted `ssh_config.d` exists because SSH refused root-owned configuration fragments as unowned inside the namespace. The nested mount namespace exists because a mount made directly under `podman unshare` persisted in podman's rootless namespace.

Custody uses binds because the owner's `~/.config` stays mode 0700: making it traversable would expose permissively readable owner configuration to subordinate UIDs. Custody is visible only inside an entry because both ends of each bind are pinned to checked descriptors, so a loop process cannot redirect either bind by replacing a path, not because the entry is namespace root: namespace root in the entry's nested mount namespace only lets the entry mount, and the binds vanish with that namespace. OpenSSH reads the entered home's passwd-resolved `.ssh` through the bind.

The two crossing signatures are greppable in any transcript: an entry naming an id that is not the calling loop's own registry id, and a bare `podman unshare` without `setpriv --reuid`, which is namespace root and reads every home.
