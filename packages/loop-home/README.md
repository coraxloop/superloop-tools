# `loop-home` · `guide:loophome:loop-home`

`loop-home` is the internal home and entry-planning library behind `superloop`, using the standard library, `nix` for safe descriptor and mount calls, and `toml` for the registry. Pure planners turn a validated registry record and arguments into exact argv, while an injected `Runner` owns every external command so unit tests never invoke podman.

## Command line · `sec:loophome:command-line`

```text
superloop [--json] enter NAME [--] COMMAND [ARG...]
superloop driver-launch --interface-version
superloop driver-launch LOOP RUN --driver-bin PATH --run-dir DIR --backend {codex|claude} -- ARGS...
superloop [--json] provision NAME
superloop [--json] run-bridge gpg NAME [--] [GPG-ARG...]
superloop [--json] run-bridge ssh NAME [--] [SSH-ARG...]
superloop [--json] verify NAME
superloop show NAME
```

`ENTER_LOOP_REGISTRY` names the registry file and defaults to `HOME/.config/loops/registry.toml`. Every entry needs the caller's nonempty UTF-8 `HOME` to derive the loop's roots and custody, so an unset, empty or non-UTF-8 value is refused by name with status 2 even with a registry override.

For the ordinary `superloop enter NAME -- COMMAND [ARG...]` form, the entry returns the command's exit status when it runs, or status 2 when it refuses before any command runs.

`show NAME` prints the loop's validated identity row as one compact JSON object on standard output, with key-sorted fields, `launch` joined to the caller's `HOME`, absent `session` as null, and declared `runs_root` as its JSON value. It accepts no `--json`, calls no podman, runs no ensure step and writes no report line, so a reader in another language takes the row from the entry's own validation rather than parsing the registry. A binary reached through a `NAME-gpg` or `NAME-ssh` generated copy dispatches directly to that bridge, with the remaining arguments passed through.

The `GnuPG` bridge enters the loop to execute fixed `/usr/bin/gpg`; the entry selects `GNUPGHOME` at the entered home's `.config/custody/gpg` with a custody tier, or at its `.config/gpg-loops/NAME` without a tier when that directory exists, and otherwise leaves it unset. The SSH bridge enters the loop to execute `ssh`; both bridges preserve the caller's standard input, output, error, and argument words unchanged. The absolute `GnuPG` path prevents a program under the loop's `HOME/.local/bin`, first on `PATH`, from replacing the signer.

`bind-custody UID LOOP_HOME ENTERED TIER` is the entry binary's private bind step, `ensure-roots UID NAME HOME REPORT` is its preparing step, and `inspect-roots UID NAME HOME REPORT` is its read-only root inspection step; none is a caller command.

## Driver launch · `sec:loophome:driver-launch`

`superloop driver-launch LOOP RUN --driver-bin PATH --run-dir DIR --backend {codex|claude} -- ARGS...` starts the configured driver as the loop UID with the entry's clean environment, adding the validated `driver_argv` and `backend_argv` selectors and source evidence as `LANE_DRIVER_ARGV`, `LANE_BACKEND_ARGV` and `LANE_SETTINGS_EVIDENCE`, `LANE_BOXED_RUNTIME=1` for the fixed run-directory client protocol, and distinct `LANE_RUNS_ROOT` and `LANE_RUN_DIR` values for the configured durable root and selected run container. The loop UID can reach its home and mode-0700 run directory; the separate namespace-owner helper validates the saved container request against a protected reservation and reaches the rootless image store, while the worker inside the box uses its allocated UID. The private backend is mandatory and validates only its own `backend_argv` key, with no default or cross-vendor fallback. The configured `driver_argv` must contain exactly one explicit `--backend` followed by `codex` or `claude`; entry replaces that value in the executed vector with the protected launch selection. The settings evidence and environment retain the original configured vectors. Install matching lane and entry versions together and check that driver selector before deployment. `ARGS...` is nonempty and follows the fixed arguments from `driver_argv` as exact positional words through `"$@"`, without shell parsing of those words; the entry returns the child's exit status. Its standard input, output and error are inherited, so the caller captures output and error through pipes outside the run directory; the entry writes neither stream to that directory.

The form requires `driver_argv`, the `backend_argv` key its `--backend` names and `runs_root` from `HOME/.config/loops/LOOP/workers.toml` and requires the loop's block in `HOME/.config/loops/allocations.toml`; a prior `box.toml` is named in the missing-file refusal and is never read as a fallback. The settings directory is owner-owned at mode 0700 and the regular file is owner-owned at mode 0600; the file opens without following a link and is limited to 65536 bytes. Ordinary `enter` also transports selectors when the loop has a workers settings file, allowing a host driver invocation to receive the same validated values; entries without workers settings retain their ordinary command environment. Both the configured driver path and `PATH` must be absolute and equal, and the driver must exist as a regular executable file. `DIR` must be exactly `runs_root/RUN`; the required workers setting must match the registry grant. An absent setting refuses with `runs_root_required`, even if the registry declares a root. The entry opens the durable root and run directory component by component through pinned descriptors without following links, and refuses an ancestor another identity could replace. A declared root is owned by the invoking owner and group at mode 0711, matching the standard runs root; its run directories are loop-owned and written from outside the worker. `DIR` is not added to the driver's argv and is not selected as its working directory; the caller supplies the same path through the driver's own arguments when the driver needs it. A run name is 1 to 64 bytes of ASCII letters, digits, `-`, `_` or `.`, opening with a letter or digit.

Status 2 and one standard-error line refuse an unregistered loop, invalid run name, missing, unreadable or malformed settings, a linked or nonregular settings file, missing or malformed `driver_argv` or selected `backend_argv` key, a missing or unknown `--backend`, a `driver_argv` without exactly one `--backend` selector naming `codex` or `claude`, a relative or mismatched `PATH`, a missing or nonexecutable driver, a run directory outside the loop's durable runs root, a declared root with the wrong owner, group or mode, a linked, nondirectory or replaceable path component, a missing `--`, or an empty argument vector; none launches the driver. The entry holds the opened root and run directory until dispatch returns, but the driver still receives a path in its own arguments, leaving a path substitution window for an identity able to rename an owner-controlled ancestor. This form validates the run path and executes the configured driver; `superloop-lane launch` creates the run and home, allocates the worker UID, pins the container invocation and records evidence outside the worker home.

## Registry and refusals · `sec:loophome:registry-and-refusals`

Status 2 identifies a refusal. Before podman is called, the tool reads and validates the whole registry and refuses invalid names, unknown loops, an unreadable or malformed TOML registry, a wrong namespace or major version, an unknown key at any level, a missing or malformed name, `uid`, `launch` or `session`, a malformed or invalid `runs_root`, a UID outside 1000–65535, duplicate names or UIDs, an absolute or dotted `launch`, an empty `session`, absent entry commands, invalid command-line forms, a nondirectory custody tier, and an unset, empty or non-UTF-8 `HOME`. Commands that require workers also refuse an absent or invalid allocation ledger, a missing loop table, an out-of-range block or overlapping blocks. Unavailable Podman resolution for ordinary entry, bridges, `driver-launch` or `provision` also refuses with status 2; `verify` reports an unavailable fixed route with status 1. Every such pre-entry failure writes one diagnostic line to standard error.

The ensure step's refusals, a standard root owned by another uid or gid, anything but a directory at a standard root, and a loop root holding entries without `private/`, also use status 2, change nothing, and end the entry before any mount. Runtime process, filesystem, probe, or publication failures use status 1.

Until the last reader moves to the registry, the env files `HOME/.local/share/superloop-tools/loops.d/NAME.env` stay for the readers not yet moved; the entry reads none of them, and `verify` compares its loop's file with the row.

Ordinary entry and `provision` resolve Podman through nonempty `ENTER_LOOP_PODMAN`, then `podman` on `PATH`, then `flatpak-spawn --host podman`; `verify` searches `/usr/bin`, `/bin` and `/usr/local/bin` for an executable Podman, then for an executable `flatpak-spawn` with `--host /usr/bin/podman`, and reports status 1 before root inspection with the searched routes named when neither is usable. It accepts a linked system program when every checked link and every holding directory and the final executable report uid 0 in the verifier's user namespace, the directories and final executable have no group or other write bit, and the final file has an execute bit; it then executes the original fixed candidate path. These checks do not establish ownership outside that user namespace or pin the chain against changes by its uid 0. An inspection failure and its reason follow the no-route message, even when an ancestor prevents determining whether the candidate itself exists.

Each `verify` child starts with a cleared environment containing only fixed system `PATH`, the validated caller `HOME` for rootless Podman, the selected `ENTER_LOOP_REGISTRY` when present, and the effective account's `/run/user/UID` as `XDG_RUNTIME_DIR` and the session-bus address for the host route; caller loader, shell-startup and tool override variables are not forwarded.

The registry is the file `ENTER_LOOP_REGISTRY` names, defaulting to `HOME/.config/loops/registry.toml`, an owner-owned file at mode 0600 inside the owner's custody root, and it is the registry of record for the entry and `run-worker`. Its first lines are `namespace = "org.superloop-tools.loophome.registry"` and `version = [1, 0, 0]`, followed by one array `loops` of inline tables, one row per loop, with the keys `name`, `uid`, `launch`, optional `runs_root` and optional `session`, and no other keys at any level. The major version must be 1; higher minor and patch versions are accepted. `uid` is an integer from 1000 through 65535 and the uid of record; `launch` is the launch directory as a path relative to the caller's `HOME` without `.` or `..` components; `runs_root` is the absolute root of the loop's durable driver directories, kept in its supplied spelling without a `.` or `..` component and allowed anywhere the owner names; `session` is a nonempty string. No row carries its home: the loop home is `HOME/.var/loops/NAME`, derived like every standard root from the caller's `HOME`, the name and `uid`. Every read validates the whole file before selecting a row.

The tools write worker ranges to `HOME/.config/loops/allocations.toml`, beside the registry: one table per loop, `[LOOP]` followed by `uids = { base = BASE, count = COUNT }`. The block is an inclusive run within 1000 through 65535 with `COUNT` at least one and must not contain namespace uid 65534; all tables are validated before selection, overlapping runs are refused, and a missing table grants no worker. The reader opens the owner-owned mode-0600 regular file through a pinned path beneath the owner-owned mode-0700 directory and refuses more than 65536 bytes. The person writes the registry's identity fields; backend vectors, vendor hosts, image and resources belong to the loop's `workers.toml`, while the tools own the allocation ledger.

Mail uses the actor's five directories and ordinary filesystem tools. The entry has no letters dispatcher, private letters helper, metadata parser or metadata follow interface. ## Entry composition · `sec:loophome:entry-composition`

Ordinary entry and `driver-launch` use one `podman unshare sh -c OUTER-SCRIPT`. At composition as the owner, the entry derives the loop home and custody tier from the selected registry row and caller's `HOME`; a nondirectory custody tier refuses with status 2 before podman. After `set -e` and the `h` assignment, the outer script calls the resolved entry executable as `ensure-roots UID NAME HOME REPORT`, then selects `private/` when present, creates temporary passwd, group and empty SSH configuration files outside the home, enters a nested mount namespace, binds those files, drops to the loop uid, and runs the command. `provision` runs only the ensure step. `verify` uses the same entry composition only after read-only inspection proves the home needs no preparation, and its outer script omits `ensure-roots`.

The inner script reads `t=$1` and `h=$2`. With custody, its next line runs the entry's resolved executable as `bind-custody UID LOOP_HOME "$h" TIER` before the three `/etc` binds; without custody that line is absent. The step opens the registry home and tier by path, opens `private` when entered, `.config/custody`, `.ssh` and the tier's `ssh` beneath descriptors with `openat2`, `RESOLVE_NO_SYMLINKS` and `RESOLVE_BENEATH`, opens every descriptor before checking any, checks each with `fstat` for a directory owned by the loop UID, then binds both sources and targets through `/proc/self/fd/N`. A failed open, check or mount writes one path and reason and returns status 1 before the `/etc` binds. The script then binds the temporary passwd, group and empty SSH configuration directory over `/etc/passwd`, `/etc/group` and `/etc/ssh/ssh_config.d`. Without custody, it tests the entered home's `.config/gpg-loops/NAME` as a directory, adds `GNUPGHOME` to the clean environment only when present, and performs no privileged action on that path. Ordinary entry executes `setpriv --reuid=UID --regid=UID --clear-groups env -i`; `driver-launch` also selects the loop UID; the separate helper retains rootless image-store authority. Both use the clean variables below before the caller's command. With custody, the command they execute runs through a fixed `/bin/sh -c` forge check under the loop UID, which exits 1 naming `forge-config-inaccessible`, `forge-config-absent` or `forge-config-not-directory` and `superloop provision LOOP` instead of executing it unless the bound `.config/custody` is searchable and `GH_CONFIG_DIR` is a directory the loop UID can read, write and search.

|Variable|Value|
|--------|-----|
|`HOME`|`CALLER/.var/loops/NAME/private`, `CALLER` being the caller's `HOME`, a directory the ensure step keeps present.|
|`USER`, `LOGNAME`|The loop name.|
|`SHELL`|`/bin/bash`.|
|`PATH`|`HOME/.local/bin:/usr/local/bin:/usr/bin:/bin:ENTRY_BIN_DIR`, where `ENTRY_BIN_DIR` is the deployed entry executable’s directory.|
|`TERM`|The caller's value, or `xterm` when absent.|
|`LANG`|The caller's value, or `C.UTF-8` when absent.|
|`TMPDIR`|`CALLER/.cache/loops/NAME/tmp`, the one row the ensure step creates inside the loop's transient partition.|
|`XDG_RUNTIME_DIR`|`HOME/.run`.|
|`XDG_CONFIG_HOME`|`HOME/.config`.|
|`XDG_CACHE_HOME`|`CALLER/.cache/loops/NAME`, the loop's transient partition.|
|`XDG_DATA_HOME`|`HOME/.local/share`.|
|`XDG_STATE_HOME`|`HOME/.local/state`.|
|`GNUPGHOME`|`HOME/.config/custody/gpg` with a custody tier; otherwise `HOME/.config/gpg-loops/NAME` when that directory exists; unset otherwise.|
|`GH_CONFIG_DIR`|`HOME/.config/custody/gh`, present only with a custody tier.|

A tiered loop home holds its clone, memory and keys under `private/`, so ordinary entry resolves its `HOME` there; the ensure step keeps that tier present. `verify` uses the same resolution only for a complete home, and skips entry when the ensure step would create, correct or refuse a row.

Every substituted value and command word is shell-quoted across both layers.

Command words are forwarded byte for byte: words with unsafe bytes use single-quoted literals because backslash-newline is a line continuation in `sh`.

## Provisioning · `sec:loophome:provisioning`

`provision NAME` runs the ensure step alone: one `podman unshare sh -c` whose script runs `ensure-roots UID NAME HOME REPORT` and nothing else, with no entry and no command run as the loop. It creates every missing standard root, corrects every differing mode, succeeds on a complete home with zero rows created, and refuses any home row the ensure rules reject. It is the form a registration or an owner-run chain uses to prepare a loop's roots before anything runs as the loop.

## Standard roots and the ensure step · `sec:loophome:standard-roots-and-ensure-step`

The standard roots are the rows of the public loop roots table (`[TOOLS-tab:workercontracts:loop-roots]`): the durable root `HOME/.var/loops/NAME` with `private/`, `shared/`, `src/`, `direct/`, `policy/` and `runs/`; beneath `private/`, the entry's XDG directories `.run`, `.config`, `.local`, `.local/bin`, `.local/share` and `.local/state` and the two custody bind targets `.config/custody` and `.ssh`; the custody root `HOME/.config/loops/NAME` with `lanes/` and `lanes/keys/`; and the cache partition `HOME/.cache/loops/NAME`, the entry's `XDG_CACHE_HOME`, with its `tmp/`, the entry's `TMPDIR`; each beneath the owner-owned partitions `HOME/.var/loops`, `HOME/.config/loops` and `HOME/.cache/loops`, `HOME` being the caller's. Every row derives from the caller's `HOME`, the name and the row's `uid`, and the table's owner, mode and ensure columns are the specification the step's tests pin row for row. The private-home `.config/custody` is only a bind target; provisioning creates the loop-owned mode-0700 `gh` child of an existing custody tier, preserves its contents, and never creates an absent tier.

`ensure-roots UID NAME HOME REPORT` accepts a decimal UID in 1000 through 65535, a valid loop name and absolute UTF-8 home and report paths; malformed arguments refuse with status 2. Preparation and verification walk the table separately and use one pure decision for each observed row's kind, uid, gid and mode. Before making any change, ensure refuses a wrong owner or group, a nondirectory or link, a checked class root without search permission for others, or a populated loop root without `private/`; it then creates missing required rows and corrects differing modes, while the optional custody tier is only checked when present. `verify` inspects without an action phase and writes no file in the named loop home.

Each row actually created or corrected by ordinary entry or `provision` appends `created PATH MODE` or `corrected PATH OLD NEW`, followed on success by `wall MICROS`, to a temporary report outside the loop home. `verify` puts its small temporary inspection report under fixed `/tmp` regardless of the caller's `TMPDIR`, removes it before returning, and writes no report or lock in the named home; its `roots` array contains the table rows plus the caller's `.config` class root, and its `would_create` and `would_correct` counts describe per-row actions after any refusals are resolved, since ensure stops at its first refusal.

## Verification and reports · `sec:loophome:verification-and-reports`

`verify NAME` accepts any registered loop name and leaves entry content, names, kinds, modes, owners, groups, modification times and change times unchanged, including on failure. It prints compact JSON with `roots` entries carrying `path`, `kind`, observed `uid`, `gid`, `mode`, `action`, `atime_may_have_changed` and a refusal or unseen reason when applicable, plus `would_create` and `would_correct`. If the home is as ensured, `probe.made` is true and the report also has entered `user`, `uid`, `home`, sorted `env`, `mounts_left` and `tmp_left`, owner-read `account_uid` and `registry_drift`, optional declared `runs_root`. If entry would require preparation or refuse, `probe.made` is false with a reason; entered fields are null, while the inspected roots and owner-read fields remain visible. The probe uses fixed system programs and NUL-framed fields and does not inspect the checkout with Git, so checkout configuration cannot launch a program or supply a warning. When `O_NOATIME` is refused, `verify` opens the readable loop root normally and marks that row `atime_may_have_changed`; its access time may also move on a filesystem that ignores `O_NOATIME`. A present account UID differing from the registry still ends with status 1 and a named diagnostic; drift alone does not change status.

After a complete home's inner probe returns, a fixed-path cleanup probe counts remaining binds at the passwd, group, SSH configuration and custody targets and temporary entry directories. The report distinguishes unavailable inner fields from zero counts when entry was skipped.

Ordinary entry, bridges, `driver-launch` and `provision` retain their byte-for-byte standard-error line `ENTER-REPORT loop=NAME uid=UID exit=STATUS wall=S.Ss created=N corrected=M`, or the existing `--json` equivalent with `created` and `corrected`. When the entry forwards a terminating signal, or its child ends by one, the line appends `signal=NAME` and `--json` adds `signal`, with `exit` at 128 plus the signal number. After `verify` creates its temporary report, it uses `ENTER-REPORT loop=NAME uid=UID exit=STATUS wall=S.Ss would_create=N would_correct=M`, or `--json` fields `would_create` and `would_correct`; counts are `null` if root inspection fails before observing them. A missing container route returns its diagnostic before report creation and therefore has no `ENTER-REPORT` line. `registry` writes no report line.

|Status|`verify` meaning|
|------|--------|
|0|Home is as ensured; the inner probe ran.|
|1|An existing runtime, filesystem, probe or publication failure; no complete report can be trusted.|
|2|An existing command-line, registry or pre-entry grammar refusal.|
|3|At least one row would be created or corrected; the inner probe was skipped.|
|4|At least one home row would be refused; this outranks status 3, and both kinds of decision remain in the report.|

Statuses 1 and 2 retain their existing failure meanings and preempt a home-state result; among observed home decisions the severity order is 4, then 3, then 0.

## Measured boundary reasons and canaries · `sec:loophome:boundary-reasons-and-canaries`

The clean environment exists because caller XDG paths leaked into the first real entry and made Git warn on every command. The temporary passwd entry exists because an unmapped subordinate UID had no passwd name and SSH exited immediately. The empty bind-mounted `ssh_config.d` exists because SSH refused root-owned configuration fragments as unowned inside the namespace. The nested mount namespace exists because a mount made directly under `podman unshare` persisted in podman's rootless namespace.

Custody uses binds because the owner's `~/.config` stays mode 0700: making it traversable would expose permissively readable owner configuration to subordinate UIDs. Custody is visible only inside an entry because both ends of each bind are pinned to checked descriptors, so a loop process cannot redirect either bind by replacing a path, not because the entry is namespace root: namespace root in the entry's nested mount namespace only lets the entry mount, and the binds vanish with that namespace. OpenSSH reads the entered home's passwd-resolved `.ssh` through the bind.

The two crossing signatures are greppable in any transcript: an entry naming an id that is not the calling loop's own registry id, and a bare `podman unshare` without `setpriv --reuid`, which is namespace root and reads every home.

**Protocol (Change-driven service wakeup)** · `proto:loophome:mail-change-wakeup`

The service arms inotify on verified outboxes, inboxes, mailbox parents, worker-discovery roots and current authorization files before enumerating candidates, then sleeps in the kernel until a change or a retry, fallback or existing one-hour retention deadline; a watch retains no mailbox descriptor, and scan descriptors close before the wait. Events supply hints only: ordinary scheduling lists the named outboxes together with senders with due retry work, preserving finite per-sender slug/recipient ordering and sender round-robin. Fresh scheduling and admission inventories, current authorization, endpoint custody checks and journal/publication ordering remain. Overflow, invalidated watches and re-registration onto a replaced inode force reconciliation before admission. Scan starts are separated by at least 250 ms, including wakes caused by restoration of a letter refused after its claim; an event storm cannot bypass that floor. An exact protected refusal-sidecar binding identifies sidecar events; a suffix alone suppresses nothing. Unchanged refused-source events follow the identity gate below.

Full recovery shares its validated pending-delivery set across mailbox refusal maintenance, avoiding a retained-history reread per mailbox; the existing exclusive journal writer lock excludes another writer, and one sender's maintenance cannot create another sender's pending record. Corruption still refuses the recovery pass. Retention runs at startup, before capacity admission and at its deadline, rather than at every idle wakeup, and checks each retained record's exact inbox name instead of enumerating unrelated inbox history. Startup, overflow and configuration reconciliation retain whole scheduling/recovery walks; incomplete notification coverage retains the documented five-second fallback. The hourly retention deadline performs its required inventory and pruning, clears refused-source observations and enumerates those remembered senders once, bounding an otherwise invisible withdraw-and-resubmit to an hour; it also discovers newly verifiable endpoints for configuration reconciliation. Its watch-repair deadline is independent of admission pruning, so event traffic cannot keep postponing repair. Ordinary selected scans do not read recovery history or list unrelated outboxes; inbox content events and disappeared successful sources do not trigger scheduling. Whole authorization inventories, finite sorting within selected outboxes, pre-admission history validation and aggregate staging/accounting still remain: this is not a population-independent delivery claim. Targeted sender/recipient resolution is the next implementation cut; pending/refusal indexes and capacity counters remain subject to the proposal’s retention decision. Pending letters, and refused letters whose refusal can clear without any watched change (an unavailable endpoint or other I/O failure, service capacity, a changed source, absent or unreadable configuration), have their own deadline queue: retries wait 1, 2, 4, 8, 16 and then at most 30 seconds after successive failed timed attempts, with at most 64 due keys selected in one batch. A refusal that only the sender's own edit or a watched authorization change can repair (name, file kind, size, recipient, retirement, estate, whitelist or storage custody) joins no queue, because that change wakes the scan that retries the letter and a timer would only repeat the refusal. Each bounded due batch retains the ordinary sender round-robin and per-sender slug/recipient order. Repeated events do not postpone a key’s existing deadline. Success or withdrawal removes its retry, and restart reconstructs obligations through the ordinary recovery/scan. Accepted retries reconcile any surviving preparation intent through the normal recovery checks before finishing publication. The first retry stays prompt for transient failures; at the ceiling, each letter waits at least 30 seconds between failed timed attempts. The retry clock selects only known unfinished keys and does not enumerate sender outboxes; each attempt retains the existing fresh inventory, authorization, retention and aggregate-capacity checks. Those existing per-attempt costs remain part of the next-stage work. An unavailable endpoint or absent private configuration cannot always be watched, but a known letter’s retry no longer waits for another event or the hourly pass. The generic proposal ``docs/proposals/mail-change-driven-delivery.md`` separates those remaining costs and their required specification decisions.

An optional hint path’s registration failure is advisory, like its open failure. An outbox or inbox registration failure other than a quota condition is reported as that mailbox’s inventory failure; unrelated senders continue. An unavailable inotify instance, a quota failure or incomplete watch coverage enables a five-second periodic full scan with the same delivery checks, both at startup and while running. Existing working watches still wake the service. The service retries registration on these scans and returns to notification-only waiting when coverage is restored or an uncovered path is no longer requested; there is no compatibility switch. The fallback is deliberately a bounded safety mechanism, not a claim of population-independent work.

The protected refusal binding is keyed by sender and exact source-name bytes; its inode and digest authenticate the reason sidecar, not the source. This narrows the generic ``rule:mail:refusal`` wording “retried on the next scan” to a source or configuration change, a due transient retry, or hourly reconsideration. The amendment proposed by ``docs/proposals/mail-change-driven-delivery.md`` remains a generic-owner action; this implementation records the explicit scheduling exception here. The scheduler separately remembers the failed source’s device, inode, size, link count, owner, group, mode and modification time (including nanoseconds) in memory, without holding a descriptor. An unchanged refused source is attempted again only after a configuration change, its retry deadline or hourly reconsideration; a change in any observed source field admits an immediate attempt. A restoring rename changes none of these fields; ctime is intentionally excluded. Hourly maintenance clears the observations and schedules the remembered senders once, bounding a missed same-name withdrawal/resubmission to that maintenance interval. Metadata failure never proves equality. Restart rebuilds these observations through ordinary recovery. Overflow invalidates them because it can hide a configuration change. An event scan that consumes a due source advances the same backoff, so the timer cannot immediately duplicate that attempt. Each admitted attempt retains fresh directory, authorization, custody and journal checks. Withdrawal schedules cleanup of the known source key through a freshly verified endpoint and the existing protected refusal remover; it does not trigger whole-history recovery. A successful claim records a retry obligation before any later fallible operation, so unavailable refusal classification cannot lose claimed work; retry distinguishes accepted publication from restoration through the existing journal checks. Selected scans also advance one bounded due batch, so continuous new submissions cannot starve claimed work.

**Procedure (Read the shared watch budget)** · `alg:loophome:mail-watch-budget`

The user unit shares ``fs.inotify.max_user_watches`` and ``fs.inotify.max_user_instances`` with the host owner’s session, including registrations charged through its subordinate namespace; ``fs.inotify.max_queued_events`` bounds each event queue. Exhaustion can affect startup or a running service. The service names ``inotify-watch-limit`` or ``inotify-instance-or-descriptor-limit`` and logs ``periodic scan fallback`` with its five-second interval, instead of reporting only the kernel’s misleading disk-space message or restarting every five seconds. An instance-limit message also names descriptor exhaustion because Linux uses EMFILE for both conditions. While fallback lasts, a reminder is emitted at most once per minute; removal of an uncovered path is reported even when other uncovered paths remain.

Read the limits, service diagnostics and visible per-process usage under the host owner; repeat the process census through ``podman unshare`` to read the service’s subordinate identities when ordinary procfs access is denied. Descriptor references are not unique instances: inherited or duplicated descriptors can count the same registration twice, and unreadable procfs entries make the census incomplete. The command reports those limitations rather than presenting an exact kernel-wide used count.

```sh
sysctl fs.inotify.max_user_watches fs.inotify.max_user_instances fs.inotify.max_queued_events
systemctl --user show superloop-mail.service -p MainPID -p LimitNOFILE
journalctl --user -u superloop-mail.service -n 100 --no-pager
python3 - <<'PYPROBE'
from pathlib import Path
references = watches = unreadable = 0
for process in Path('/proc').glob('[0-9]*'):
    try:
        descriptors = list((process / 'fd').iterdir())
    except OSError:
        unreadable += 1
        continue
    for descriptor in descriptors:
        try:
            if descriptor.readlink().as_posix() != 'anon_inode:inotify':
                continue
            rows = (process / 'fdinfo' / descriptor.name).read_text().splitlines()
            count = sum(row.startswith('inotify ') for row in rows)
            references += 1
            watches += count
            print('pid', process.name, 'fd', descriptor.name, 'watch_rows', count)
        except OSError:
            unreadable += 1
print('visible_descriptor_references', references, 'visible_watch_rows', watches,
      'unreadable_entries', unreadable, 'duplicates_possible', True)
PYPROBE
```

## Mail migration and rollback · `sec:loophome:mail-migration`

`superloop-mail migrate {prepare|apply|verify|rollback|reconcile} STATE PLAN` runs as namespace root under the held install-and-cutover operation. STATE is an existing root-owned directory at mode 0700, outside every source and retained deployment tree. PLAN is a root-owned, non-writable-by-group-or-world JSON deployment plan. No mode enables the service or resumes new mail: `verify` reports readiness for the loop's separate activation operation. A missing expected store, uncertain native run history, unaccounted execution tree or changed artifact refuses the transition.

The version-one plan names `home` and `deployment`. The deployment names digest-pinned `controller` and `native_lane` artifacts, `artifacts` with an installed `path` plus independently retained `current` and `previous` images, and two `retirements` records for entry and round retirement. Each retirement names its requirement, full revision, digest-pinned review and `installed_digest`, the SHA-256 of the ordered artifact array encoded as compact JSON. Every loop-home linker must be present. The native census image must be the reviewed current lane image. Retained images and reviews stay outside mutable installed paths through rollback review.

The controller is the reviewed estate adapter for sessions, watchers, remote workers and the previous deployment. It receives exactly `OPERATION HOME STATE`, a cleared environment with `HOME`, `PATH` and `LC_ALL`, no stdin, and writes one JSON object containing the matching `operation`, `home`, `state` and `complete: true`. Output and failures are retained in STATE. `hold` stops all old producers and readers and keeps the new service stopped. `verify-held` proves that persistent hold remains in force. `restore-state` restores only the manifest's backed-up legacy state and independently retained previous deployment, retaining all lifetime-vault objects and hold markers. `restore-processes` restarts the previous processes only after state and artifact verification. `verify-restored` measures that restored deployment and process state. `install-current` reinstalls the retained reviewed current images during explicit history re-import, with producers still held. A successful controller response never substitutes for the command's registry, kernel-UID, native-census, artifact, backup, byte or journal checks.

Preparation freezes the whole registry and consumes fresh `census LOOP --mail-migration` output from the pinned lane image. Native launch admission must be paused through the owning lane command. Every boxed run must be drained and retired through its native owning path, including node reconciliation. Legacy `letters` reservations and plans naming `.local/inbox/dispatch.md` require that reconciliation; they are not rewritten by migration. The manifest lists every old loop `inbox/new` and `inbox/cur`, both old box stores, and excluded driver trees with their byte commitments. Missing optional loop stores are explicit absence; existing loop inbox roots make both children expected. Existing worker-run trees must match the protected table exactly and relocate before any historical birth.

Apply creates each historical worker mapping through the common birth and retirement path, sealing its mailbox and releasing the UID before preparing read-history moves. Thus the 64-UID block bounds simultaneous identities, not lifetime migration entries. Opaque bytes and raw basenames, including malformed legacy names and temporary spellings, remain unchanged. Duplicate basenames receive separate provenance directories. The old `.local/outbox` leaf is explicitly **inert** in the manifest: it has no reader, grants no delivery or resume authority, and writes there do not submit mail. Worker instructions that name `/mail/outbox` are part of the instance's cutover documents; this command neither reads nor writes them.

Before activation, rollback restores letters, parks post-cutover bindings and namespaces in a private lifetime vault, reverses execution-home relocation, restores the previous configuration and deployment, and then restores previous processes. Namespace-root hold markers prevent ordinary provisioning or birth from replacing quarantined history. Blind configuration-backup restoration remains a refusal. `reconcile` resumes the install hold after a completed rollback, requires the frozen legacy configuration to match its backups, relocates execution homes again, parks the restored legacy configuration, and re-imports the exact lifetime vault before removing its hold markers. It retains every prior mapping and assigns a fresh historical name for the next conversion generation, never reactivating a retired name. Changed legacy configuration needs reviewed reconciliation and is refused rather than overwritten. `apply` then resumes provisioning and a fresh byte manifest; an old configuration cannot erase retained name history. New journal reservation or delivery closes legacy rollback permanently and requires mail-journal reconciliation.

The controller interface and deployment-plan schema are migration interfaces, not a compatibility transport. Plan, controller-output and global-manifest bounds are 16 MiB implementation limits; reviewed artifact reads are bounded at 512 MiB. Namespace-root orchestration is reviewed by reading where the node blocks user namespaces. Its positive production-entry rehearsal belongs to the loop's host deploy operation; node byte, history, native-census and two-account fixtures do not claim that root rehearsal.

## Worker lifetime entry · `sec:loophome:worker-lifetime-entry`

The library’s `hold_active_beneath` acquires an active lifetime lease using receiver-validated configuration, loop storage, private storage and the identity executable. Its first phase, `verify_active_beneath`, returns a `VerifiedLifetime` that grants no admission and holds no lease. This supplies the lifetime prerequisite for descriptor-relative mail and reply binding; the lane reply entry uses it together with journal and endpoint custody, while mail binding retains its separate route.

The host worker harness and native lane retirement composer hand one configuration, executable and storage bundle through Podman stdin. The private birth and execution-home forms require the manifest; directory numbers alone grant no authority. The loop child validates the private-directory capability after dropping identity and keeps it as cwd for relative configuration publication, while the service child validates its journal capability before releasing reservation pins. The native lane retains its timeout, environment, process-group handling and bounded output capture.
