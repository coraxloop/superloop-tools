# Scope-floor directory context and filename expansion · `rec:scopefloor:directory-and-expansion`

This design record explains why visible command-text inspection cannot promise working-directory or filename-expansion containment. It is reasoning for contributors and for the owner deciding what a loop may rely on before enabling the hook, not a contract, implementation plan or activation approval. The smaller directory rule and its expansion cut are unimplemented alternatives: every transfer, checklist, test and estimate below describes a proposed design, not behavior the code keeps or a promise to build it. The published aid claim remains the current scope contract. The record does not change hook activation.

The scope-floor implementation spans the shared tokenizer and projection in ``packages/execute-command/src/checks/hygiene.rs`` and path policy and refusal rendering in ``packages/permission-triage/src/hook.rs``. The package README carries its current contract. The product principle is (`prin:publictools:well-made-and-good-to-use`); the open problem is (`prob:hooks:the-scope-floor-reads-expansions-remote-standard-input-and-copy-operands`). This record preserves the design's decisions, conditional reasoning and open owner choices rather than defining another source of execution authority.

## Decisions and correction · `sec:scopefloor:location-finding`

The recorded engineering decisions are: no further repair by lists of spellings, names, prefixes or bracket positions; publish the corrected aid claim as explanatory prose; and land brace mechanics only together with the command-position rule. The last condition matters because ``{cd,} && pwd`` reaches HOME, whereas the landed blanket brace refusal rejects it. A further recorded decision is not to build the smaller directory rule for harness Bash, even as an aid: captured startup state invalidates its external-command transfer and it would merely add refusals. The first subset includes the additions below. These engineering points are no longer owner alternatives; the reliance contract, certified data workload and enabling any loop remain the owner's.

Location depends on positive evidence. Two independent questions must remain separate. Directory flow needs to know whether an invocation runs an external process or code in the current shell. Argument interpretation needs to know which arguments are paths, shell bodies or data. An external program cannot change its parent's working directory; its argument grammar is unnecessary to prove that fact. It can change its own directory or run arbitrary children, so the same fact proves nothing about those effects or about the location of code passed to an unknown launcher.

Requiring a binding for both questions on every command would refuse every ordinary line until those bindings existed, including ``git status``, ``rg PAT src`` and ``cargo test``. The smaller cut below avoids that unnecessary cost under one shell-state contract. It does not introduce certified data roles and does not promise to make sed patterns safe by looking for a directory named s. Filesystem-dependent grammar decisions, current glob matches and another bracket-closing-character check remain rejected.

## A smaller directory-closed cut · `sec:scopefloor:positive-location-rule`

**Claim (Directory flow has an unknown default)** · `claim:scopefloor:positive-location-evidence`

At each level of code, carry a bounded set of possible working directories, or unknown. Give a transfer only to an external command, a positively admitted directory-preserving builtin, the exact explicit-directory form, or an admitted connective. Every other construct has unknown directory effect. Every relative path is checked at all bases that can reach its evaluation; under unknown it is unresolved and imposes estate scope. Lexical fallback supplies literal fragments but never establishes a base. Recognition can add an interpretation or an unresolved result, never erase an existing obligation. A forgotten construct therefore loses precision rather than inheriting request.cwd by default.

The one execution fact is a fixed, known command-resolution and process-placement contract: a pinned shell with no aliases, functions or startup/trap behavior that can substitute current-shell code for a supposed external command, and with pipelines/background/subshells placed as the model assumes. For the proposed Bash subset this includes lastpipe off. This is one shell-state invariant, not a certificate for every external program's arguments. It must hold initially and remain true along every admitted transition; commands that change dispatch, traps or relevant options are not directory-preserving merely because they do not themselves call chdir. Captured session state is not compatible with assuming this invariant.

The builtin inventory can be obtained from the pinned shell during development; membership alone does not certify preservation. The first subset admits ``:``, ``true``, ``false``, ``echo``, ``pwd``, ``test``, ``[`` with its required closing operand, and ``printf`` without ``-v``, subject to the existing literal/expansion checks. It also admits ``set`` only with the positive option grammar below. A token outside the shell's special forms, builtin inventory and function/alias space is external under the established shell-state contract, even if executable lookup fails. No hook-side reading of its own PATH substitutes for that contract.

For ``set``, admit enabling ``-e``, ``-u`` and ``-x`` separately or clustered, and ``-o`` with a separate value exactly ``pipefail``, ``errexit`` or ``nounset``. A cluster ending in o consumes that one value, so ``set -euo pipefail`` is included; other clusters, operands and options are unknown. These options preserve directory state and the command-resolution/process-placement invariant. Errexit can stop execution; the abstract analysis may conservatively retain a continuation that never runs, but must not drop a base on a continuation which can run. This is a directory overapproximation, not an exact shell exit simulator. ``printf -v``, ``export``, standalone assignments, ``source``/dot, eval, alias, trap, shopt, function definitions and unmodeled compound commands stay unknown. An option change outside the positive set cannot silently retain the shell contract.

The shell-state contract becomes this checklist, read in the **executing process** through an established trusted bootstrap, not inferred from a separate clean probe or caller-supplied attestation:

|Observation|Required evidence|
|-----------|-----------------|
|Shell image|Exact pinned Bash binary identity and expected invocation/startup mode, not just a version string or a pathname.|
|``alias -p``|Empty.|
|``declare -F``|Empty, including ``command_not_found_handle`` and functions with slash-containing names. A shell probe recorded during design review observed a function shadowing ``/bin/echo``; an absolute name is not an escape from this check.|
|``trap -p``|Empty. This is a proposed contract check, not a claim that vendor snapshots capture traps.|
|``shopt`` state|``lastpipe`` and ``extdebug`` off.|
|``set -o`` state|``posix`` and ``monitor`` off for this proposed subset; other options agree with the pinned baseline and the admitted set changes.|
|``enable -a``|Equal to the pinned enabled/disabled builtin set.|
|Nested-shell startup environment|``BASH_ENV`` and ``ENV`` unset; no inherited function definitions or option imports which invalidate the contract. A child inherits known bases only under its own established shell contract.|

The bootstrap itself cannot rely on an untrusted function named like its inspection builtin. Execution ownership must establish how these observations are obtained before untrusted code, and admitted commands must preserve the checked invariant. Checks on another process do not certify this one. A failed or absent observation prevents the guarantee; this checklist is a proposed acceptance fixture, not authorization to probe or change a live harness.

For each construct, retain success and failure exit-base sets, S and F; unknown is the top element and union with it stays unknown. An external command returns both possible statuses at its input bases unless a tighter result is justified. A preserving builtin does likewise, with exact statuses only where established. The initial set is the validated request cwd for the outer command. Each fresh request uses its supplied current cwd; the hook does not reconstruct the harness's inter-request directory history.

The first directory-changing transfer is exactly ``cd -P -- ./LITERAL`` in the pinned subset, with one nonexpanding literal relative destination, no parent component, and no hidden operand. Resolve and check that target using the existing path policy at each input base, use its physical directory on success, and retain the old base on failure. An unreadable or unresolvable target cannot yield a successful known base. A failed check still contributes estate scope; failure to enter a prohibited directory is not a policy exemption. Every later relative operand and redirect uses the resulting set, not request.cwd. The proof remains subject to the existing judgement/use filesystem assumptions; static canonicalization cannot close a symlink race.

|Trivial connective|Transfer in the first subset|Obligation that is not discarded|
|------------------|----------------------------|--------------------------------|
|``time PIPELINE``|Use the pipeline's transfer unchanged; the reserved word times that pipeline, not the entire following conjunction. Other time option shapes need an explicit admitted grammar.|Keep path obligations and statuses; ``time X && Y`` composes timing with the existing conjunction rule.|
|``! PIPELINE``|Swap the pipeline's success and failure sets; do not restore the old base when negating status.|A successful directory change followed by negation still changed directory.|
|``A ; B``|Evaluate B from S(A) union F(A); the sequence's exit sets are B's exit sets.|Inspect both commands and their redirects.|
|``A && B``|Evaluate B from S(A); success is S(B), failure is F(A) union F(B).|A's failed states remain available to any later continuation.|
|``A \|\| B``|Evaluate B from F(A); success is S(A) union S(B), failure is F(B).|Do not reuse only A's successful directory.|
|``A \| B``|With lastpipe off, each pipeline process starts from the enclosing input bases; inspect each internally. The enclosing shell's post-pipeline base stays unchanged for either status.|An unsafe or unknown relative use inside a child still imposes estate. Status/pipefail details may be overapproximated without inventing a new base.|
|``A &``|Inspect the asynchronous child from the input bases; continuation in the parent keeps those bases.|Do not treat an unsafe child as harmless because it cannot change its parent's cwd.|
|``( A )``|Inspect A from the input bases in the subshell; the parent's exit bases are unchanged, with A's possible statuses.|Subshell isolation restores the parent state, not a lower scope verdict.|

Redirects are checked at the point the pinned shell evaluates them, including before a command's directory change, rather than after its transfer. Connectives compose over the finite set; a global state/depth limit yields unknown instead of truncating the set. Unsupported compound syntax, functions and other shell modes are unknown. The tokenizer must preserve grouping and connector order well enough to implement these transfers; a flattened list cannot claim them. New syntax gets no implicit preserving transfer.

|Code level|Base supplied by the smaller rule|
|----------|---------------------------------|
|Outer request|Validated request.cwd, conditional on the executing shell-state invariant.|
|Known nested shell form|Inherited bases only if its launch and startup semantics establish them; otherwise unknown. Run the same transfers within it.|
|Text supplied to an unknown launcher|Unknown: an external launcher preserves its parent's base but may choose a different base for the body it runs.|
|Nested text which parses|Parsing gives syntax, not inheritance; use its known or unknown starting bases.|
|Nested text which falls back to a lexical split|Unknown throughout; literal fragments retain path checks but cannot grant a directory proof.|
|Remote code|Never borrow the caller's local cwd. Use only established remote facts; absolute remote path checks remain textual, not remote filesystem containment.|

This closes the directory-flow class only inside the supported shell contract: every accepted node has a transfer overapproximating its possible bases, composition retains all reachable bases, and every unsupported node contributes unknown. It is not a claim that external programs access only argv paths. A successful parse is also not proof that the tokenizer and real shell agree; the pinned-shell variant needs the differential evidence below. State this condition rather than claiming the abstract interpreter proves its own parser.

## Expansion is a separate cut · `sec:scopefloor:expansion-rule`

The smaller directory cut leaves expansion under the landed non-erasing data-as-code treatment. It does not need per-program data certificates, and it gives up their usability benefit: quoted patterns in possible code may still be refused. Its safe fallback is not to pretend a regex slash establishes a path boundary.

The following expansion cut needs segment provenance at every possible code level: active ``*``, ``?`` or ``[`` means unresolved filename expansion regardless of a closing bracket's position, an initial-member ``]``, or a following slash. Do not enumerate current directory entries in the hook. Quoting establishes a literal only at that shell level; an unknown consumer can treat that text as code at another level. Lexical fallback grants neither a data exemption nor expansion safety. This covers the bracket class structurally and honestly retains the sed/regex cost until the owner chooses a certified data workload.

Bounded comma-only brace alternatives may be reused from the reviewed but unlanded mechanics, with a limit over the whole derivation: initially at most 64 alternatives, at most 4096 bytes per alternative, and the existing depth guard. Retain original literal coverage and check every alternative. Ranges and unsupported brace grammar remain unresolved. Crucially, any brace or glob in command position is unknown in the smaller directory subset; benign alternatives do not certify a directory transfer. Thus ``{cd,} && pwd`` cannot become loop-scoped by treating cd as a path. If a later subset admits expanded command names, it must derive and join each command's effect, not merely its path verdict. Brace relaxation and this command-position default are one inseparable landing.

Certified data modes are a later owner choice. A basename such as sed or awk is not a certificate: evaluating modes and options exist. An exact non-evaluating argument subset needs its own justified interpretation. Keep the non-erasing protected-literal checks even for certified data; do not silently weaken the previous literal guarantee to make a prose argument pass.

A documentation lookup on 2026-11-17 confirmed the following at the vendor's [hook reference](https://code.claude.com/docs/en/hooks.md), [hook guide](https://code.claude.com/docs/en/hooks-guide.md), [tool reference](https://code.claude.com/docs/en/tools-reference.md), [environment-variable reference](https://code.claude.com/docs/en/env-vars.md), [headless guide](https://code.claude.com/docs/en/headless.md), [sandbox guide](https://code.claude.com/docs/en/sandboxing.md) and [settings reference](https://code.claude.com/docs/en/settings-reference.md). In that lookup, neither a switch disabling captured startup state nor the prefix's position relative to the hook and captured state was documented. A separate process does not imply a clean shell.

**Answer:** from these facts, replacement is possible, but binding a directory proof to arbitrary current harness Bash execution is not established. Replacing the body with a simply quoted call to a pinned clean child is not sufficient evidence: the vendor's outer shell still interprets that call under captured state, and prefix handling is not established. Nor does placing ``unalias``, ``unset`` or option-reset commands at the start prove they run before uncontrolled startup behavior or with the assumed interpretation; the documented capture names captured aliases, functions and options, not captured traps. An absolute executable spelling alone proves neither the whole outer execution state nor the route. There is a plausible engineered route—replace input with a fixed, permission-checked invocation of an approved executor, and establish that the harness/prefix reaches it without uncontrolled reinterpretation—but it needs a documented or independently established entry boundary. These documentation observations do not prove that boundary exists or that it is impossible; they do rule out treating it as already solved.

Consequently harness requests can presently be offered the truthful aid contract, or whatever containment guarantees a specifically configured sandbox is confirmed and rehearsed to provide. They cannot yet be offered the smaller directory-closed guarantee. An owner-managed clean startup snapshot, fixed shell/options, and fixed prefix could be a route to the pinned-shell contract if those conditions can be enforced and shown to apply to every request; that is an engineering prerequisite, not a hidden session assumption. If the vendor cannot support it, no command spelling repairs the absence of the invariant.

The decisive vendor question is whether the configured prefix is executed directly as the **outermost process**, before any shell applies captured state, and exactly what bytes/argv it receives relative to the input judged or replaced by the hook. A confirmed direct entry with an unambiguous binding to the judged request could select a clean pinned shell or refuse a mismatch. An alternative enabling fact is a documented switch disabling captured startup state together with a fixed shell choice. Neither enabling fact was documented at the pages checked on 2026-11-17. The record therefore neither claims an available clean route nor declares one impossible.

## Unlanded work and public wording · `sec:scopefloor:held-disposition`

The proposed replacement for the unlanded name/prefix directory check is the base-state rule, not another builtin/eval/command loop. Drop the bracket-before-slash heuristic. Retain bounded brace enumeration only as mechanics subordinate to complete grammar, global bounds and the command-position rule, all in the same landing. Keep useful table rows as evidence, update expectations only under the chosen contract, and retain the non-erasing literal coverage as an independent restriction. Prose claiming all directory and bracket cases closed must not land.

The published aid paragraph states the current limit, before the remote and command-string rules: “The scope floor inspects visible command text: where it finds a refused path it imposes estate scope; finding none is not evidence that the command stays in scope. Literal coverage does not depend on which argument a command recognizer selects, but a loop scope from this check does not prove where a later relative path will resolve or which filenames the shell will generate. Directory changes, filename expansion, opaque code/data roles, scripts and inherited execution state can require facts this check does not possess. The hook must not be enabled on the assumption that these effects are contained by the checkout or a domain root. Model judgement and the independently configured execution controls remain necessary; a scope floor is never an allow.”

The directory and bracket repairs remain unlanded. A future cut would separate directory-flow proof under an established shell-state contract from argument roles, and brace relaxation would include the command-position rule. Recording that disposition does not schedule or authorize the cut.

If the smaller proof is later implemented, its conditional README claim should be: “For requests executed under the registered fixed-shell contract, the directory analysis checks relative paths at every possible base, propagates directory effects through the supported connectives, and treats unsupported effects and lexical fallback as unknown. This is a directory-flow guarantee for the admitted language, not proof of external programs' file effects or filename expansion, nor protection against filesystem changes between judgement and use. Requests outside that execution contract receive no such guarantee.” Do not publish that paragraph as a property of harness Bash until the entry binding and shell state are established.
