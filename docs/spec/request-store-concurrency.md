# A concurrent request store · `proposal:requeststore:concurrent-custody`

One canonical record per request is the chosen representation; immutable revisions commit independently without a store lock. Readers take no store lock; notification makes them reread state rather than conferring authority. This concept records the design decisions, not an implemented protocol or an adoption of new invariants. Its candidate properties remain proposals, separately reachable from the adopted invariant sources described by (`sec:contributing:invariants-and-their-sources`). It supplies the concurrency argument beneath (`proposal:collectionjournal:bounded-request-work`), not another journal implementation beside the existing owners.

The commit path holds no lock. A fully prepared revision wins by no-replace publication at the next revision-numbered name; readers probe forward from a hint, and no abandoned writer can leave a commit lock held. Work follows changed records and returned answers. A few milliseconds is a measured commit-wall objective, not a guarantee that a filesystem syscall cannot stall; required syncs precede acknowledgement or effect. Execution/recovery activity leases are separate: they establish whether one request still has a live executor and never exclude another request's commit. The design removes whole-batch atomicity in favour of all-or-nothing input validation and per-item concurrency outcomes, and uses a policy reread after a durable claim rather than a gate shared by admissions.

## Evidence and actors · `sec:requeststore:evidence-and-actors`

There are more than two exclusion mechanisms. The door uses shared/exclusive nonblocking flock, a process-local writer ticket queue and 15-second base attempts (``store.rs:44–50,1316–1694``); the queue does not order other processes. The journal PID lock uses exclusive create, a 2 ms retry, a 4 s default and dead-and-60-second-old recovery (``permission-triage/src/journal.rs:39–50,1782``; ``journal/request_lock.rs:65–169``), including a file sync and directory sync at acquisition. The owner commit also takes a stable blocking flock inside ``Transaction::open`` (``transaction.rs:140–169``), then validates and syncs under it. Per-request publication leases and per-box execution admission are additional, different protections; removing collection locks does not remove them by implication.

The files are not all merely replaced snapshots. The owner helper replaces the collection snapshot with preserved disposition lines (``owner.rs:392–424``), whereas legacy permission escalation and consumption append under the journal lock (``permission-triage/src/journal.rs:387–449``). The door replaces run records, shapes and learned data in sequence, with invalidation and rollback (``store.rs:2105–2173``). ``channel.rs:579–670`` holds the door lock over helper preview and commit; ``channel_client.rs:110–150`` starts the helper process there. ## Candidate properties · `sec:requeststore:candidate-properties`

Each statement here is a candidate invariant with an argument and a current witness, not an adopted ``inv``. Mechanism names refer to the publication and projection sections below. Tests cited as literal names are existing evidence to retain, not claims that the new mechanisms have passed them.

### Proposal (Identity survives concurrency and retirement) · `proposal:requeststore:identity`

One identity denotes one immutable request ground, including kind, loop, worker, run and source binding, even after archival. Actor A files while actor B files the same identifier or retirement removes its hot row; without an occupied identity or tombstone both can create a fresh execution opportunity, or B can substitute a different body. Today ``model.rs:238–268`` rejects duplicates, ``owner.rs:56–115`` checks repeat gateway filings, ``channel.rs:98–122`` binds common and source identities, and ``store.rs:2255–2300`` checks grants. Propose an exclusive initial identity publication and a permanent compact identity/tombstone containing the original ground digest; a matching duplicate is an explicit already-filed result, never permission to execute again. Retirement changes location, not identity. A hash path is an address, not sufficient validation of the stored ground.

### Proposal (A transition retains its authority) · `proposal:requeststore:authority`

Only the authenticated role for the registered scope and kind changes a request, and only protected custody supplies accepted state. Actor A supplies an allowed door update while actor B substitutes a permission decision or changes a path to another inode; without independent scope and descriptor checks a transport owner becomes a policy owner. Today ``owner.rs:243–301`` checks gateway and permission authority; ``transaction.rs:40–110`` rejects unsafe custody and pins read identity; ``requests-helper`` integration tests reject unknown authority. Keep these checks before preparation and validate the pinned root/epoch at publication. Prepared files, references and indexes have the same protected owner boundary, no caller-selected path or symlink traversal. Splitting files grants no new filesystem access. Scope-specific helper verbs narrow the current common envelope rather than weakening checks.

### Proposal (Concurrent changes preserve fields and review history) · `proposal:requeststore:revision-merge`

A successful change applies to the revision it validated; a stale change neither overwrites another field nor revives an older review. Actor A records an effect while actor B returns an agent result, or an adjudicator answers a review while another review replaces it. Last-writer-wins would lose the effect, owner label or review history. Today the door lock protects ``change_one_locked`` (``store.rs:3139–3168``), the helper compares its entire preview preimage (``owner.rs:402–408``), and ``model.rs:321–362`` checks the latest review identifier. Witnesses include ``agent_merge_preserves_effect_and_supervisory_label`` (``store.rs:4756``) and ``review_is_monotonic_and_stale_adjudication_is_write_free`` (``request-core/tests/transitions.rs:117``). In the model, contenders based on revision N publish only at N+1, so exactly one wins; a loser rereads and reapplies only its permitted field transition, never its old full image. History is immutable referenced events, not a growing current-row array rewritten on each update. A stale review answer still refuses rather than being silently rebased.

### Proposal (One claim admits at most one execution) · `proposal:requeststore:single-claim`

A request admits execution once, and departure before the claim grants nothing. Two handlers read an allowed answer before either saves a claim, or a waiter departs between those operations; without a one-winner claim transition both handlers execute or a departed request executes. Today ``model.rs:366–423`` distinguishes the first claim, identical repeat, conflicting claim and matching completion; ``store.rs:2216–2252`` rereads workspace ground under the lock and requires a publication lease. ``workspace_waiting_claim_moves_state_once_under_the_store_lock`` and ``workspace_claim_reads_owner_label_under_the_lock`` (``requests/workspace_tests.rs:1406,1425``) exercise it. The lane guide's adopted ``inv:superlooplane:workspace-execution-follows-its-own-claim`` still states this in terms of one store write-lock operation; its implementing slice owes the restatement specified below. Put decision, departure, claim token and result reference in the same request revision. The executor wins that revision, makes the claim durable, then rereads the current policy root and run fence before starting the effect. A veto records a nonperformed result against the claim; it does not clear the claim. An identical repeated claim returns no new permission; a process death does not free a durable claim. Permission approval consumption uses the same one-winner transition on the approval identity: two hooks cannot both consume it (current journal consume at ``journal.rs:423–444``). A claim is not an exactly-once effect guarantee.

### Proposal (Unknown effects remain unknown and recoverable) · `proposal:requeststore:effect-evidence`

An effect's recorded result is bound to its claim, and failure to record or deliver it does not authorize replay. Actor A executes then dies before recording; actor B restarts and sees a claim without a result. Executing again can duplicate the effect; calling it unperformed invents evidence. Today ``model.rs:405–423`` admits only identical completion retries, and publication leases prevent the recovery sweep from racing a live publisher (``store.rs:3171–3375``; ``publication_recovery_skips_live_and_completes_abandoned_effects`` at ``:4204``). Retain an independent per-request activity lease through effect and evidence publication, plus explicit unknown/abandoned outcome evidence when the lease is gone. This lease is not store-commit exclusion. Recovery only supersedes an unfinished claim intent; it never completes that intent into a new execution claim on an absent executor's behalf. An already committed claim remains occupied even if its acknowledgement was lost. Reconcile effect-specific evidence where available; do not reset a claim. Exactly-once external effects need an idempotent or transactional executor, which this store cannot supply.

### Proposal (Readers see complete, durable authority) · `proposal:requeststore:publication`

A reader sees one validated request revision, never half of its ground, decision or history; an acknowledged authoritative transition survives a crash within the filesystem's stated durability model. Actor A publishes while B reads, or A loses power between publication and sync. In-place writes tear; an unsynced claim can disappear after execution. Today ``transaction.rs:185–254`` stages, syncs, renames and syncs the parent, returning ``requests-commit-uncertain`` after a post-rename failure; ``store.rs:283`` supplies local leaf replacement. Keep immutable payloads and complete revision envelopes published at unoccupied numbered names. Consumers of authority finish the durability barrier, not interpret visible bytes alone as acknowledged durability. A torn or invalid object refuses; no partial decode or implicit fallback grants an effect. The sequence and its crash cases are below.

### Proposal (Learning never gains authority from a stale projection) · `proposal:requeststore:learning`

Learned decisions retain their owner labels and citations, including retired conflicts, and no correction acknowledged before the executor's post-claim policy reread is outrun by that effect. Actor A adjudicates a correction while B uses an older allowing snapshot; without rereading the current authority B could execute after an already acknowledged refusal. Today ``store.rs:2105–2173`` invalidates before custody changes and publishes after; ``channel.rs:619–663`` invalidates before helper commit; and a filing refuses when the mode snapshot it carries differs from the effective modes it rereads under the writer lock (``store.rs:2273–2285``). Tests at ``store.rs:4799,4901,6078`` preserve retired labels and keep a failed correction publication in audit. The chosen model retains the request's own admitted ground but adds a current-policy veto after its durable claim: a recorded or projected old mode is not the last authority before an effect. Only policy writers CAS the single policy-root revision stream. A correction acknowledged after the reread is not promised to stop that already admitted effect; removing that interval would require exclusion through effect start, which is not the chosen contract.

### Proposal (Invalid batch input changes nothing) · `proposal:requeststore:batch-atomicity`

The whole batch input is validated before any item is written; invalid input changes no request. Once validation succeeds, each item has its own revision-bound outcome, and an item changed concurrently does not undo the others. Actor A validates two rows while B changes the second: the first may commit and the second reports conflict, instead of silently overwriting B or claiming the whole batch rolled back. Today ``model.rs:276–318`` validates on a clone and the owner publishes one collection image; ``atomic_triage_refuses_every_member_before_changing_any_record`` (``request-core/tests/transitions.rs:78``) and ``whole_batch_refusal_writes_nothing`` (``store.rs:6285``) witness the stronger current contract. The implementing slice retains their invalid-input guarantee and changes the concurrent-update expectation and command wording. No multi-request reservation or batch commit descriptor is introduced. Retrying an interrupted batch reports each operation ID's existing result and attempts only remaining items; already committed items stand.

### Proposal (Notification cannot strand a waiter) · `proposal:requeststore:wakeup`

A committed answer eventually causes a live waiter to reread, even if the commit races subscription, notification overflows or the notifier dies. A waiter reads pending, a writer commits and sends a hint, then the waiter begins watching; the missed hint strands it. Today ``door.rs:2190–2290`` polls, avoiding dependence on a single hint at the cost of repeated reads; request wait tests at ``store.rs:7080–7182`` distinguish contention from other refusal. Propose watch-before-read, revision recheck and durable outbox recovery, with absolute-deadline expiry as a bound rather than an idle polling clock. Notification is advisory; decision and claim checks still read authoritative state.

### Proposal (Archival preserves evidence and does not resurrect work) · `proposal:requeststore:retention`

An archived identity keeps its terminal decision, claim outcome and resolvable history; an active claim cannot be archived as completed. Actor A retires a run while B records its final effect or owner label; removal before durable archival can lose review evidence or reopen deduplication. Current recovery and retirement inspect unpublished effects (``store.rs:3297–3375,4169``), and learned-index tests retain retired labels. Publish immutable archive objects first, then a new request revision containing a tombstone that references them; keep identity occupied. Archive compaction is explicit history work, never on a request's commit path. Tombstones and occupied revision names consume storage with retained identities and revisions; retention does not make perpetual deduplication fit finite storage. Payload reclamation and its limits are specified below. The separate run-retirement fence prevents new filings from escaping the retirement inventory.

### Proposal (Retirement fences new filings) · `proposal:requeststore:retirement-fence`

Once a run closes admission, no new filing can enroll; destructive retirement starts only after every previously enrolled filing and execution is durably resolved. Actor A prepares a filing while B inventories and moves the run: a mere read of an open flag lets A publish after B's inventory, losing custody or resurrecting a retired run. Today the lane guide's adopted ``inv:superlooplane:retirement-lock-order`` makes host retirement and uid release hold the request-store lock exclusively; ``launch/retire.rs:292`` and ``launch/retire_absences.rs:270`` take its retirement guard, which refuses while a request of the run waits, is marked or carries a pending correction or an unpublished effect (``store.rs:852–928``). In this model a run-local revision stream contains lifecycle state and an immutable index of enrolled admission IDs. Filers CAS an enrollment while open; retirement CASes open to closing in the same stream, makes it durable, then resolves that sealed enrollment set. Its commits hold no lock, although filings for that run contend on this small publication point. Unrelated runs do not share it. Claim-then-reread alone is insufficient: a filer can pause after reading open. Enrollment and drain are what account for that paused filer.

A filer takes its request activity lease before durably enrolling, retains it through filing and any execution/publication it owns, rereads the run fence after durable request publication, and records either accepted filing or withdrawn/nonperformed outcome. Enrollment is not discharged merely because a filing succeeded: it remains indexed until no execution or publication is outstanding and its terminal evidence is durable. Retirement waits for live activity or fenced recovery to resolve the sealed admissions; a late provisional row is included through its enrollment and never escapes the inventory. A sealed admission whose request still awaits an owner decision, is marked or carries a pending correction has no live activity or recovery to resolve it, so retirement refuses on it as the store's retirement guard does today, and the run stays closing for the retry; a dry run reads the stream and publishes nothing. The fence closes admission, not the ability to finish or withdraw an already enrolled operation. An executor also rereads the fence after its durable claim; if closing, it records refusal without execution. If closing occurs after that reread, retirement waits for its already enrolled activity rather than deleting resources beneath it. Only after the sealed set is resolved does retirement move custody and publish retired. A successor process cannot revive an old enrollment as new work; it must satisfy the closed fence and canonical state. Crashed retirement resumes from closing and its named enrollments, never reopens automatically. Existing configuration, preparation, mailbox and node-retirement guards are not removed by this store concept. The implementing slice must restate the request-store part of the adopted retirement invariant with this argument.

## Per-request publication model · `sec:requeststore:publication-model`

One canonical envelope owns the common request and door-specific source/effect fields. The door's run records are projections, not a second authoritative store with rollback between copies. The common journal owner retains its registered root and role checks; unbound local stores use the same primitive under their own custody. Unifying representation does not unify permission scopes or uids. A transition references disposition, agent and history evidence within its immutable revision so none depends on an independent day-file append succeeding later.

|Object|Use|
|------|---|
|``format``|Version and store identity established by the crossing; no global mutation revision.|
|``requests/SHARD/ID/rev/N``|Complete small immutable envelope for revision N: predecessor digest, operation ID, current-state and committed-operation-index roots, history/archive references. Numbers are consecutive, never reused.|
|``requests/SHARD/ID/hint``|Advisory revision locator only. A stale, missing or regressed hint cannot authorize an answer; readers probe the numbered sequence.|
|``objects/SHARD/DIGEST``|Immutable ground, transition, index-path and history payloads, durable before any revision references them.|
|``outbox/SHARD/OP``|Durable preparation with identity, expected revision, candidate digest and projection changes; exists before commit and remains through a durable projection receipt.|
|``unresolved-claims/SHARD/ID``|Conservative restart index, durably registered before attempting a claim and removed only after its matching result or supersession is durable. False positives are checked against canonical state; no committed claim is omitted.|
|``runs/RUN/rev/N``|Run-local lifecycle and immutable enrollment-index root; the same numbered no-replace publication mechanism. This is admission bookkeeping, not a copy of request decisions or effects.|
|``views/``|Indexed diagnostic memberships, counts and shape observations with applied-operation receipts and visible catch-up state; never granting authority.|
|``policy/rev/N``|One policy-root revision stream referencing immutable settings, learned evidence and pending-correction state. Only policy writers commit here.|
|``archive/``|Immutable terminal evidence reached through canonical tombstones; no second writable collection.|

Use capped current envelopes and separately addressed payload/history objects. Bounds protect decoding and one transition's work, not an exact store capacity. Paths derive from validated identities under held descriptors. Every revision validates its predecessor and operation ground. A no-replace rename of a complete staged envelope, on the same filesystem as its final name, is the preferred primitive: ``renameat2(..., RENAME_NOREPLACE)`` at ``rev/N+1`` is the compare-and-set for state N. All contenders for N choose that same destination. One wins; ``EEXIST`` makes the others read the winner and report conflict or recompute outside any exclusion. A writer must never skip an occupied number and publish its old candidate at a later one. There is no commit lock, lock-holder recovery or lock-contention timer.

Do not expose a half-written revision by creating the final name with ``O_EXCL`` and then filling it. Exclusive create is suitable only for a complete-state publication primitive with a proved completion protocol; the chosen ordinary-file implementation stages, writes and syncs first and uses no-replace rename. Content-addressed object publication likewise never overwrites an existing object and checks its digest/custody. Same-identity operations serialize at the atomic namespace operation, not during preparation, process execution, policy evaluation or sync.

An update reads the latest validated revision; prepares immutable changed objects and the committed-operation index path; syncs their files and directories; durably publishes its outbox intent; stages and syncs the complete next revision; then attempts the no-replace rename at N+1. Success is followed by a sync of the revision directory before acknowledgement, projection receipt, or effect. A successor first makes its predecessor durable, so an acknowledged later revision cannot depend on a predecessor whose name disappears on crash. A reader that will act on a visible revision completes that directory barrier if durability is not otherwise established; visibility alone is not permission to execute. Initial filing uses the same complete publication at revision zero, with the new identity directories synced before acknowledgement. Duplicate zero publication validates identity and returns already filed, never execution permission.

A reader starts at a validated hint or zero and probes later numbered names, validating the selected envelope and predecessor chain evidence. Absence of N+1 after observing N is a read's linearization point; a later commit belongs to a later read. A hint is not a snapshot and is never trusted without probing. Ordinary sequential probing costs the revisions since the hint, not retained requests. To avoid a permanently stale hint causing a linear history walk, retained contiguous names permit exponential then binary existence probes, followed by a final successor check, using logarithmic probes in the missed revision distance; payload and operation-index validation stays bounded by the returned revision and index depth. Under continuous writers, a reader may reach its deadline and report retry/unavailable rather than promise a wait-free latest read. A stale hint update can hurt latency but cannot overwrite a revision or change authority.

Each update costs bounded opens/reads/stats for its envelope and changed index paths; one open/write/file-sync per new object; directory syncs for the affected object directories; an intent file sync and parent sync; one staged revision file sync; one revision-directory sync before the attempt unless the writer already knows its predecessor durable; one no-replace rename attempt; and one revision-directory sync on success. Additional retry attempts cost a winner read and any recomputed objects, never an entire-collection scan. A claim also durably creates its unresolved-claim index member before the attempt and retains its existing activity lease. Enrollment and closure each cost one run-stream revision publication; final enrollment resolution costs another. Policy writers pay the same per-root publication costs; admission only reads that root after its claim. These are logical I/O counts, not a promise that a write uses one syscall or that sync has bounded wall time. All parsing, helper starts, validation and sync run without commit exclusion.

|-----------|-------------------------------|

### Proposal (Revision reclamation preserves occupied slots) · `proposal:requeststore:revision-reclamation`

Reclaim obsolete full-state payloads only after a durable checkpoint revision preserves current state, identity, committed-operation results, unresolved work and archive/history reachability. Old readers holding an object descriptor may finish reading it; a reader that loses an obsolete object before opening it restarts from the checkpoint and never interprets absence as an empty request. A writer that finds a content-addressed object already present reuses it, so reclamation must not remove an object that a current revision, an outstanding intent or a writer still preparing can reference; binding every payload object to the identity whose stream references it and to the operation that created it, so that no object is shared or recreated by a later transition, meets this. Historical evidence remains in its archive, not silently deleted. Keep a configured recent payload window and compact older state/index paths during explicit maintenance, not a commit. The window bounds redundant hot payload versions after maintenance catches up; no finite total bound follows while producers outrun maintenance or retained history grows.

Occupied revision names remain as small seals; do not unlink or reuse them in this model. A delayed writer based on N could otherwise recreate reclaimed N+1 and claim a second successful transition. A durable checkpoint makes old payloads dispensable, not the exclusion performed by those names. The seals have a capped size per revision but their total number grows with committed revisions. A finite-inode bound or deletion of these names requires a separately designed epoch/fencing or reader-quiescence protocol; neither age nor a best-effort hint proves that a stale writer cannot return. That reclamation extension is further design; keeping the small seals is the safe initial choice. No new store capacity guarantee is introduced. Revision-number exhaustion refuses without wraparound or reuse.

## State, projections and notification · `sec:requeststore:states-and-views`

Keep the common state machine: ``filed`` becomes ``marked`` or a triage decision; a marked request gets successive reviews and an adjudication bound to the latest review. Non-service decisions are terminal; a service decision becomes ``service-pending``, where a one-time claim and matching result lead to ``completed`` (``model.rs:8–32,276–423``). ``waiter_gone`` is monotonic metadata, not an allowance. The door's effect state, agent observation, owner label and final-write evidence are separate fields. An owner decision never supplies execution evidence. After a durable claim, policy or retirement veto produces a nonperformed result under that claim; it does not return the request to an executable unclaimed state.

A projector consumes committed operations and publishes immutable indexed generations for pending/run/approval memberships, diagnostic counts and shape observations. Its service lease excludes a second projector, not request commits. Its applied-operation membership and counts are in the same generation so replay cannot apply a delta twice. Fixed-depth hash/radix indexes update the keys changed by an operation; ordered pagination has its own index-path cost. A full listing necessarily costs its returned rows. Listings identify their projection generation and catch-up state, recheck actionable rows against canonical revisions and offer a fence for the caller's own operation receipts; they do not claim a globally atomic or current snapshot. Authority never comes from a lagging count or shape display.

Durable outbox intents are registered before their transitions, watched and retained until receipt. Startup and notification-overflow recovery reconcile this outstanding set, not the retained collection. A preparation observed before commit remains pending while its actor can commit; subscribe to that identity's revision directory before rechecking. A stopped producer requires proof of absence through its activity/liveness evidence, not PID age alone. A recovery actor supersedes an unfinished claim intent by a competing revision; it never creates its execution claim. Other authenticated mutations may be retried from current state. Backpressure for outstanding recovery work is reported as such, not as a capacity promise for the request store.

The restart index is ``unresolved-claims/SHARD/ID``. Its member is durable before a claim attempt, and contains the candidate operation ID and expected revision. It is removed only after a durable matching terminal result, or after a dead producer's claim intent has been durably superseded; a failed CAS rereads before removal. Because a request's execution claim is once-only, no later claim generation can race that removal. The index may contain a preparation that never won, but a committed claim without a result always has an entry. Restart reconciles these entries and outstanding outbox intents against canonical revisions and activity leases. Unlike diagnostic views, this conservative index cannot lag creation of a claim; it prevents a crash between claim and asynchronous projection from hiding an abandoned request.

Wait on parent directories, not replaced payload inodes. Register the watch, read/probe revisions, drain queued events and recheck before blocking; on a hint reread and validate. Overflow, watch invalidation and notifier restart cause named-identity reconciliation; absolute deadlines bound the wait without a periodic polling clock. A projection waiter watches its receipt generation with the same ordering. CAS losers already have a concrete winner to read, so they need no lock-release wake-up or retry sleep. Process exit/liveness notification resolves abandoned preparations; no transient socket or inotify event is itself durable authority.

## Shared state decisions and implementation obligations · `sec:requeststore:shared-decisions`

Capacity belongs to the owner of a resource, not to the request store. The store gives no capacity guarantee: any retained storage cap is checked against a versioned, possibly lagging count and may be overshot by admissions in flight; growth is retention's matter. The door's limits on peers and waiting requests remain local admission limits, not store properties. Today's whole-file bounds and scan are at ``store.rs:2297–2319``. Projection lag can also hide already completed filings, so overshoot is not bounded solely by the instantaneous number in flight without a separate freshness bound. No tickets, exact allocator or capacity invariant is part of this design.

Batch input validation is all-or-nothing against the versions read: schema, duplicate identities, kind/role authority, requested transition and supplied review IDs are checked for every item before the first write. After that, each item commits independently against its validated revision. A changed item reports conflict; successes remain, including across a caller crash. Persistent per-item operation IDs make retry outcomes inspectable. This deliberately removes simultaneous whole-batch visibility. The implementing slice owes replacement of the sentence in ``reg:superlooplane:door-request-custody-and-limits`` in the lane guide that triage “changes the whole batch or none”, together with its parser/result contract and concurrency tests; invalid-input tests retain their no-write expectation.

Policy admission is claim, durable claim, current policy-root reread, then effect if still allowed. The reread is a fresh probe of the one root revision stream, never a cached policy object, diagnostic projection or hint alone. It may veto but does not invent missing request ground, undo a refusal label or create a second claim. Record the policy revision used. Only policy writers CAS this stream; admissions do not mutate it or join a shared gate. Acknowledged policy corrections have completed their root-directory durability barrier, so a reread begun after their acknowledgement observes that correction or a later policy. A later correction, after the reread, is not promised to cancel the effect already admitted by it.

An owner correction is acknowledged only after both its canonical decision and the resulting policy root are durable. Before changing the decision, a policy writer can publish a pending/unavailable root revision; readers refuse until the writer publishes a reconciled root. The root carries pending operation identities so another writer cannot restore a stale granting root over an unfinished correction. A losing policy CAS rereads and recomputes, retaining all pending corrections. Recovery completes policy reconciliation from durable owner decisions without inventing labels. This preserves fail-closed crash behavior with no lock, at the cost of temporary refusals while a correction is incomplete. Settings and learned evidence are immutable referenced nodes, not a whole learned-index rewrite.

The implementing slice owes restatement of ``inv:superlooplane:workspace-execution-follows-its-own-claim`` in the lane guide: replace the single store-write-lock wording with the once-only durable request claim followed by the current-policy reread and its veto, while retaining the exact envelope/grant ground, box admission guards, label restrictions during execution and abandoned-at-start behavior. Its argument is that no correction acknowledged before that reread is outrun by an effect; it does not promise revocation after the reread. The source filing check that compares mode snapshots must move to this explicit before-effect check, retaining the recorded original ground and the later policy observation rather than silently rewriting history. No adopted invariant is edited here.

Run retirement uses the enrollment/closing/drain mechanism above. Its implementing slice also owes restatement of the request-store clause of ``inv:superlooplane:retirement-lock-order``; it retains the other lock-order and node-attempt clauses. The phase that inventories and moves custody cannot start while an enrolled filing or executor remains unresolved. Merely adding a post-claim run-state read would leave a paused filer outside the inventory and is rejected for that reason.

One canonical request record replaces the staged design's separate door store. Run-shaped files, counts and display shapes become projections; their failed publication leaves recovery work, not a second authoritative history to roll back. Helper authority scopes stay separate. Acknowledged decisions and execution evidence reside in the canonical revision and its referenced immutable objects, regardless of which process supplied the observation.

These choices remove the proposed shared policy gate, exact-capacity allocator and multi-request batch transaction. The remaining publication points are per request, per run for its fence/enrollments, and the single policy root for policy writers. They serialize conflicting revisions through exclusive namespace publication, never through a held commit lock. No hard millisecond or syscall-wall guarantee is implied. The unresolved extension is safe deletion of old occupied revision names if a finite metadata bound is required; retaining seals keeps the properties without assuming such a bound.

## Relation to the staged design and crossing · `sec:requeststore:crossing`

Keep the earlier reductions in repeated reads and the scope-specific helper API. Stage 3's identity-addressed rows and memberships remain useful; replace its global revision and single in-flight WAL with per-identity revision-numbered commits and per-operation recovery. Stage 4's terminal archives and tombstones remain, with no bounded-total deduplication claim. Stage 5 changes ownership of truth: door run files become projections of the one canonical record, not a separately authoritative per-request store; shape and count updates follow committed operations. Stage 6's directory notification and policy-by-reference remain with subscribe/read/recheck and the post-claim policy reread. Per-hold collection caches and commit-lock queues disappear when queries address revisions. The earlier stages are cited at (`sec:collectionjournal:stage-3`), (`sec:collectionjournal:stage-4`), (`sec:collectionjournal:stage-5`) and (`sec:collectionjournal:stage-6`).

|Cut|What it removes by itself; prerequisite|
|---|---------------------------------------|
|Define scoped verbs, item outcomes and the reader floor|Carries the decided batch and policy semantics into command contracts; no latency claim by itself.|
|Add revision-numbered no-replace publication and fault witnesses in request-core|Proves one winner, durability, stale-hint reading and safe payload reclamation with seals retained; no production speed claim yet. Reuse current authority/descriptor code.|
|Implement scoped row queries and mutations in journal/helper and door adapters|Removes whole-collection transport from callers. An old-format backend may still scan internally until crossing; do not describe this as eliminating its lock.|
|Implement canonical records, unresolved-claim index, run fence, policy reread, outboxes and views|Removes collection/run rewrites and commit exclusion after crossing. Restate the adopted claim and retirement invariants in this implementing slice; readers report projection lag.|
|Cross every writer and reader of one custody root together|One measured traversal exports current collection, legacy lines, local runs, histories, approvals, labels and unresolved claims. Verify identity counts, ground digests, decisions, results and dispositions; prepare the new root, sync it, and publish its format marker last. This alone removes the old collection lock for that root.|
|Enable watch/read/recheck waiting; retire old lock credit and queue once old callers are absent|Removes idle polling. Keep request deadlines and admission limits; no credit is needed for a nonexistent global custody wait. Any remaining same-identity contention is separately measured rather than credited through the old collection protocol by accident.|
|Retire terminal records and compact evidence through the existing retirement owner|Reduces hot storage and explicit history-query cost, not already constant request work. No active claim is reclaimed.|

Crossing must stop admission and quiesce door, gateway, hook and owner-command writers for that registered root; stopping only a door leaves journal writers alive. Finish or explicitly preserve in-flight claims and publication leases before migration. The migration is digest-bound to its exact inputs and resumable from its own preparation record. Its duration follows measured bytes and rows; no minute-scale estimate is established here. The old sources remain read-only evidence. Do not dual-write or accept both layouts as a standing compatibility path (`sec:publictools:versioning`).

An old binary does not know the new marker and may recreate its old journal; a marker alone cannot fence it. Before crossing, stop and replace all owner-held writer processes and their launch paths, including hooks and gateways; verify their executable identity and that no old publication lease remains. If that exclusion cannot be established, refuse migration. New binaries refuse an absent/wrong format marker or a live legacy writer surface beside the new root. Because a reader of the old layout would be a compatibility reader (`sec:publictools:versioning`), the canonical records and the crossing ship in one format release whose binaries, apart from its one-time migration, refuse an uncrossed root; that release installs with the root's writers stopped, then migrates, then starts its writers, and the cuts before it (the primitive and the scoped queries over the old backend) install as ordinary releases. Before any new-format write, rollback may restore the untouched old inputs and old binaries together. After new writes, rolling back binaries loses new decisions and claims; use forward repair or a separately reviewed reverse conversion under the same quiescence. A mixed old program and new live store is unsupported and must be prevented operationally, not treated as a harmless stale reader. This crossing is a data-format transition, not a reason to hold every ordinary install.

The process-local writer arrival queue and measured wait-credit protocol remain useful while old store transactions exist. In the final model there is no population-wide queue to be fair about, and unrelated requests must not join one. Same-identity CAS conflicts read the winner and respect the caller deadline; no lock waiter, timed contention poll or cross-process FIFO guarantee remains. Existing per-box admission for mutually exclusive effects remains outside the store redesign.

## Measures and focused tests · `sec:requeststore:verification`

The baseline release line is the ``door-request-lock`` event with ``outcome: released``, ``path``, ``wait_ms``, ``hold_ms`` and exclusive phase counts/times (``requests/store/hold.rs``; lane guide's literal locator ``proto:superlooplane:request-lock-hold-observation``). Acquisition events distinguish retry/timeout and may have a null holder for another process; they do not measure that process's hold. The new commit has no hold to time: record preparation, CAS attempt/winner, directory durability, acknowledgement, projection lag and notification latency separately, with total commit wall and syscall counts. A hidden serialized queue would still be a finding. Activity-lease duration is execution/recovery evidence, not a commit hold.

The staged design records 2026-11-14 field holds of 42–49 s for filing and 38–43 s for effects before its first reduction, and reports its measured subsequent reductions separately (`sec:collectionjournal:measurement-basis`), (`sec:collectionjournal:slice-a`). An owner adjudication of 2026-11-26 is reported with two 15-second lock expiries and 89 seconds total; its raw events are not recorded here, so it is an incident report, not a measured hold or a reproduced benchmark. It cannot identify an unknown holder. A small-collection baseline from the door's own hold lines on 2026-11-26, release 0.13.2, one boxed worker and a collection whose listing is 207 KB: 119 exclusive holds, none waited for; hold 6 to 203 ms, median 85 ms, ninth decile 120 ms; by operation, filing 127 ms median, the workspace claim 117, finishing 97, publishing the observation 83, recording the effect 84 and the first-mode check 13; a quick request takes five holds, about 0.4 s of exclusive hold in all. Even there the median hold is over sixteen times the 5 ms objective below, so the cost lies in what runs under the hold, not only in the collection's size. No new performance measurement was run for this concept.

For the implementation, report median, tail and maximum commit wall with host load, bytes changed, CAS attempts, syscall counts and sync phases; define commit wall from a complete, file-synced candidate's publication attempt through its revision-directory durability barrier, and show preparation separately as well as end-to-end mutation wall. Use 5 ms as an investigation objective on a healthy local filesystem, not an elapsed-time unit-test assertion or permission to omit sync. Any application lock on the commit path is a deterministic design finding. A fixed change against a larger retained request population should perform the same bounded authority reads and changed-path writes, apart from explicit revision-discovery/index depth and returned results. Measure unrelated competing requests and same-identity losers separately.

Select these focused tests for basic confidence; later stress permutations are backlog. Names below describe proposed witnesses, not existing tests claimed to pass. The build design must give the concrete command for each when the implementation supplies its test entry point; existing regression selectors remain available in the named files.

|Witness|Discriminates|
|-------|-------------|
|One numbered slot, two writers; independent identities|Force both contenders to prepare from N: exactly one N+1 wins, loser cannot publish its stale image at N+2; another identity completes while the first producer is stopped before rename or during sync. No commit lock is acquired.|
|Claim intent, claim durability and restart|Crash before/after winning claim publication and sync. Recovery supersedes only an unfinished intent, never creates an execution claim; the unresolved-claims index has no false negatives. A durable claim is never replayed, including lost acknowledgement and conflicting completion.|
|Batch validation and policy reread|One invalid batch item writes nothing; after successful validation, a concurrent change conflicts only its item and preserves others. A correction acknowledged before post-claim reread vetoes execution; a later correction does not falsely claim to have revoked an already admitted effect. Failed correction publication leaves policy unavailable.|
|Closing a run against a paused filer|Pause before enrollment, after enrollment, after canonical publication and after the final open check. Closing prevents new enrollment, accounts for earlier operations and delays destructive retirement until they resolve. A closing crash resumes the sealed set without reopening.|
|Revision discovery, crash and reclamation|Fail each object/intent/revision sync boundary, regress or remove a hint and reclaim an obsolete payload while another writer prepares. Reads recover through revisions/checkpoints; a delayed writer cannot recreate an old slot because its seal remains, and no published revision references a reclaimed object. Foreign custody and symlink twins refuse. Process-kill tests do not stand for power-loss proof.|
|Projection replay and subscribe race|Repeated projection receipt does not double-count; commit at every watch/read boundary, then overflow/restart. Named-state reconciliation wakes the waiter without periodic polling or granting from a hint. A growing unrelated retained population adds no collection scan to one commit.|

These tests select the failure boundaries on which the concept depends. Broad filesystem/platform coverage, extreme retention histories, adversarial load, watch-limit exhaustion, prolonged storage faults and exhaustive multi-object schedules remain further testing chapters. This concept does not execute them or make a full test bed a prerequisite to discussing the product design (`[ORCHESTRATION-prin:environment:testing-serves-the-product]`).

## Limits and unresolved evidence · `sec:requeststore:limits`

Not established from this source reading: production uid/service topology and actual writer concurrency; the raw events behind the reported 89 seconds; deployed filesystem durability and rename/sync latency; operational limits for projection lag, objects, checkpoints and watches; a finite metadata reclamation protocol for occupied revision names; and deployment evidence excluding old hook and gateway executables during crossing. These require deployment inspection, measurement or further design, not inference from a function name. The selected batch, policy, capacity and listing semantics are no longer open alternatives. The run fence's enrollment and drain require their focused race witness before implementation is accepted.

The source proves neither exactly-once external effects nor lossless recovery after loss of the storage device. The model promises neither. It preserves custody and uncertain-effect evidence with lock-free commit publication, retains occupied revision names rather than inventing safe reuse, and makes the changed batch and policy contracts explicit implementation obligations. No Invariant-kind statement is minted or amended by this concept.
